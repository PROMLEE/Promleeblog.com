## 开始之前

我们编写测试代码的一个主要原因，是为了更放心地*重构（Refactoring）*。
很多时候，我们想把代码整理得更清晰，却担心破坏功能而不敢动手。
<br/>
<br/>
可如果一改代码，测试就接连失败，会怎样？
功能照常运行，测试却亮起红灯，这就是**脆弱的测试（Brittle Test）**。
今天来看看怎样写出**经得起重构的测试**，让我们在修改代码时有保障。

<Ads1/>

## 反例：测试实现细节

最常见的错误，是测试用户无须了解的*内部实现*。
以一个简单的**切换按钮（Toggle Button）**为例。

### 不好的测试习惯

- 检查状态（State）名称是否为 `isOpen`。
- 检查 `div` 标签的类名是否为 `active`。
- 监视内部逻辑，确认某个函数恰好被调用了两次。

这些都是代码作者随时可以修改的*实现细节（Implementation Details）*。
如果测试依赖这些细节，哪怕只改一个变量名，测试也会失败。

## 正例：围绕用户行为编写测试

好的测试关注**结果**。

- 点击按钮后，内容是否出现？
- 再点一次，内容是否消失？

内部变量叫 `isVisible` 还是 `show`，类名是 `on` 还是 `active`，用户都不关心。
用户在意的是**界面上是否出现内容**。

## 第 1 步：编写测试，关注稳定的行为

创建 `src/components/ToggleButton.test.tsx` 文件。
测试不依赖状态名称等内部实现，只验证**点击后文本是否出现**。

```tsx title="src/components/ToggleButton.test.tsx" showLineNumbers
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { describe, test, expect } from 'vitest';
// 컴포넌트는 잠시 후에 만듭니다.
import ToggleButton from './ToggleButton';

describe('ToggleButton 리팩토링 내성 테스트', () => {

  test('버튼을 클릭하면 숨겨진 메시지가 나타나고, 다시 클릭하면 사라진다', async () => {
    const user = userEvent.setup();
    render(<ToggleButton />);

    const toggleBtn = screen.getByRole('button', { name: '토글' });

    console.log('[Step 1] 초기 상태 확인');
    // 처음에는 메시지가 없어야 합니다. (queryBy 사용)
    const hiddenMessage = screen.queryByText('짜잔! 숨겨진 메시지입니다.');
    expect(hiddenMessage).not.toBeInTheDocument();

    console.log('[Step 2] 버튼 클릭 (열기)');
    await user.click(toggleBtn);
    screen.debug(); // 화면 출력

    // 클릭 후에는 메시지가 보여야 합니다.
    expect(screen.getByText('짜잔! 숨겨진 메시지입니다.')).toBeInTheDocument();

    console.log('[Step 3] 버튼 클릭 (닫기)');
    await user.click(toggleBtn);
    screen.debug(); // 화면 출력

    // 다시 클릭하면 메시지가 사라져야 합니다.
    expect(screen.queryByText('짜잔! 숨겨진 메시지입니다.')).not.toBeInTheDocument();
  });
});
```

## 第 2 步：完成初始实现（Green）

为了让测试通过，先用最常见的方式实现功能。
用一个 `useState` 管理状态。

```tsx title="src/components/ToggleButton.tsx" showLineNumbers highlight="{5,8}"
import { useState } from 'react';

export default function ToggleButton() {
  // 상태 이름을 'show'라고 지었습니다.
  const [show, setShow] = useState(false);

  const toggle = () => {
    setShow((prev) => !prev);
  };

  return (
    <div>
      <button onClick={toggle}>토글</button>
      {/* show 상태가 true일 때만 메시지 표시 */}
      {show && <p>짜잔! 숨겨진 메시지입니다.</p>}
    </div>
  );
}
```

## 第 3 步：重构代码（Refactor）

有一天，团队负责人说：
> “变量名怎么叫 `show`？改成 `isVisible` 吧。再把逻辑拆到自定义 Hook 里。”

通常我们可能会担心，改代码时是不是还得一起改测试。
但这里测试的只有**用户行为**，所以可以放心重构。
接下来动手调整代码结构。

### 调整代码结构

```tsx title="src/components/ToggleButton.tsx" showLineNumbers
import { useState } from 'react';

// [리팩토링] 로직을 커스텀 훅으로 분리하고 변수명을 바꿉니다.
function useToggle(initialValue = false) {
  // 변수명 변경: show -> isVisible
  const [isVisible, setIsVisible] = useState(initialValue);
  const toggle = () => setIsVisible(v => !v);
  return { isVisible, toggle };
}

export default function ToggleButton() {
  // 기존 useState 코드를 삭제하고 훅을 사용합니다.
  const { isVisible, toggle } = useToggle();

  return (
    <div>
      <button onClick={toggle}>토글</button>
      {/* 변수명이 바뀌었지만 화면에 그리는 결과물은 똑같습니다 */}
      {isVisible && <p>짜잔! 숨겨진 메시지입니다.</p>}
    </div>
  );
}
```

今天学习了如何编写让重构更安心的测试。

- **避开实现细节**
  状态名、函数名和 CSS 类名随时可能调整，不必测试这些细节。
- **关注行为**
  留意用户点击后在界面上能看到什么。
- **可维护性**
  改动内部代码时，测试应该继续通过。这样开发者才能放心改进代码。

现在，你可以编写经得起内部实现变动的测试了。
