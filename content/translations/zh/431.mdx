## 开始之前
给编码代理接入多个 Skill 和 MCP 服务器后，很容易以为每次都会加载用不到的功能。
实际开销取决于**什么内容在何时加载**。
Skill 的简短说明、MCP 工具定义、调用工具后返回的结果，是三种不同的信息。
混在一起看，可能会削减错地方。
<br/>
本文分别梳理 Skill 和 MCP 的加载过程，并说明实际工作中应先核对什么。

## 加载阶段
> 节省上下文可以从安排信息入手，让每个阶段只加载当时需要的内容。

Skill 提供重复任务的**处理方法**，MCP 提供外部数据查询和**执行工具**。
根据 OpenAI 文档，模型先查看 Skill 的名称与说明，匹配请求后才读取完整指引。
MCP 服务器用于访问工具与数据，Skill 则说明应按什么顺序和标准使用这些工具。
[OpenAI Developers 对 Skill 和 MCP 职责的说明](https://developers.openai.com/plugins/concepts/skills)

| 阶段 | Skill | MCP |
| --- | --- | --- |
| 发现 | 根据名称与说明判断是否适用 | 根据服务器和工具说明寻找功能 |
| 选择 | 加载 `SKILL.md` 和所需参考文档 | 加载所需工具定义 |
| 执行 | 按指引完成任务 | 将工具调用结果加入上下文 |

**延迟加载工具定义和缩小调用结果，是两项独立的优化。**
即使节省了定义开销，一次过长的搜索结果也会再次撑大上下文。

## Skill 设计
Skill 的说明应当像一块简短的路标，告诉模型*哪些请求适合使用这个 Skill*。
如果说明含糊，模型可能加载无关 Skill，或漏掉本来需要的 Skill。
OpenAI 建议让 Skill 说明简短清楚，把详细流程和示例分到按需阅读的参考文件。
[OpenAI Developers 的 Skill 上下文设计](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

```text title="skills/review-pr/"
review-pr/
├── SKILL.md
├── references/
│   ├── security.md
│   └── performance.md
└── scripts/
    └── summarize-diff.sh
```

例如，收到 PR 审查请求时，`SKILL.md` 会说明审查顺序和结果格式。
涉及安全变更就读 `references/security.md`，涉及性能变更就读 `references/performance.md`。
如果要求每次审查都读两份文档，小到一句文案的修改也会重复承担相同成本。

```yaml title="skills/review-pr/SKILL.md"
---
name: review-pr
description: PR의 코드 변경을 리뷰하고, 동작 오류와 검증 누락을 찾을 때 사용합니다.
---

변경된 코드와 관련 테스트를 확인합니다.
인증·권한 변경이면 references/security.md를 읽습니다.
성능 경로 변경이면 references/performance.md를 읽습니다.
```

<Ybox>即使参考文件已经拆开，如果 SKILL.md 仍要求“开始前阅读整个 references 目录”，拆分也无法节省开销。请同时写明各文件的阅读条件。</Ybox>

## MCP 工具
MCP 把外部系统的功能作为工具提供。
工具较多时，名称、说明和输入模式等定义可能占用上下文。
OpenAI 的 Tool Search 文档说明，在工具列表较大时，按需加载定义可以减少 token 用量。
这会增加一个搜索步骤，且可用设置因运行环境而异。
[OpenAI 文档的 Tool Search 指南](https://developers.openai.com/api/docs/guides/tools-tool-search)
<br/>
Claude Code 也通过 MCP 工具搜索延迟加载定义。文档介绍了先查看工具名称和服务器指引，再寻找所需工具的方式。
[Claude Code 的 MCP 工具搜索文档](https://code.claude.com/docs/en/mcp)
<br/>
实际工作中可以按以下顺序处理。

- 区分常用工具和不常用的工具。
- 在服务器和工具名称及说明中写清实际使用条件。
- 查看运行环境提供的工具搜索或工具许可设置。
- 减少调用结果中无用的正文与字段。

例如，任务是“只查看本次 PR 中失败的 CI”，首先需要的是失败任务的名称、错误消息和相关日志链接。
等问题范围缩小后，再获取详细日志，会比先读取完整构建日志更高效。

<Rbox>延迟加载工具定义之后，外部服务器的响应大小仍需单独控制。评估节省了多少 token 时，同时查看工具列表和调用结果。</Rbox>

## 选择标准
要决定增加 Skill 还是 MCP，可以先判断所需信息的类型。

| 所需内容 | 合适的位置 | 示例 |
| --- | --- | --- |
| 可复用的操作顺序 | Skill | PR 审查流程与输出格式 |
| 视任务选择的详细指引 | Skill 参考文件 | 安全审查清单 |
| 查询当前状态或执行操作 | MCP 工具 | 查询 CI 结果、创建 Issue |
| 整个仓库的通用规则 | `AGENTS.md` | 测试命令和变更边界 |

例如，“分析 CI 失败原因”可以同时使用一个 Skill 和一个 MCP 服务器。
Skill 规定分析顺序，MCP 获取当前 CI 结果。
划分职责后，静态流程无需每次从外部获取长篇内容，实时数据也无需复制到 Skill 文件里。

## 核对方法
更改设置后，确认成本和质量是否一起改善。
可以分别选一个简单任务、一个需要外部数据的任务和一个复合任务，按相同条件比较。

- 在新会话中核对默认可见的 Skill 说明和 MCP 工具定义。
- 记录工作中实际加载的 Skill 正文与参考文件。
- 比较调用过的工具、响应大小、输入 token 和总耗时。
- 同时检查准确率是否下降，或验证遗漏是否增多。

**如果 token 减少了，却找不到必需的工具，优化就失败了。**
要同时观察任务完成率和响应时间。
OpenAI 文档也建议选取代表性任务，按完成率、输入 token 和延迟比较工具加载方式。
[OpenAI 文档的工具加载策略](https://developers.openai.com/api/docs/guides/tools-tool-search)

## 结论
Skill 和 MCP 的上下文成本取决于实际加载的内容。
按**说明元数据 → 完整指引与工具定义 → 调用结果**的顺序逐项核对。
<br/>
Skill 可以采用简短入口和按条件读取的参考文档，MCP 则适合使用便于搜索的工具说明，并只返回所需结果。
