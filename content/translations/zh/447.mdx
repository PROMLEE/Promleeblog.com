## 开始之前

我和 AI 花了一个小时分析缺陷，完成了一半的实现。
第二天在新会话里说“继续昨天的工作”，它却从已经核对过的文件读起，再次提出已经排除的假设。
如果把之前的对话全部粘贴进去，旧日志和失败的修改又会占满新的上下文。

<br/>

为了接着做，下一次会话需要有可供判断的**当前状态与核查依据**。
记录目标、代码实际改到了哪里、验证过什么，以及接下来要做什么。
本文区分对话压缩与任务交接，并介绍如何借助仓库里的简短记录恢复工作。

## 恢复与交接

> 恢复对话和核对当前代码状态是两个独立步骤。

如果同一个工具可以重新打开旧会话，接着聊会比较方便。
对话保存后，其间人手修改的文件和切换后的分支仍要核对。
不管是交接给新会话，还是恢复原有会话，都要确认当前工作路径与改动状态。

| 方式 | 继承的信息 | 需要另行核对的内容 |
| --- | --- | --- |
| 恢复旧会话 | 已保存的对话和工具能恢复的状态 | 当前工作路径、文件和运行环境 |
| 压缩对话 | 后续工作需要的对话状态 | 重要条件和依据是否保留 |
| 依据交接记录重新开始 | 明确记录的目标、状态和下一步 | 记录与当前代码是否一致 |

OpenAI 介绍了用于延续长对话的压缩功能，并指出 API 返回的压缩项是不透明的状态。
[OpenAI 对话压缩文档](https://developers.openai.com/api/docs/guides/compaction)

API 压缩项与供人审阅的 `handoff.md` 在格式和用途上都不同。
交接记录是团队文档，便于在不同工具或新会话中核对工作依据。

## 应记录的状态

与其概括整段对话，可以只保留下一步判断所需的四项信息。
以修复搜索筛选器的后退异常为例，可以这样整理。

| 项目 | 应记录的内容 | 示例 |
| --- | --- | --- |
| 目标和边界 | 完成条件、修改和排除范围 | 恢复 URL 与输入值，API 不在修改范围内 |
| 当前代码 | 工作路径、基准提交、改动文件 | 搜索表单修改中，测试文件尚未跟踪 |
| 验证依据 | 命令、结果及验证所针对的代码状态 | 类型检查通过，后退测试失败 |
| 下一步 | 未完成事项、待作判断 | 核对 URL 变化时本地状态如何更新 |

### 事实与假设

“后退时 URL 恢复为 alpha，但输入框仍显示 beta”是观察结果。
“只读取了初始值，遗漏了状态同步”是关于原因的假设。
在记录中把两者分开，可以避免下一次会话把推测当成确定的事实。

<br/>

必要时也可以记录排除的做法和原因。
例如：“输入框状态异常的复现中，只有输入框与 URL 不一致，因此暂不采用搜索 API 缓存导致故障的假设。”
失败尝试的所有日志和代码无需复制到正文。
保留原始日志的位置或相关文件，供后续查看。

<Bbox>
把下一次会话的第一步写成一个具体动作。
“检查 SearchForm 如何订阅 URL 变化并更新本地输入状态”比“收尾搜索功能”更容易着手。
</Bbox>

## 交接文档

下面是按任务记录状态的文档示例。
文件名和位置由团队决定，工具不会赋予它特殊含义。
在新会话的请求里写明路径，才能引导工具实际阅读。

```yaml title="docs/tasks/search-history-handoff.yaml"
task: search-history
updated_at: "2026-10-15T15:00:00+09:00"
goal: 뒤로 가기와 새로고침 뒤 URL과 입력값을 함께 복원
scope:
  include: 검색 폼 상태와 관련 테스트
  exclude: 검색 API와 정렬 규칙
workspace:
  path: /Users/dev/work/shop
  head: "git rev-parse HEAD로 확인한 커밋 해시"
  uncommitted: true
  changed_files:
    - src/features/search/SearchForm.tsx
  untracked_files:
    - tests/search-history.spec.ts
observed:
  - alpha → beta → 뒤로 가기에서 URL은 alpha, 입력창은 beta
hypothesis:
  - URL 변경을 로컬 입력 상태가 다시 반영하지 않을 수 있음
checks:
  - command: npm run typecheck
    result: passed
  - command: npx playwright test tests/search-history.spec.ts
    result: failed
    detail: 입력값 alpha를 기대했으나 beta가 남음
  - command: npm run build
    result: not_run
evidence_scope: 위 변경 파일 상태에서 실행한 예시 결과
next_action: URL 변경과 로컬 상태 동기화 경로 확인
```

这是用于说明格式的虚构示例，未使用实际项目的运行结果。
实际记录应填入当前路径、提交哈希、执行的命令和结果。
如果保存了日志，补上路径，并确认下一个会话能够访问。

<br/>

尤其要注意，**只有提交哈希，无法传递未提交的改动。**
在同一个检出目录里继续时，先确认文件仍在。
如果要迁移到另一个环境，按团队选择的方式，通过提交、补丁等手段另行传递必要改动。
只写下工作路径，并不会在另一个环境中生成文件。

### 何时更新

每次对话都重写长篇状态记录，成本会越来越高。
在下列工作阶段切换时更新更实用。

- 完成原因分析并开始实现时
- 验证失败已确定为下一次修改的依据时
- 暂停任务或交给新会话、其他工具时
- 完成后整理剩余限制和最终验证时

已完成的事项无需一直累加，只保留当前判断所需的内容。
如需查看详细历史，可参考 Git 变更历史与原始依据。

## 核对代码状态

阅读交接记录后，对照实际仓库状态。
在 macOS 终端可用下面的命令查看当前路径、提交、已跟踪文件的改动和新文件。
Windows 和 Linux 上的 Git 命令相同，只需按环境调整路径写法。

```bash title="재개 전 저장소 확인"
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short
git diff --stat
git diff --cached --stat
git ls-files --others --exclude-standard
```

仅看 `git diff` 可能漏掉已暂存的改动和未跟踪文件。
按需阅读相关文件的实际差异和新文件内容。
上面的命令也看不到被忽略的环境文件或外部数据库状态，因此需要单独核对任务所需的运行环境。

<Img src="/261015-100003.webp" width={650} height={433} alt="在新会话恢复任务的步骤，从阅读交接记录、核对代码状态和验证结果到执行下一步"/>

<Ybox>
即使 HEAD 相同，只要未提交文件有变化，之前测试结果的适用范围就可能改变。
提交不同也未必需要重跑所有检查。
先核对改动与原有依据之间的关系，再重跑受影响的检查。
</Ybox>

## 恢复会话

Claude Code 可以通过 `claude --continue` 恢复当前目录最近的会话。
若要从历史对话列表中选择，使用 `claude --resume`。
[Claude Code 恢复对话](https://code.claude.com/docs/en/common-workflows)

```bash title="Claude Code 이전 세션 재개"
claude --continue
```

Codex CLI 可以通过 `codex resume` 选择已保存的对话继续。
在应用中，打开对应项目的已有聊天即可继续。
[Codex 项目与聊天](https://learn.chatgpt.com/docs/projects)

```bash title="Codex CLI 이전 세션 재개"
codex resume
```

无论用哪种方式，都要核对选择的工作目录和聊天是否正确。
可以明确要求先把当前记录与实际代码对照，再做剩余事项，比单说一句“继续”更清楚。

### 对话压缩

如果仍在做同一项任务，只是对话变长了，可以考虑压缩。
Claude Code 提供自动压缩和 `/compact`，也可以指定要保留的内容。
[Claude Code 上下文管理](https://code.claude.com/docs/en/best-practices)

```text title="Claude Code 세션의 압축 요청 예시"
/compact 목표와 제외 범위, 변경 파일, 검증 결과, 남은 판단을 보존
```

压缩用于继续当前任务，交接文档用于让人核对依据，或把工作移交到其他会话。
不同工具的压缩行为可能有差异，重要状态需要结合实际文件确认。
切换到无关任务时，可以先保存必要的交接记录，再另开会话，便于管理上下文。

## 发给新会话的请求

提供记录路径和启动步骤，可以省去复制整个对话。
使用下面的请求时，把交接文件路径和任务名称改为当前环境中的实际值。

```text title="작업 재개 요청"
docs/tasks/search-history-handoff.yaml을 읽고 작업을 이어가세요.
먼저 현재 경로, HEAD, 미커밋·미추적 변경을 기록과 대조하세요.
차이가 있으면 관련 파일을 확인해 현재 상태를 갱신하세요.
통과·실패·미실행 검사를 구분하고 결과의 적용 범위를 확인하세요.
다음 행동에 필요한 파일부터 읽고, 기존 목표와 제외 범위를 지키세요.
수정 뒤 관련 검증을 실행하고 인계 기록을 최신 상태로 바꾸세요.
```

即使限制新会话最初阅读的文件数量，也应允许它读取必要的依赖。
这样可以减少无关的重复探索，同时保留必要的核查。

<Rbox>
旧记录里的“完成”或“测试通过”需要和当前代码状态核对。
记录与实际状态不一致时，先找出发生了什么变化，再决定怎样处理代码。
</Rbox>

## 记录的有效期

第 2 篇的 `AGENTS.md` 和 `CLAUDE.md` 用来存放仓库中反复适用的规则。
如果把本次任务的失败日志和下一步也不断加入通用指引，之后的所有任务都会读到同一份过时上下文。
根据信息能保持有效的时间，选择不同的存放位置。

| 信息 | 合适的位置 | 更新条件 |
| --- | --- | --- |
| 通用规则和验证命令 | 仓库指引 | 规则或环境变化时 |
| 本次任务的当前状态 | 按任务维护的交接文档 | 阶段切换、暂停或恢复时 |
| 详细失败输出 | 日志与测试产物 | 按每次运行结果保存 |
| 最终设计与用法 | 正式文档或 PR 说明 | 实现和共识落实时 |

把已完成的交接文档移出活动任务列表，或标记为完成。
这样后续任务就不会把过时的未完成指令误当作当前要求。
只有值得复用的结论才移入正式文档或通用指引。

<Bbox>
评估交接质量时，可以看下一个会话重新确认了哪些内容。
检查它是否重复了已完成的探索、遗漏了未完成事项，或因为记录与当前代码不一致而返工。
</Bbox>

## 结论

要继续 AI 任务，除了简短的对话摘要，还需要记录代码状态与依据。
写下目标、修改边界、未提交文件、验证结果和下一步，恢复时再与实际状态核对。

<br/>

可以把**阅读记录 → 核对代码状态 → 确认依据 → 执行下一步**作为任务启动流程。
第 11 篇将介绍如何根据这些记录和任务边界并行处理多项工作，再集成各自的成果。
