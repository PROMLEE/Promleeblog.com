## 开始之前

改按钮文案和排查登录会话偶尔失效，你会用同一个模型、同一档推理强度吗？
改文案只需找到修改位置，排查会话则要追踪 Cookie、服务端渲染和重定向之间的关系。
用同一套设置处理两种任务，可能让小改动等得更久，也可能让复杂问题反复被改错。

<br/>

**模型路由是按任务选择模型与推理强度，并在需要时调整选择的规则。**
可以从简单的规则开始。
独立开发时，有一套开工前的选型标准，以及卡住时的调整标准，就已经够用。
本文介绍适用于 Claude Code 和 Codex 的选型标准、配置示例、升级规则和成本比较。

## 任务分类

> 比文件数量更重要的是答案有多明确，以及改错会有什么影响。

只改一个文件的任务也可能很难。
一行权限检查可能影响整个服务，而修改 20 个文件的 import 路径，可能只需遵循既定规则。
拿到任务后，先回答三个问题。

- **怎样才算改对？**
有修改前后的示例和完成条件，判断起来更容易。
- **影响范围有多大？**
确认是只涉及一处界面，还是会同时改变 API、数据库和认证边界。
- **如何验证？**
判断类型检查是否足够，还是需要复现多种状态及用户权限。

据此将任务分为快速路径、默认路径和高性能路径。
这些路径是团队测试后分配的角色，会随模型和需求变化。

| 路径 | 任务条件 | 开发示例 | 初始设置 |
| --- | --- | --- | --- |
| 快速路径 | 预期结果和修改位置明确 | 修改按钮文案、整理 import、修复已复现的简单类型错误 | 轻量模型、低推理强度 |
| 默认路径 | 需要阅读现有模式并选择实现 | 添加搜索筛选、表单校验、处理 API 响应 | 主力模型、默认推理强度 |
| 高性能路径 | 需要比较多个假设、设计方案或审查风险 | 排查会话丢失、并发错误、设计数据迁移 | 判断能力较强的模型、按需设置推理强度 |

OpenAI 官方文档建议用相同输入比较模型和推理设置，选择达到质量要求的最轻量配置。
[OpenAI 模型选择指南](https://developers.openai.com/api/docs/guides/model-selection)

<Bbox>
起步时，把平常使用的主力模型设为默认路径，再把反复出现的简单任务移到快速路径。
如果连陌生仓库的任务也一次性换成轻量模型，结果不佳时就难以区分模型能力与任务信息不足。
</Bbox>

## 模型与推理强度

更换模型和调整推理强度是两个选择。
模型影响基础能力与定价结构，推理强度则在支持该设置的模型内调节用于推理的资源。
轻量模型即使用高推理强度，也未必能达到另一款高性能模型的效果。

<br/>

例如，为现有 React 表单增加必填校验，可以从主力模型的默认强度开始。
校验函数和错误提示位置明确之后，如果只需整理提示文案，用低强度即可。
如果需要决定在哪一层校验，或如何统一服务端和客户端的错误契约，就要给判断留出更多预算。

<Ybox>
同时更换模型和推理强度，很难查清结果变好或变差的原因。
保持任务请求和验证标准一致，每次只改一项进行对比。
模型和产品支持的推理级别不同，需查看选择界面或官方配置文档。
</Ybox>

## Claude Code 配置

Claude Code 启动时可指定 `--model`，也可在会话中用 `/model` 选择模型。
`sonnet`、`opus` 等别名对应的实际模型及其可用性，应在当前环境中确认。
[Claude Code 模型配置](https://code.claude.com/docs/en/model-config)

```bash title="터미널에서 Claude Code 시작"
claude --model sonnet
```

任务进行中需要分析复杂原因时，可以在会话中切换模型。

```text title="Claude Code 세션"
/model opus
```

### 规划与实现

把确定结构和按该结构实现分成两个阶段，也是一种路由方式。
Claude Code 的 `opusplan` 在规划模式使用 Opus，在执行模式切换到 Sonnet。
[Claude Code 的 opusplan 设置](https://code.claude.com/docs/en/model-config#opusplan-model-setting)

```bash title="계획과 구현 모델 분리"
claude --model opusplan
```

例如，添加搜索功能时，可以在规划阶段确定 URL 查询结构、数据查询位置和空结果处理方式。
实现阶段按这些决定编写组件与测试。
除了“在服务端处理”这类结论，计划还要列出修改文件、输入输出及验证条件，避免实现模型再解一遍同样的问题。

<br/>

分阶段也有交接成本。
只改一句文案时，单独安排设计阶段可能增加调用和等待时间。
把这种方式用于确实需要选择设计方案的任务。

## Codex 配置

Codex 可分别配置模型与推理强度。
CLI 配置项 `model_reasoning_effort` 的可选值取决于所选模型与客户端支持的级别。
[Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)

下面演示如何在 CLI 中明确指定模型和推理强度。
模型 ID 应选择当前账号可用的值。

```bash title="Codex CLI 기본 작업"
codex --model gpt-6.1-sol --config model_reasoning_effort='medium'
```

```bash title="Codex CLI 복잡한 원인 분석"
codex --model gpt-6.1-sol --config model_reasoning_effort='high'
```

第二个示例只提高同一模型的推理强度。
先比较哪些任务从这种调整中受益。如果仍达不到要求，再考虑其他模型。
在应用中，可以在模型与推理级别选择界面采用同一标准。
这些命令用于明确设置，按难度自动路由还需要用户自行制定并执行选择规则。

## 失败原因与升级

测试失败后，先检查原因，再决定是否更换模型。
依赖安装失败、环境变量为空或复现步骤有误，都可能是运行条件造成的。
先对失败分类，再决定是否**升级**模型或提高推理强度。

| 失败信号 | 优先操作 | 升级判断 |
| --- | --- | --- |
| 找不到文件 | 提供实际路径和入口 | 提供路径后仍反复误解依赖关系时考虑升级 |
| 需求不明确 | 确认预期行为和排除范围 | 需要产品决策时向用户确认 |
| 无法运行测试 | 检查环境、命令和测试数据 | 单纯的环境问题无需升级 |
| 同一修改反复失败 | 固定失败输入与观察结果 | 无法提出新的可验证假设时升级 |
| 发现认证或数据边界 | 重新评估影响范围和验证步骤 | 增加推理预算并安排人工审查 |

重试次数也要设限。
例如，可以从“针对同一复现案例改了两次仍无法缩小原因范围，就整理情况并升级”这条规则开始。
两次只是团队可以调整的运行标准。

<Rbox>
如果修改试图通过移除权限检查、删除测试或忽略异常来消除失败，应在升级前暂停。
即使用了高性能模型，涉及认证、支付和数据的变更仍须经过审查并满足完成条件。
</Rbox>

### 交接摘要

切换到新会话或其他工具时，整理工作状态和核查依据即可。
同时保留可重新查看当前代码和日志的路径。

```text title="handoff.md"
목표: 새로고침 뒤 검색 필터 유지
완료 조건: q와 status가 URL에서 복원되고 뒤로 가기도 동작
수정 파일: src/features/search/SearchForm.tsx
현재 변경: 초기값을 searchParams에서 읽도록 수정
통과: 타입 검사, 초기 필터 복원 테스트
실패: 뒤로 가기 후 입력값이 이전 상태로 돌아오지 않음
재현: 필터 A → 필터 B → 브라우저 뒤로 가기
관찰: URL은 A지만 입력값은 B로 남음
남은 판단: URL 변경과 로컬 입력 상태의 동기화 방식
제외 범위: API와 검색 결과 정렬은 변경하지 않음
```

更强的模型可以根据这些信息，先检查 URL 与本地状态的关系。
这样可以少做一些已完成的 API 探索和首次复现工作。

## 每项完成任务的成本

评估路由效果时，要比较**每项通过验证的任务的总成本**。
轻量模型失败后再交给高性能模型，会增加首次尝试和交接的成本。

以下数字仅用于演示计算，未使用实际价格或基准测试。
将输入、输出与推理 token 换算为同一单位的调用成本。

| 路径 | 首次尝试 | 重试与交接 | 更强模型运行 | 完成前的总成本 |
| --- | --- | --- | --- | --- |
| 从高性能模型开始 | 10 | 0 | 0 | 10 |
| 由轻量模型完成 | 2 | 0 | 0 | 2 |
| 轻量模型失败后升级 | 2 | 1 | 10 | 13 |

如果升级比例为 `p`，本例的平均成本就是 `2 + 11 × p`。
实际工作中，更强的模型可能复用之前的修改、更快完成，也可能花更多时间撤销错误的改动。
应按实际任务记录计算费用，避免把这个公式直接当成通用的节省比例。

### 对比记录

选用重复出现的代表性任务，取得默认路径的基准值，再用相同的起始代码、请求和验证条件比较其他设置。
起步时记录以下内容即可。

- 任务类型、起始模型及推理强度
- 是否满足完成条件，以及升级原因
- 包含重试和升级在内的总耗时
- 使用 API 时，按实际用量与计费口径计算的费用
- 人工修改时间和审查发现的问题

订阅版 Claude 和 Codex 的用量限额无法直接按 API token 单价换算。
订阅环境可以比较完成率、等待时间与限额消耗。API 环境则按实际用量和适用费率计算费用。

<Bbox>
分别比较错字修复、常规功能实现、复杂缺陷分析等任务类型。
如果只看总体平均值，简单任务省下的费用可能掩盖困难任务的返工成本。
</Bbox>

## 结论

模型路由根据预期结果是否明确、影响哪些边界和如何验证，来决定任务的初始设置。
从反复出现的简单修改开始试用轻量路径，并给复杂设计和高风险改动留足推理预算。

<br/>

卡住时先核对环境与任务信息，确实是模型判断不足时再升级。
同时管理**初始设置、升级标准、交接摘要和每项完成任务的成本**，就能根据完成工作的耗时和费用选择模型。
