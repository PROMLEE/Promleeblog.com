## 开始之前
长期用 AI 编码代理工作时，模型选择会影响*成本*，工作方式也会带来很大差异。
实现同一项功能，一个代理只读`필요한 파일`（所需文件），一次就通过测试，另一个则遍历`저장소 전체`（整个仓库），改了几轮后又重新开始。
差异来自输入 token、工具调用次数、等待时间和开发者复核的时间。累积起来，差别会越来越明显。
<br/>
*上下文工程*是**按合适的顺序提供当前任务真正需要的信息**。
它让代理拿到准确完成工作所需的内容，并留下可供后续任务复用的状态。
Claude Code、Codex 等 AI 编码代理都适用这个原则。
<br/>
本文会介绍一种同时减少 token 用量和返工的实际工作方式。
<Bbox>即使公司目前提供的代理额度还够用，养成减少 token 消耗和返工的习惯，也能更从容地应对突然的策略变化或模型切换。</Bbox>

## 节省 token 的原则
> 简短的提示词有时反而会消耗更多 token。

信息不足时，代理可能`더 많이 탐색`（扩大搜索范围）并读到不相关的文件，也可能基于错误假设`수정과 테스트를 반복`（反复修改和测试）。
如果一次塞入所有架构文档和日志，重要指令又会被淹没，输入成本也会增加。

### token 浪费的来源
- **不必要的仓库探索**  
  代理读取与任务无关的文件，导致上下文变大。
- **重复的仓库指引**  
  AGENTS.md、CLAUDE.md 和 README 重复写相同规则，每项任务都会再次读取。
- **工具输出过大**  
  直接传递完整测试日志、完整 API 响应或构建产物。
- **缺少验证的修改**  
  修改范围和完成条件不明确，导致同一个文件被反复修改。

token 用量是成本指标，返工次数也是质量指标。
*即使用量少，频繁返工的工作流程也还有改进空间。*
衡量一项任务的效率时，除了输入和输出 token，还可以记录工具调用数、失败测试数和人工撤销的变更数，再据此改进。

### 衡量指标
一开始无需建立大型观测系统。
选三个同类任务，记录下表项目，就可以比较改进效果。

| 衡量项目 | 负面信号 | 改进目标 |
| --- | --- | --- |
| 读取文件数 | 远超任务范围 | 限于修改路径所需的文件 |
| 工具调用数 | 重复运行同一命令 | 提前写明探索和验证命令 |
| 测试重试 | 原因不明便反复重跑 | 只传递失败日志中的相关部分 |
| 修改文件数 | 小功能牵涉大量改动 | 在任务请求中写明允许范围 |
| 人工审查时间 | 需要重新推断意图 | 同时保留完成条件和验证结果 |

## 任务范围
只给代理一个功能名称，它就得自己推断所需文件与完成标准。
<Bbox>只给代理项目目录，再说一句“帮我修改某功能”，可能让它遍历全部文档并消耗 token。</Bbox>
在简单任务中可能看不出问题。仓库越大，搜索范围和假设就会迅速增加。
**先明确任务范围和完成条件**，可以让代理用较低成本着手。

### 任务请求模板
下面的模板可用于聊天输入、Issue 正文或自动化流水线的任务说明。

```text title="agent-task-template.txt"
목표
- 게시글 목록 API에 페이지네이션을 추가합니다.

수정 범위
- src/app/api/posts/route.ts
- src/lib/posts/query.ts
- 관련 테스트 파일

완료 조건
- page와 limit이 없을 때 기존 응답과 호환됩니다.
- 잘못된 쿼리는 400 응답을 반환합니다.
- npm test와 npm run lint가 통과합니다.

금지 사항
- 데이터베이스 스키마와 공개 응답 필드는 변경하지 않습니다.
- 지정한 범위 밖 리팩터링은 하지 않습니다.

작업 방식
- 수정 전에 관련 파일만 읽고 변경 계획을 세웁니다.
- 완료 후 수정 파일과 검증 결과를 짧게 요약합니다.
```

这一格式给代理*保留了选择实现步骤的空间*。
由代理解决问题，由人确定可以读到哪里，以及用什么判定成功。

### 何时拆分任务
一次任务跨越多个边界时，可以拆开处理。
例如，把认证、数据库迁移和界面改动放在同一个请求里，会把各自的失败原因混在一起。
按下面的顺序拆分，可以缩小所需的上下文。

- `조사 단계`（调查阶段）只核对相关路径和当前行为。
- `구현 단계`（实现阶段）只处理已确定的文件与测试。
- `리뷰 단계`（审查阶段）只核对变更 diff 和验证结果。

这样拆分后，无需把前一阶段的长篇探索日志全部带到下一阶段。

## 仓库指引
`AGENTS.md` 和 `CLAUDE.md` 适合传达团队规则。
如果把所有历史和例外都堆在同一份文件里，小改动也会加载无关指引。
可以把指引写成*导航*，让代理找到对应任务的文档和命令。

### 最少必要指引
根目录指引只保留大多数任务共用的内容，例如以下项目。

```md title="AGENTS.md"
 # 프로젝트 공통 규칙

- 패키지 설치는 npm을 사용합니다.
- 변경 후 npm run lint와 npm test를 실행합니다.
- API 응답 형식 변경은 요청에 명시된 경우에만 허용합니다.
- 데이터베이스 변경은 prisma/schema.prisma와 migration을 함께 검토합니다.

 # 작업별 안내

- 인증 작업은 docs/auth.md를 읽습니다.
- 배포 작업은 docs/deploy.md를 읽습니다.
- 데이터베이스 마이그레이션은 docs/database-migrations.md를 읽습니다.
```

认证或部署等少数任务才需要的细节，可以放进独立文档。
代理仅在处理对应任务时阅读，其他任务不必载入完整说明。
<br/>
OpenAI 官方文档也提到，冗长或重复的 `Skill` 说明，以及过多的仓库指引，会占用上下文，让模型更难选出当前需要遵守的要求。
[OpenAI 文档：重新设计 Skill 与提示词](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

### 可以从根目录指引移出的内容
- 已经能在 package.json 脚本中核对的长命令列表。
- 只在 Git 历史中有意义的旧决策记录。
- 仅适用于特定功能或目录的详细规则。
- 在不同文档中重复出现的代码风格规则。

移除前，先把必须保留的内容转到独立文档，并在根目录指引里留下链接与适用条件。

## 任务状态
继续长任务时，如果保留整段对话，之前的探索结果与失败日志会持续占用上下文。
把任务状态保存在*短文件*里，新会话就能只读必要事实并接着做。

### 状态文档
状态文档可以很短。
有下面这些信息，新代理或其他团队成员就可以直接接手。
```md title="docs/agent-state/pagination.md"
 # 게시글 페이지네이션 작업 상태

 ## 완료
- 기존 목록 API의 응답 구조를 확인했습니다.
- page와 limit의 기본값을 합의했습니다.

 ## 남은 작업
- query.ts에 범위 검증을 추가합니다.
- route 테스트에 잘못된 limit 사례를 추가합니다.

 ## 검증 명령
- npm test -- posts
- npm run lint

 ## 결정 사항
- 기존 클라이언트 호환성을 위해 total 필드는 추가하지 않습니다.
```

这份文件是项目的*决策记录*。
任务结束后，可以删除它，或只把关键决策移到 `ADR` 和 Issue 中。
<br/>
Claude 的官方指南也建议，对于横跨多个上下文窗口的任务，先准备测试和设置，再在后续阶段使用结构化状态。
[Anthropic 提示词最佳实践](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/prompt-templates-and-variables)

### 何时开启新会话
在以下情况下，开启新会话可能更有效率。

- 调查已经结束，实现范围已经确定。
- 错误日志很长，已经积累多次失败尝试。
- 负责的功能完全不同，原先的文件列表已无用。
- 只剩审查，不再需要实现对话中的细节。

新会话的第一条请求只写任务状态文件、变更文件列表和验证命令。
这样可以腾出上下文，同时保留人作出的决定。

## 工具输出与验证
代理使用终端和 MCP 工具时，结果通常比命令本身消耗更多 token。
可以只返回下一步判断所需的结果，避免加载完整构建日志或全部数据表。

### 工具输出
找文件时，先缩小路径与搜索结果，再读取必要的内容。

```bash title="terminal-workflow.sh"
 # 필요한 경로를 먼저 찾습니다.
rg --files src | rg 'posts|pagination'

 # 관련 심볼이 있는 줄만 확인합니다.
rg -n 'getPosts|page|limit' src/app src/lib

 # 확정한 파일만 읽습니다.
sed -n '1,220p' src/lib/posts/query.ts
```

测试失败时，也先查看失败的测试名称、错误消息和相关调用栈帧。
只有仍不清楚原因时，才扩大输出范围。

### 验证循环
为节省 token 而跳过测试，最终可能带来更多返工。
先运行与任务完成条件匹配的最小检查，最后再运行完整验证。

```text title="verification-order.txt"
1. 변경한 함수의 단위 테스트를 실행합니다.
2. 변경 경로의 타입 검사와 린트를 실행합니다.
3. 영향 범위가 확인되면 전체 테스트를 실행합니다.
4. 수정 파일과 테스트 결과를 diff와 함께 검토합니다.
```

在 Codex 中，可用 `/status` 查看当前会话的模型、上下文占用和 token 用量。
记录任务前后的数值，就能判断哪些指引与工作流程起了作用。

## 团队检查清单
✓ 在请求中写明目标、修改范围、完成条件和禁止事项。
✓ 根目录的 AGENTS.md 或 CLAUDE.md 只保留通用规则与文档路径。
✓ 先搜索或总结长日志和大型响应，只读必要部分。
✓ 调查、实现和审查等上下文不同的阶段使用独立会话。
✓ 把任务状态与验证命令记录到仓库里的短文档。
✓ 先执行小范围测试，最后完整验证并审查 diff。
✓ 在一个月内选三个任务，对比读取文件数、测试重试和审查耗时。

## 结论
要节省 Claude 和 Codex 的 token，可以从设计工作环境入手。
让代理读到正确的文件、只调用必要的工具，并尽量在一次修改后完成验证。
<br/>
可以先做好三件事：把任务请求写成契约，按任务拆分仓库指引，并把状态保存在文件中。
