## 开始之前

团队成员使用 AI 的方式各异，PR 里留下的信息也会不同。
有的 PR 交代清楚了修改原因和测试结果，有的却只写了“用 AI 实现，能运行”。
代码生成得快，审查者却得重新查找需求和验证命令。

<br/>

本系列分别介绍了如何提供必要的上下文、选择模型和验证结果。
最后一篇将把这些方法串成**让下一位接手者有据可依的开发流程**。
示例任务是在现有服务里添加搜索词和状态筛选。
文中的文档和结果仅用于演示方法，未采用特定项目的实测结果或生产力数据。

## 如何启动任务

> 在交付实现之前，先确定如何确认任务已经完成。

比起“改进搜索”，直接描述用户操作和预期结果更清楚。
本任务的完成条件是把搜索词和状态筛选写入 URL，并在刷新或后退时恢复页面上的相应值。
空结果和错误提示也在范围内，排序规则和数据库结构则保持原样。

<br/>

任务负责人确定完成条件和变更边界。
AI 可以找出并解释现有代码的约束与可选做法。任务请求应写明判断标准，避免 AI 自行决定会改变产品行为的选项。
如果现有需求足以支持某项实现决策，就在该范围内继续。

```yaml title="docs/tasks/search-filter.yaml"
task_id: search-filter
goal: 검색어와 상태 필터를 URL과 동기화
acceptance:
  - 검색 시 q와 status가 URL에 반영됨
  - 새로고침 뒤 URL과 화면 필터가 일치함
  - 뒤로 가기 뒤 이전 필터가 복원됨
  - 빈 결과와 API 오류를 구분해 표시함
scope:
  include:
    - 검색 폼과 상태 처리
    - 기존 검색 API의 필터 처리
    - 관련 테스트
  exclude:
    - 정렬 규칙 변경
    - DB 구조 변경
contract: docs/contracts/search-filter.md
verification:
  - 저장소에 정의된 타입 검사
  - 필터 파싱과 API 계약 테스트
  - 실제 브라우저의 새로고침과 뒤로 가기
```

工具不会把这个文件当成配置自动执行。
在任务请求里指出它的路径，并按实际仓库的命令和文档填写。
小改动只需使用相关条目。

<Bbox>
团队第一次尝试时，可以选一项经常重复且容易验证结果的任务。
先挑一个已有模式可循的功能，走通请求、验证和审查流程，再考虑把完成标准模糊的大项目交给 AI。
</Bbox>

## 各阶段应留下的依据

依次衔接请求、契约、实现、验证和审查。
每个阶段结束时，都要留下下一阶段能用的依据。
衡量覆盖整个过程，结果用于改进下一项任务。

<Img src="/261015-120002.webp" width={650} height={433} alt="团队 AI 开发循环，串联请求、契约、实现、验证和审查，并根据完成率、返工、耗时和成本改进"/>

| 阶段 | 要做的判断 | 留给下一阶段的内容 |
| --- | --- | --- |
| 请求 | 目标和完成条件清楚吗？ | 任务说明和排除范围 |
| 契约 | 页面和 API 对行为的预期一致吗？ | 参数、响应和错误处理约定 |
| 实现 | 需要哪些信息，应从哪里修改？ | 代码、变更原因和待决定事项 |
| 验证 | 最终代码满足完成条件吗？ | 执行的命令、结果和未验证范围 |
| 审查 | 是否检查了变更意图和回归风险？ | 审查结论和后续行动 |

Claude Code 官方文档也建议区分探索、规划和实现，并提供测试或预期结果等可核查标准。
[Claude Code 最佳实践](https://code.claude.com/docs/en/best-practices)

小任务可以在短暂探索后直接进入实现。
各阶段可以保持简洁，只需确保必要的判断和依据都有记录。

## 上下文与契约

开始时，把 AI 首先阅读的内容限制为通用指引、相关入口和本次任务说明。
告知搜索页面入口文件、现有 API 路由和测试命令的位置，能减少重新探索整个仓库的工作。
发现确实需要更多依赖时再阅读。

<br/>

第 2 篇的 `AGENTS.md` 和 `CLAUDE.md` 用来保存仓库内反复适用的规则。
第 4 篇的任务请求记录本次功能的目标和边界，第 10 篇的交接文档则记录进行中的状态。
按信息各自的有效期分开维护。

### 搜索契约

先确定页面和 API 共享的规则。
例如，把状态筛选的允许值、空搜索词的处理、响应字段和错误状态写下来。
在实际代码中核对前端发送的参数和服务端读取的参数。

```text title="docs/contracts/search-filter.md"
입력: q는 검색어, status는 all 또는 active 또는 archived
빈 q: 검색어 제한 없이 상태 필터만 적용
status 누락: all로 처리
성공: HTTP 200, items 배열과 nextCursor 반환
잘못된 status: HTTP 400, INVALID_QUERY 오류 반환
빈 결과: HTTP 200, items는 빈 배열
URL 복원: 누락된 status도 화면에서는 all로 표시
```

这里的契约只是示例行为。
如果现有服务有其他规则，应遵循原有约定，或先达成修改共识。
除了类型声明，还要核对真实请求和响应是否符合契约。

## 模型选择与实现

遵循现有模式的筛选功能，可以从第 6 篇的默认方案着手。
遇到无法复现的状态异常，或需要分析跨多个层级的问题时，先检查信息缺失和环境问题，再调整模型或推理强度。
测试失败有多种原因，需要先定位再判断是否与模型能力有关。

<br/>

第 5 篇的 Skill 用于可重复的流程和规则，MCP 用于查询必要的外部状态。
第 9 篇的缓存适合在确有重复输入时测量后应用。
只加载本功能实际需要的工具和文档。

### 如何判断是否并行

搜索契约和负责的文件足够稳定时，可以并行实现页面和 API。
如果契约还在变化，先确定契约，再分工。
采用并行方式时，按第 11 篇的方法隔离工作空间、划分修改责任，并在集成后检查完整链路。
小功能放在一个会话里依次实现，也可能降低交接与集成成本。

## 验证与返工

把第 7 篇的验证循环与本次完成条件对应起来。
用单元测试验证筛选参数的解析，用契约测试核对 API 输入和响应，用浏览器操作验证后退与刷新。
验证的重点是确认了哪项完成条件。

| 完成条件 | 验证方法示例 |
| --- | --- |
| 反映 q 和 status | 检查请求参数和 URL |
| 缺少 status 时的默认值 | 解析单元测试和 API 测试 |
| 区分空结果与错误 | 测试页面状态并核对实际响应 |
| 后退或刷新后恢复 | 浏览器端到端测试，或记录手动复现过程 |

OpenAI 的迭代修复示例也介绍了如何衔接审查、修改和验证，并把尚未解决的失败作为下一轮修改的输入。
[OpenAI 迭代修复循环](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex)

<br/>

验证失败时，区分已观察到的现象和待验证的假设，再决定下一步。
如果 URL 已更新，输入框却仍显示旧值，就保留复现结果并检查状态更新路径。
如果测试服务器未能启动，先检查运行环境。
如果需求互相冲突，整理需要任务负责人决定的问题。

<Rbox>
不要为了让验证通过而放宽完成条件或移除异常检查。
如果需求变了，先记录变更原因和新标准，再按新标准重新验证。
</Rbox>

### 暂停与交接

如果围绕同一个失败反复修改，却没有新依据，就回到原因分析。
记录当前路径、提交、未提交的改动、通过或失败的检查、未执行的检查和下一步操作。
下一个会话先对照记录与实际代码，再继续工作。
即使换模型或开启新会话，也保留任务编号，便于把重试成本计入同一个任务。

## 审查与完成

审查者除了阅读 AI 的说明，也要查看实际变更和验证依据。
任务负责人判断目标与范围，实施者说明变更和执行结果，审查者核对意图和遗漏。
即便实施者借助 AI，团队仍要明确由谁负责确认任务完成。

<Img src="/261015-120003.webp" width={650} height={433} alt="角色对照表，列出任务负责人、实施者和审查者各自要做的判断以及应保留的依据"/>

在小团队里，同一个人可能承担多个角色。
即便如此，也要按照完成条件和修改文件重新审查，避免只凭实现时的说明就批准。
所用模型可以留在运营记录里，PR 则聚焦审查需要的变更原因和依据。

```text title="PR 설명 예시"
문제: 검색 필터가 URL에 남지 않아 공유·새로고침 시 조건이 사라짐
변경: q·status 직렬화와 URL 변경에 따른 화면 상태 복원
범위: 검색 폼, API 필터 처리, 관련 테스트
검증: 타입 검사, 파싱·계약 테스트, 브라우저 복원 시나리오
미검증: 실행 환경이 없는 브라우저는 별도로 표시
제외: 정렬 규칙과 DB 구조는 변경하지 않음
작업 기록: docs/tasks/search-filter.yaml
```

以上是报告格式示例。
实际 PR 应附上能核对执行命令、结果和对应代码状态的链接或日志。
根据审查意见修改后，重新运行受影响的检查。

<br/>

按团队的定义区分开发完成、合并和部署。
如果像本例一样，把通过验证与审查作为完成标准，报告也应停留在这个阶段。
若任务包括部署，记录现有部署流程及部署后的核查依据。

## 记录与改进

要改进重复任务，除了记录结果，也要记录时间花在哪里。
把第 8 篇介绍的完成率、人工返工、总耗时和总用量关联到任务编号。
使用 API 时记录实际计费标准，使用订阅工具时则记录能够查到的用量和限额。

<br/>

OpenAI 的重复工作自动化案例也介绍了如何整理任务上下文、记录运行结果，以及如何把以往运行的经验用于下一项工作。
[OpenAI 的重复工作流程案例](https://developers.openai.com/blog/automating-repetitive-work-at-openai-with-codex)

如果审查时反复出现对 API 字段的误解，就改进契约文档。
如果经常花时间找同一个位置，就补充入口指引。
如果验证等待时间过长，就查明实际瓶颈，调整顺序以便先运行相关检查。
每次调整一个变量，在相同条件下比较模型、指引或验证方法的效果。

<Bbox>
每周选一个反复发生的问题，试着修改通用规则或任务模板。
在通用指引里留下下次还会用到的简短规则和依据所在的位置，具体失败日志留在各自的任务记录里。
</Bbox>

## 本系列的应用顺序

可以从团队反复遇到的问题入手，选择 12 篇中的相关方法，再按测量结果扩大使用范围。

| 团队反复遇到的问题 | 优先应用的方法 | 相关篇目 |
| --- | --- | --- |
| AI 花太多时间找相关文件 | 最少必要指引和仓库入口 | 第 1–3 篇 |
| 结果偏离请求 | 任务范围、完成条件和契约 | 第 4 篇 |
| 加载了过多文档和工具 | 按需加载 Skill 和 MCP | 第 5 篇 |
| 任务成本和等待时间失衡 | 选择模型和推理强度 | 第 6 篇 |
| 测试通过后仍需返工 | 复现、验证和完成依据 | 第 7 篇 |
| 难以判断改进是否有效 | 按任务记录指标并比较 | 第 8 篇 |
| 重复处理同一输入 | 核对缓存读写和总成本 | 第 9 篇 |
| 切换会话后上下文丢失 | 代码状态和交接记录 | 第 10 篇 |
| 合并并行结果时出问题 | 职责边界、隔离和集成验证 | 第 11 篇 |

可以先统一一份任务说明、仓库中实际使用的验证命令和完成报告格式。
这三项用起来后，就可以在同一套完成标准下比较模型路由或并行方案。

## 结论

团队的 AI 开发流程包括明确目标与变更边界、传递必要信息、审查代码和运行依据。
把任务记录与指标关联起来，才能判断快速生成的代码是否交付了真正完成的功能。

<br/>

贯穿 12 篇的共同方法是**留下下一步判断需要的信息，用实际结果验证**。
从小型重复任务开始应用，观察完成率和人工返工的变化，再按团队情况调整。
