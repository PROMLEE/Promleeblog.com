## 开始之前
“请修复登录错误”对人来说已经够模糊，对 AI 编码代理而言，更像一项范围很广的调查请求。
代理需要查看登录界面、API、会话、环境变量和测试，并猜测各种可能的原因。
结果往往也不理想。
<br/>
**一份好的任务请求，是代理可以实际执行的小型任务契约。**
本文介绍如何在请求中完整说明任务的目标、范围、约束和完成条件。

<Bbox>交给代理的任务，最好以一个可验证的结果为单位。任务契约越小，探索范围越容易控制，失败后也更容易定位原因。</Bbox>

## 任务契约
> 代理写出不符合预期的代码，往往是因为请求里没有定义怎样才算完成。

在任务请求里写明下面六项。
每项不必写得很长，但凡是让代理猜测会带来风险的地方，都要明确说明。

| 项目 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 目标 | 应该产生什么变化？ | 密码重置页面能提示链接已过期。 |
| 范围 | 哪些地方可以修改？ | 只修改 `apps/web` 及相应的 API 处理器。 |
| 约束 | 哪些内容不能动？ | 保留现有重置令牌格式和公开 API。 |
| 完成条件 | 怎样才算完成？ | 过期链接显示提示页面，有效链接仍按原来的方式工作。 |
| 验证 | 用什么方法确认？ | 运行相关单元测试和 `pnpm lint`。 |
| 决策边界 | 何时应该暂停并提问？ | 如果需要修改数据库结构或邮件模板，先询问。 |

OpenAI 的 Codex 指南也建议保持 `AGENTS.md`、Skill 和任务提示词等工作指引的时效性，并指向与任务相关的文档。
[OpenAI Developers 的指引设计原则](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

## 对比两种请求
即使要实现的是同一项功能，请求结构也会影响代理阅读的范围和最终结果。

```text title="vague-request.txt"
로그인 오류를 고쳐 주세요.
```

这条请求没有说明故障现象、允许修改的范围、测试方式或需要保留的既有行为。
代理可能大范围调查，也可能修改最近找到的代码，得到与需求不符的结果。

```md title="agent-task.md"
## 목표
만료된 비밀번호 재설정 링크를 열면 안내 화면을 표시합니다.

## 범위
- apps/web의 재설정 페이지와 apps/api의 토큰 검증 핸들러만 수정합니다.
- 기존 정상 토큰 흐름은 바꾸지 않습니다.

## 완료 조건
- 만료 토큰은 안내 화면을 표시합니다.
- 유효 토큰은 현재 비밀번호 변경 화면을 표시합니다.
- 관련 테스트와 pnpm lint가 통과합니다.

## 판단 경계
- DB 스키마, 토큰 형식, 메일 문구 변경이 필요하면 구현 전에 질문합니다.
```

第二条请求给代理保留了选择实现方式的空间。
同时明确了**哪些事情可以自行决定，以及哪些现有行为必须保留**。

<Ybox>把实现方式定得太死，可能会挡住更简单、更安全的方案。可以先写清结果和边界，例如要求“向用户明确展示链接已过期”，把是否需要增加三个 React 状态留给实现时判断。</Ybox>

## 范围和边界
任务请求里，最重要的一句话往往是哪些内容不能修改。
因为代理在解决问题时，可能顺手改动更大范围的代码。

### 变更边界
把下面三项分别写清楚，可以避免工作范围无谓扩大。

- **允许修改的范围**  
  指定可以改动的目录、文件和 API。
- **必须保留的契约**  
  列出需要保持兼容的公开 API、数据格式和用户流程。
- **需要询问的条件**  
  写出数据库结构、支付、权限和部署等需要团队决定的事项。

<Rbox>默认只授予任务所需的修改权限，避免笼统地写“需要时可以重构”。把与请求无直接关系的大规模重构、依赖替换和数据库结构变更拆成独立任务。</Rbox>

任务较大时，可以先建立调查契约。
例如，先要求“整理原因和可选改动，修改前给出计划”，再另行交付实现契约。
把调查和实现分开，有助于在大改动中保留回退余地。

## 完成条件
“已经实现”还需要具体的核对依据。
请写出代理和审查者都能观察到的结果，让双方按同一标准核对。

| 类型 | 模糊说法 | 可核查的说法 |
| --- | --- | --- |
| 页面 | 把错误展示清楚 | 过期链接显示标题、重新申请按钮和帮助链接。 |
| API | 安全地处理 | 无效令牌返回 400，且不泄露用户信息。 |
| 测试 | 请测试 | 添加并运行过期、有效和缺失令牌的测试。 |
| 性能 | 不要变慢 | 沿用现有令牌验证流程，不新增网络请求。 |

## 请求模板
可以用下面的模板起草 Issue、PR 说明，或开启与代理的对话。

```md title="docs/agent-tasks/password-reset-expiry.md"
 # 목표
<사용자에게 달라져야 하는 결과>

 # 범위
- <수정 가능한 경로>
- <보존해야 하는 기존 흐름>

 # 완료 조건
- <관찰 가능한 결과 1>
- <관찰 가능한 결과 2>
- <실행할 검증 명령>

 # 판단 경계
- <질문이 필요한 변경>
- <명시적으로 제외한 작업>

 # 전달 결과
- 변경한 파일과 이유를 요약합니다.
- 실행한 검증 명령과 결과를 기록합니다.
- 남은 위험 또는 결정이 있으면 적습니다.
```

写请求可能多花一点时间。如果能减少代理重复探索和审查往返，总耗时反而会缩短。
对于团队中反复出现的改动，把这个格式做成 Issue 模板，更容易共享质量标准。

## 团队检查清单
✓ 目标写成了用户或系统能够观察到的变化。
✓ 区分了允许修改的路径和需要保留的契约。
✓ 完成条件包含测试或验证命令。
✓ 单独写明哪些事项需要提问。
✓ 超出任务范围的重构已拆成独立契约。

## 结论
交给 AI 编码代理的请求可以保持简洁。
一份**清楚的任务契约**应覆盖目标、范围、约束、完成条件、验证方式和决策边界。
<br/>
减少需要猜测的地方，增加可以核对的依据，有助于提高交付质量，也能加快团队审查。
