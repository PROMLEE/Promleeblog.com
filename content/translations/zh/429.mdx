## 开始之前
交给 AI 代理一项功能后，如果它第一步就把整个 `docs/` 读了一遍，可以先检查仓库结构。
如果没有说明*哪类任务需要读哪份文档*，代理就只能扩大搜索范围。
小改动也读取大量背景，会增加成本与等待时间，还可能因为采用过时文档而做出错误决定。
<Bbox>设想自己是个刚入职的员工，却接手了一个连 README 都没有的项目。光想想就有点来气……</Bbox>
本文将把根目录指引、任务文档和子目录规则连接起来。

<Img src="/260927-030002.webp" width={500} alt="AI 代理仓库结构，从根目录指引通往任务文档与子目录规则"/>

## 上下文路径
> 仓库结构应帮助代理缩小各项任务的阅读范围。

Codex 按顺序收集从仓库根目录到当前工作路径的 `AGENTS.md`，较深路径的指引会在后面应用。
[OpenAI 文档：AGENTS.md 的加载方式](https://developers.openai.com/api/docs/guides/latest-model?gallery=open&galleryItem=trivia-quiz-game&model=gpt-5.3-codex)
因此，根目录的 `AGENTS.md` 适合只放适用于各项任务的简短约定。
测试命令、包管理器、修改时需要遵守的兼容边界，都是*不能靠猜测来决定的事实*。

```md title="AGENTS.md"
 # 프로젝트 공통 규칙

- 패키지 명령은 pnpm을 사용합니다.
- 변경 후 관련 테스트와 pnpm lint를 실행합니다.
- 공개 API와 데이터베이스 스키마 변경은 호환성 영향을 설명합니다.

 # 작업별 문서

- 인증 변경은 docs/auth.md를 읽습니다.
- 배포 변경은 docs/deploy.md를 읽습니다.
- 결제 변경은 docs/billing.md와 apps/api/AGENTS.md를 읽습니다.
```

如果在这里写入完整架构与历史故障记录，连小改动也会承担不相关的上下文开销。
OpenAI 也建议按任务条件指向相关文档，避免在每项任务前强制加载整组文件。
[OpenAI Developers 的上下文指引设计](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

## 拆分文档
按**什么情况下需要阅读**来拆分文档。
以下结构可供同时运营 Next.js 服务和 API 的团队使用。

```text title="repository-layout.txt"
.
├── AGENTS.md                # 모든 작업에 적용되는 최소 규칙
├── README.md                # 사람이 빠르게 이해할 프로젝트 소개
├── docs/
│   ├── architecture.md      # 서비스 경계가 필요한 변경
│   ├── auth.md              # 인증·권한 변경
│   ├── deploy.md            # 배포와 운영 변경
│   └── decisions/           # 중요한 설계 결정 기록
├── apps/
│   ├── web/
│   │   └── AGENTS.md        # 프런트엔드 지역 규칙
│   └── api/
│       └── AGENTS.md        # API와 데이터 접근 지역 규칙
└── packages/
    └── ui/
        └── AGENTS.md        # 디자인 시스템 변경 규칙
```

`README.md` 帮助初次接触项目的人了解项目，`AGENTS.md` 则帮助代理安全地开始工作。
如果合并成一份文档，供人了解的背景会与代理需要立即执行的规则混在一起。

<Ybox>如果只把文档分开存放，没有从根目录指引链接过去，代理可能不知道 docs/auth.md 存在。把任务专用文档的文件名与适用条件一起写下来。</Ybox>

### 子目录规则
子目录中的 `AGENTS.md` 只需记录*该目录特有的差异*，例如本地命令、测试范围与禁止使用的依赖。
根目录规则可以直接继承。

```md title="apps/api/AGENTS.md"
 # API 변경 규칙

- API 계약 변경 전 docs/architecture.md를 확인합니다.
- 데이터 모델 변경은 prisma migration을 함께 만듭니다.
- apps/api/의 테스트는 pnpm --filter api test로 실행합니다.
```

根目录提供通用原则，API 目录再补充 API 规则，两份文档各有用途。
这种结构尤其适合 monorepo。
前端任务无需阅读支付后端流程，数据模型指引则只在修改 API 时加入。

## 探索成本
代理如何在仓库里查找文档，也可以通过仓库结构来引导。
区分*默认读取的范围*与*需要时才读取的范围*，同时保留按需查找文档的能力。

| 信息 | 默认加载 | 按需加载 |
| --- | --- | --- |
| 运行与验证命令 | `AGENTS.md` | — |
| 服务边界 | 简短链接 | `docs/architecture.md` |
| 认证策略 | 简短链接 | `docs/auth.md` |
| 变更记录 | — | `docs/decisions/` |
| 特定应用的规则 | — | 对应路径的 `AGENTS.md` |

在任务请求里直接提供路径，也能让范围更明确。
例如，“修改 `apps/web` 的登录页面，并查看 `docs/auth.md` 中的会话规则”比只说“修改登录页面”更容易确定从哪里查起。

## 核对循环
调整结构后，要确认代理实际上只读了所需的路径。
用下面这样的小任务核对，能更快发现文档的遗漏与重复。

```text title="repository-context-check.txt"
1. 웹 화면 수정, API 수정, 배포 변경 작업을 각각 하나씩 고릅니다.
2. 각 작업에서 필요한 문서와 AGENTS.md를 목록으로 적습니다.
3. 공통 규칙이 중복되지 않았는지 확인합니다.
4. 작업과 무관한 문서가 기본 지침에 강제되지 않았는지 확인합니다.
5. 문서가 가리키는 테스트 명령을 실제로 실행합니다.
```

通过 `git ls-files '*AGENTS.md' 'docs/*.md'`，可以快速查看已跟踪的指引与主要文档。
新成员修改文档后也可以重复核对，避免指引随着时间变得臃肿。

## 团队检查清单
✓ 根目录 `AGENTS.md` 只保留通用命令和安全边界。
✓ 把任务专用细节拆到 `docs/`，并链接到适用条件。
✓ 子目录 `AGENTS.md` 只补充对应路径的局部规则。
✓ 区分 `README.md` 和代理指引的读者。
✓ 用代表性任务核对实际加载路径与测试命令。

## 结论
适合 AI 代理的仓库结构，应让代理快速定位任务所需的信息。
通用规则保持简短，详细文档按任务条件查阅。
路径明确后，代理可以少读一些文件，同时更准确地工作，团队也能减少文档重复与上下文开销。
