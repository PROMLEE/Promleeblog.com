## 开始之前

我把搜索页面交给一个 AI，把搜索 API 交给另一个 AI。
两边都说测试通过，可合起来一看，页面读取的是 `items`，API 返回的却是 `results`。
由于两边没有修改同一个文件，Git 也没有报告冲突。
但功能无法运行。

<br/>

开几个会话只是并行工作的起点。
还需要**先确定共享契约与职责范围，隔离各自的修改，再验证集成结果**。
本文以搜索功能为例，说明如何拆分任务、管理 Git worktree，以及集成各项成果。

## 拆分任务

> 可以同时开展的工作，应该能够在无需等待对方未完成成果的情况下独立做出判断。

要并行实现搜索页面和 API，需先确定输入参数和响应结构。
如果响应格式还没选定，最好先完成 API 设计再拆分任务。
若两个任务各自猜测尚未协商的边界，协调时间可能比实现时间还长。

| 任务关系 | 建议流程 | 原因 |
| --- | --- | --- |
| 契约已确定的页面和 API 实现 | 并行开展 | 可以按相同的输入和输出工作 |
| 设计响应结构与实现使用该结构的页面 | 先设计，再实现 | 前一步的决定是后一步的输入 |
| 不同模块的独立缺陷修复 | 考虑并行 | 需确认共享状态和测试环境 |
| 对同一个核心函数做不同修改 | 依次完成或由一人统一处理 | 变更意图和回归条件重叠 |

把契约写进代码或文档，比只说“前后端分开做”更明确。
以下是页面和 API 共同遵循的类型示例。

```ts title="src/contracts/search.ts"
export type SearchItem = {
  id: string;
  title: string;
};

export type SearchResponse = {
  items: SearchItem[];
  nextCursor: string | null;
};

export type SearchError = {
  code: "INVALID_QUERY" | "INTERNAL_ERROR";
  message: string;
};
```

除了类型，也要确定请求参数、空结果和 HTTP 状态码。
即使类型一致，页面发送 `q`、API 却接收 `query`，两边也无法衔接。
还要验证运行时响应是否遵循契约。

<Img src="/261015-110002.webp" width={650} height={433} alt="先确定输入输出契约和基准提交，再并行实现页面与 API，随后逐项集成并进行回归验证的任务拆分流程"/>

<Bbox>
如果共享契约需要变更，约定由相关任务向集成负责人提交变更方案。
把必要的变更纳入基准代码，受影响的任务核对新契约后再继续。
</Bbox>

## 职责范围

每项任务除了目标和完成条件，也要指定可以修改的文件范围。
没有分配给某个任务的公共文件由集成负责人管理。

| 职责 | 修改范围示例 | 共享边界 |
| --- | --- | --- |
| 页面任务 | `src/features/search/`、页面测试 | 使用 API 契约 |
| API 任务 | 搜索路由和服务、API 测试 | 按相同契约返回响应 |
| 集成负责人 | 共享契约、包配置、整体连接 | 决定变更顺序并负责最终验证 |

`package.json`、锁文件和公共测试配置容易出现改动重叠。
如需添加依赖，可以记录需求，再由一位负责人统一处理。
只要避免多个会话同时改同一份配置，就能缩小协调范围。

<br/>

读取范围可以更宽。
例如，负责 API 的会话阅读页面如何调用接口是有益的。
交代任务时，**把可读取的范围和负责修改的范围分开说明**。

```text title="화면 작업 요청 예시"
목표: 검색어 입력, 빈 결과, 오류 상태 표시
계약: src/contracts/search.ts와 합의된 q 파라미터 사용
수정: src/features/search/와 관련 화면 테스트
공유 파일: 계약·패키지 설정 변경은 제안만 전달
검증: 화면 상태 테스트와 요청 파라미터 확인
완료 보고: 결과 커밋, 변경 파일, 검증 결과, 미검증 범위
```

## 使用 worktree 隔离

多个会话在同一个检出目录修改时，一个会话可能读到或覆盖另一个会话的变更。
Git worktree 可以为同一仓库关联多个工作目录，让不同分支分别使用各自的文件和索引。
[Git worktree 文档](https://git-scm.com/docs/git-worktree)

以下是通过终端手动管理的例子。
假定共享契约已经提交，而且分支名称和目标路径尚未使用。
先检查当前仓库的变更状态。

```bash title="동일 기준에서 작업 공간 생성"
git status --short
task_base=$(git rev-parse HEAD)
git worktree add -b ai/search-ui ../shop-search-ui "$task_base"
git worktree add -b ai/search-api ../shop-search-api "$task_base"
git worktree list
```

`task_base` 是两项任务共同的起始提交。
当前目录中未提交的修改不在该提交里，因此不会自动传到新 worktree。
如果必要的契约变更还没提交，应先按团队约定准备好基准状态。

<br/>

Codex 应用提供基于 worktree 的隔离工作流程。
由应用管理的 worktree 通过应用的创建、切换和清理功能管理。上面的手动命令适用于独立操作的 CLI 流程。
[Codex worktree 指南](https://learn.chatgpt.com/docs/environments/git-worktrees)

Claude Code 也介绍了如何通过 `--worktree` 启动隔离的并行会话。
如果 worktree 已经手动建好，可以分别在各目录里启动会话。
[Claude Code worktree 工作流程](https://code.claude.com/docs/en/common-workflows)

### 共享资源

目录分开以后，开发服务器端口和外部数据库仍可能共享。
例如，两项任务用同一端口启动服务器就会冲突，修改同一批测试数据也可能影响彼此的结果。
按项目现有的隔离方式，划分端口、测试账号和数据范围。

<Img src="/261015-110003.webp" width={650} height={433} alt="worktree 隔离文件和分支，端口、数据库及本地配置则需要另外确认"/>

Node 项目的依赖和 Git 未跟踪的环境文件，也可能需要分别准备。
一个 worktree 能运行服务器，并不代表另一个也已经就绪。
例如，页面服务器使用 3101，验证 API 的服务器使用 3102，并同步调整内部 API 地址和测试的基准 URL。

<Ybox>
即便拆开了测试数据库，也要确认迁移目标和外部 API 账号是否仍然共用。
worktree 隔离的是文件变更，外部服务的权限和数据需要单独隔离。
</Ybox>

## 集成结果

并行任务完成后，参照第 10 篇的交接记录收集成果提交、基准提交、变更范围和验证依据。
集成负责人先核对共享契约，再逐项纳入成果。
采用能辨认各项变更的方式引入成果，避免把未完成文件复制到一起。

<br/>

下面的示例假设每项任务的结果都整理成了一个提交。
此前记录的 `task_base` 和两个任务分支依然存在，两个任务均已完成，无需再修改。

```bash title="별도 작업 공간에서 순차 통합"
git worktree add -b ai/search-integration ../shop-search-integration "$task_base"
task_ui_commit=$(git rev-parse ai/search-ui)
task_api_commit=$(git rev-parse ai/search-api)
git -C ../shop-search-integration cherry-pick "$task_ui_commit"
git -C ../shop-search-integration cherry-pick "$task_api_commit"
```

`cherry-pick` 会把指定提交的改动应用到当前分支。
如果成果分为多个提交，只引入最后一个可能会漏掉之前的修改。应核对提交列表和依赖顺序，或采用团队约定的合并方式。
[Git cherry-pick 文档](https://git-scm.com/docs/git-cherry-pick)

<br/>

第一次应用因冲突暂停时，先解决当前冲突。
确认双方意图和契约，解决后用 `git cherry-pick --continue` 继续。
如果需要取消，先确认 `git cherry-pick --abort` 的恢复范围，再中止本次应用。

### 冲突类型

即使 Git 没有报告冲突，也可能出现语义冲突。
例如，开头的 `items` 和 `results` 不一致，或页面将空数组视为正常结果，API 却以错误返回。

| 冲突 | 示例 | 核查方式 |
| --- | --- | --- |
| 文件冲突 | 修改同一函数的同一行 | 审查 diff 和变更意图 |
| 契约冲突 | 响应字段或错误码不一致 | 契约检查和 API 消费方测试 |
| 环境冲突 | 共用端口或测试数据 | 确认运行地址和数据隔离 |
| 验证遗漏 | 只通过了各自的测试 | 在集成状态下运行用户流程 |

<Rbox>
不要为消除冲突而整段选用一方改动，或删除测试。
按双方任务的完成条件保留必要行为，并在集成结果中重新验证。
</Rbox>

## 集成验证

任务 A 的测试只为 A 的代码状态提供依据，任务 B 的测试也只对应 B 的代码状态。
合并后的代码需要重新取得验证依据。
在集成分支核对契约和实际连接。

- 确认页面发送约定的请求参数。
- 确认页面能处理 API 的成功、空结果和错误响应。
- 运行相关类型检查、单元测试和集成测试。
- 在真实浏览器中检查从输入搜索词到展示结果的流程。
- 如果集成时改了代码，重新运行受影响的检查。

如果先用模拟响应实现了页面，最后的连接验证应使用真实的测试 API。
也要确认模拟响应与真实响应遵循同一契约。
本例用于说明工作步骤，未在生产项目运行这些命令。

### 清理条件

成果已保留，运行中的会话和服务器也不再使用 worktree 时，才开始清理。
对于手动创建的 worktree，先用 `git worktree list` 核实路径，检查变更和需要保留的本地文件，再运行 `git worktree remove`。
对于应用管理的 worktree，使用应用提供的清理功能。

<Bbox>
Git 忽略的环境文件和测试产物可能不在成果提交里。
清理前确认哪些文件需要保留，未完成的任务应另行处理。
</Bbox>

## 时间与成本

如果任务 A 和 B 相互独立，并行执行阶段通常由耗时较长的任务决定结束时间。
不过总耗时还包括任务拆分准备、各任务的探索、成果审查、冲突解决和集成验证。
把一个小改动拆成多项任务，可能会产生更多额外耗时。

<br/>

计算 token 成本时，应汇总所有任务以及集成负责人的用量。
各并行会话可能都要读取仓库指引和相关代码，所以缩短耗时不一定也能减少 token。
参照第 8 篇，一起比较完成率、人工返工、总耗时和总用量。

第一次应用并行工作时，可以从两项契约稳定、修改范围不同的任务开始。
记录集成环节多花了多少时间，再据此调整团队选择并行任务的标准。

## 结论

开展 AI 并行工作时，可以先确定共享契约，再划分职责、隔离工作空间，最后依次集成。
即使用了 worktree，也要单独检查端口、数据库等共享资源，以及 Git 无法提示的语义冲突。

<br/>

可以把**确定契约 → 划分职责 → 隔离工作空间 → 逐项集成 → 验证连接**作为基本流程。
最后的第 12 篇会把这个过程与前面的请求设计、模型选择、验证和测量串起来，形成团队开发流程。
