## 开始之前

缩短指引文件并换用更轻量的模型后，token 用量下降了。
可是审查 PR 时更常发现遗漏的异常处理，人工修复耗时也增加了。
如果只看 token 图表，会以为效率提高了，实际开发却可能花了更长时间。

<br/>

系列前面介绍了上下文、任务请求、模型选择和代码验证。
还需要**记录工作方式的改变对完成率、耗时和成本的影响**。
本文介绍按任务记录和对比指标的方法，无需先搭建大型仪表盘。

## 衡量单位

> 以有明确完成条件的一项任务为记录单位，比按一次对话或一次提交更合适。

“修复搜索筛选在后退时无法恢复的问题”是一项任务。
即使为此追加了三次请求并切换模型，也归入同一项任务。
如果按调用单独统计成功与否，多次失败后才解决的任务就难以反映实际成本。

<br/>

先确定起点与终点。
本文示例从向 AI 发出任务请求开始，到通过约定的验证和审查为止。
尝试过但未完成的任务标为失败或中止。
如果团队把部署也纳入工作范围，就把部署核验加入结束条件，并对各组配置统一采用。

<Bbox>
可以先记录任务编号和完成条件。
“后退后 URL 和输入值同时恢复”比“改进搜索”更容易核实结果。
如果任务跨多个会话，沿用同一任务编号。
</Bbox>

## 核心指标

起步时同时观察四项指标就够了。
优化其中一项前，先检查其他指标是否恶化。

| 指标 | 计算或记录口径 | 注意事项 |
| --- | --- | --- |
| 完成率 | 已完成任务数 ÷ 已结束评估的全部任务数 | 分母包含失败和中止 |
| 返工时间 | 人工修复和准备追加请求的时间 | 与常规审查时间分开 |
| 总耗时 | 从首次请求到完成验证和审查 | 区分 AI 运行和等待原因 |
| 总用量与成本 | 纳入同一任务的重试与模型升级 | 区分 API 费用和订阅限额 |

进行中的任务单独统计，暂不纳入最终完成率的分母。
提前确定运营数据的评估截止时间，避免晚完成的任务不断改写上周的数据。

<Img src="/261012-080002.webp" width={650} height={433} alt="同时观察 AI 编码完成率、人工返工、总耗时和总用量的指标图"/>

OpenAI 官方文档也建议在代表性任务中比较成功情况、延迟、token 用量和每个成功任务的成本。
[OpenAI 部署检查清单](https://developers.openai.com/api/docs/guides/deployment-checklist)

### 区分返工

把常规审查与修正 AI 结果的返工分开。
阅读和审查代码的 10 分钟，与说明遗漏条件并重新提出请求的 20 分钟，是两类成本。
分别记录手动修改和准备追加请求的时间，就能看出增加的是哪种负担。

<br/>

AI 在验证过程中自行修正的迭代，不计入人工返工时间。
这部分成本计入总耗时和用量。
另外标注有无人工介入修正，这样即使最终完成率较高，也能找出需要大量人工协助的任务。

## 任务记录

起步时，每项任务写一条备注或一行 CSV 就够了。
优先添加实际决策会用到的字段。
下面是团队可采用的 TypeScript 记录示例，格式由团队自行定义。

```ts title="tools/task-metrics.ts"
type TaskRecord = {
  taskId: string;
  taskType: "small-edit" | "feature" | "debug";
  startCommit: string;
  requestVersion: string;
  modelPath: string[];
  outcome: "accepted" | "failed" | "blocked";
  elapsedSeconds: number;
  humanReviewMinutes: number;
  humanReworkMinutes: number;
  extraRequests: number;
  apiCostUsd: number | null;
};
```

在 `modelPath` 中按执行顺序记录实际使用的模型和推理设置。
`extraRequests` 指人在首次请求后追加的修改请求次数。
工具调用和测试执行不计入。
订阅环境无法确定 `apiCostUsd` 时，用 `null` 表示，避免把未知费用填为 0 美元。

<br/>

按第 7 篇的完成报告格式另行保存验证命令和失败依据，再通过任务编号关联。
汇总表里保留简短的失败原因即可。
写清“缺少入口信息”“误解响应结构”“测试环境未就绪”等具体原因，便于决定下一步怎么改。

### 收集用量

当前 Claude Code 官方文档建议在 `/usage` 的 Session 区域查看会话的 token 用量和预估费用。
订阅用户可以在同一界面查看用量限额。按 API 单价算出的会话费用估算与订阅账单属于不同口径。
核实实际 API 账单时，使用 Claude Console 的用量数据。
[Claude Code 费用管理](https://code.claude.com/docs/en/costs)

如果一个会话完成多项任务，不能把整段会话的用量原样复制到每项任务。
先确认能否按任务边界计算用量差值。无法区分时，注明数据只能按会话汇总。
每次请求后把累计统计直接相加，可能重复计算同一批 token，因此还应分清采集的是累计值还是单次调用值。

<Ybox>
输入、输出、缓存和推理 token 之间的关系，取决于提供方返回的用量结构。
如果明细已经包含在合计中，就无需再加一次。
价格还要按实际适用的模型、缓存和处理费率计算。
</Ybox>

## 每项完成任务的成本

第 6 篇讨论了单项任务升级到更强模型时的成本。
对比多项任务时，汇总包含失败尝试在内的费用，再除以完成任务数。
否则漏算未完成的任务，容易让某个配置显得比实际更便宜。

```ts title="tools/task-metrics.ts"
function summarize(tasks: TaskRecord[]) {
  const accepted = tasks.filter((task) => task.outcome === "accepted");
  const costsKnown = tasks.every((task) => task.apiCostUsd !== null);
  const totalCost = costsKnown
    ? tasks.reduce((sum, task) => sum + task.apiCostUsd!, 0)
    : null;

  return {
    evaluated: tasks.length,
    accepted: accepted.length,
    completionRate: tasks.length ? accepted.length / tasks.length : null,
    humanReworkMinutes: tasks.reduce(
      (sum, task) => sum + task.humanReworkMinutes, 0,
    ),
    costPerAcceptedTask:
      accepted.length && totalCost !== null
        ? totalCost / accepted.length
        : null,
  };
}
```

本例假定输入的任务都已结束评估。
各任务的成本包括重试和模型升级。如果任意一项成本未知，每项完成任务的成本也标为未知。
完成数为 0 时，同样不能将成本显示为 0。
每个 `taskId` 只传入一条记录，以免调用次数较多的任务被重复统计。

### 对比示例

下面用虚构数据演示计算，未采用实测数据或模型性能资料。
假设配置 A 和 B 分别执行相同的 10 项任务。

| 项目 | 配置 A | 配置 B |
| --- | --- | --- |
| 已完成任务 | 9 项 | 7 项 |
| 失败或中止的任务 | 1 项 | 3 项 |
| 完成率 | 90% | 70% |
| API 总成本 | 12 美元 | 10 美元 |
| 每项完成任务的 API 成本 | 约 1.33 美元 | 约 1.43 美元 |
| 人工返工时间 | 45 分钟 | 80 分钟 |

B 的 API 总成本更低，但每项完成任务的成本更高，人工返工也更久。
分别查看人工时间与 API 成本，才能看清这个差异。
如果团队没有内部人工成本标准，可以分别保留两个指标，无需用任意时薪折算成一个金额。

## 对比条件

直接比较不同任务得出的数字，会把配置效果和任务难度混在一起。
使用相同的起始代码、请求、验证标准和运行环境，一次只改一个变量。
如果在已经包含前一次改动的代码上运行第二种配置，后者就继承了前者的结果。

<Img src="/261012-080003.webp" width={650} height={433} alt="固定起始代码、请求、验证标准和运行环境，一次改变一个变量，对比完成率、返工、耗时和成本"/>

例如，要观察缩短 `AGENTS.md` 的效果，就保持模型和推理等级不变。
要对比模型路由，就固定指引和任务请求。
如果同时改动任务请求、模型和验证方式，就很难判断是哪一项影响了结果。

<br/>

OpenAI 关于 Skill 评估的文章也介绍了先定义成功标准，再用运行结果和检查标准判断改进与退步的方法。
[OpenAI 的 Skill 评估方法](https://developers.openai.com/blog/eval-skills)

### 按任务类型汇总

分开看简单修复、常规功能实现和复杂调试。
如果一周主要是简单任务，另一周主要是难题，直接对比两周的整体完成率无法判断模型是否变好。
按任务类型同时列出任务数和完成率。

<br/>

除了平均耗时，也看已完成任务的中位数和耗时较长的个例。
中位数是排序后位于中间的数值，比平均值更少受到少数耗时很长的任务影响。
由于只衡量已完成任务，还需另行记录失败和中止的数量以及这些任务消耗的时间。

<Rbox>
请保留难度较高的任务和原有验证标准。
如果输入和成功标准变了，即使指标名称相同，也无法与之前的结果直接比较。
</Rbox>

## 改进顺序

收集指标是为了选出下一步行动。
查看数值恶化的任务记录和失败原因，再选择一项改进。

| 观察结果 | 优先核查 | 可采取的改进 |
| --- | --- | --- |
| 输入用量增加 | 反复读取的指引、文档与工具输出 | 补充入口说明、按条件引用、限制返回范围 |
| 完成率下降 | 失败能否复现，是否漏写完成条件 | 写清请求并提供验证手段 |
| 人工返工增加 | 需求或接口是否被误解 | 明确输入输出示例和改动边界 |
| 等待时间增长 | 测试、工具与环境的瓶颈 | 优先运行相关检查，完善运行环境 |
| 升级与重试增加 | 初始模型选择和信息是否充足 | 调整各类任务的选型标准和交接摘要 |

即便用量增加，只要返工减少、完成率提高，也可能是可接受的变化。
如果成本下降的同时验证遗漏增多，保留该设置的理由就变弱了。
单个指标不足以确认原因，应查看具体任务的依据。

### 如何开始

选一种反复出现的任务，记录当前配置的基准值。
从指引长度、模型和推理强度中选一个变量调整，用相同的案例对比。
小样本结果可用来判断方向，确认新任务也保持同样趋势后，再更新默认配置。

<Bbox>
每周选一项改进。
比起笼统地说“节省 token”，可以定一个可观察的目标，例如“在相同的搜索功能任务上维持完成率，同时减少重复读取文档”。
</Bbox>

## 结论

AI 编码指标应体现有多少任务通过了验证与审查并真正完成。
按任务定义完成条件，把失败、中止和重试一起记录，才能判断用量下降是否转化为实际效率提升。

<br/>

本系列介绍的上下文整理、最少必要指引、仓库导航、任务请求、Skill 与 MCP 加载、模型路由和代码验证，可以逐项调整。
按**记录基准值 → 改变一个变量 → 在同样条件下对比 → 核查各任务的原因**的顺序，找到适合团队的方法。
