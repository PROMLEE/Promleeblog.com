## はじめに

AIに検索フィルターを直してもらうと、「型チェックとテストはすべて通りました」と返ってきました。
ところがブラウザーでフィルターを2回変更してから「戻る」を押すと、URLは前の値に戻っても入力欄には新しい値が残ります。
コードのコンパイルに成功し、一部のテストが通っても、ユーザーが期待する挙動まで確認できたとは限りません。

<br/>

こうした手戻りを減らすには、**期待する挙動を明確にし、実行結果を次の修正に生かす検証ループ**が必要です。
今回は検索フィルターを例に、不具合の再現、小さな修正、再検証、完了の判断をつなげます。
ClaudeとCodexに共通して使える作業依頼と完了報告のテンプレートも紹介します。

## 検証基準

> 検証コマンドの成功と、依頼した機能が動くことは、個別に確認します。

「検索フィルターをURLと同期して」という依頼には複数の解釈があります。
初期値を読むだけでよいのか、再読み込みや「戻る」にも対応するのか、検索語が空ならどう表現するのかが曖昧です。
実装前に次のような観察可能な基準をAIに伝えると、修正と検証の方向がそろいます。

```text title="검색 필터 완료 조건"
입력: 검색어 A로 검색한 뒤 B로 다시 검색
기대: URL의 q와 검색 입력값이 B를 표시
추가 동작: 브라우저 뒤로 가기
기대: URL의 q와 검색 입력값이 모두 A로 복원
새로고침: 복원된 A가 그대로 유지
제외 범위: 검색 API와 정렬 규칙은 변경하지 않음
```

ここでは実装方法を指定していません。
`useEffect` を追加するか、状態を管理する場所を変えるかは、実際のコードを見て決めます。
基準を挙動で表せば、実装を変えても同じ検証を使えます。

Claude Codeの公式ドキュメントでは、テスト、スクリーンショット、期待する出力など、結果を自分で確認できる手段を与えることを推奨しています。
[Claude Codeの検証のベストプラクティス](https://code.claude.com/docs/en/best-practices)

<Bbox>
バグ修正では、正しい結果に加え、現在失敗する入力と再現手順も伝えてください。
「戻ると状態がずれる」より「A → B → 戻るの順に操作すると、URLはA、入力欄はBになる」と書くほうが、修正箇所を絞りやすくなります。
</Bbox>

## 不具合の再現

まず、修正前に不具合が実際に再現するかを確認します。
再現できないまま直すと、修正後に画面が正常に見えても、元の問題が解決したか判断しづらくなります。
不具合が起きたコードのバージョン、実行コマンド、入力、期待した結果、観測した結果を短く記録します。

<br/>

自動化できるなら、回帰テストにします。
回帰テストは、今回修正した問題が後の変更で再発しないかを確認するテストです。
検索フィルターの例はブラウザーの履歴を扱うため、関数のテストだけでは十分に確認できません。

```ts title="tests/search-history.spec.ts" showLineNumbers
import { test, expect } from "@playwright/test";

test("뒤로 가기 뒤 검색어가 URL과 함께 복원된다", async ({ page }) => {
  await page.goto("/search");
  const input = page.getByRole("textbox", { name: "검색어" });
  const submit = page.getByRole("button", { name: "검색", exact: true });

  await input.fill("alpha");
  await submit.click();
  await expect(page).toHaveURL(/\?q=alpha$/);

  await input.fill("beta");
  await submit.click();
  await expect(page).toHaveURL(/\?q=beta$/);

  await page.goBack();
  await expect(page).toHaveURL(/\?q=alpha$/);
  await expect(input).toHaveValue("alpha");

  await page.reload();
  await expect(input).toHaveValue("alpha");
});
```

この例は、`/search` が `q` だけを含むURLを作り、入力欄とボタンに例のアクセシブルネームが付いた画面を前提としています。
実際のリポジトリに合わせて、パス、クエリの構造、要素名を調整します。
クエリパラメーターが複数ある場合は、URL文字列の末尾を比較する代わりに、`URL.searchParams` で `q` を検証します。

Playwrightの `toHaveURL` や `toHaveValue` などのウェブアサーションは、期待条件を満たすまで再試行します。
固定時間だけ無条件に待つ代わりに、実際のURLと入力値を待機条件にできます。
[Playwrightのアサーションドキュメント](https://playwright.dev/docs/test-assertions)

<Ybox>
修正前にテストが失敗したら、その理由も確認します。
入力欄が見つからずに失敗した場合、フィルター復元の不具合は再現できていません。
意図した箇所で「alphaを期待したがbetaが残った」という失敗が出るか確認します。
</Ybox>

## 修正と再検証

再現手順を固めたら、原因の仮説を一つ選び、関連するコードだけを修正します。
例えば、初回のレンダリングでだけURLの値を読む構成なら、「戻る」でクエリが変わったときに入力状態が更新されるかを確認します。
検索APIや並べ替えルールも同時に変えると、どの変更で問題が解決したか追いにくくなります。

<Img src="/261012-070002.webp" width={650} height={433} alt="不具合の再現、小さな修正、再検証、完了判断をつなぎ、失敗したら修正に戻るAIコード検証ループ"/>

修正後は同じ入力と同じアサーションで再実行します。
今回の問題を検出するテストが通ったら、関連する既存の挙動も確認します。
検索語の直接入力、空の値の扱い、再読み込み、「戻る」など、変更の影響を受ける経路を選びます。

<br/>

OpenAIのCodexの例でも、レビュー、修正、検証をつなぎ、残った失敗を次の修正への入力にする反復構造を説明しています。
[OpenAIの反復修正ループの例](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex)

### 検証の順序

最初からE2Eテスト全体とビルドを繰り返すより、変更に合う速い検査から始め、必要に応じて範囲を広げます。
ただし、不具合を直接再現するテストは早い段階で含めます。
型チェックが速くても、ブラウザー上の不具合の再現は後回しにしません。

| 検証 | 確認すること | 別途確認すること |
| --- | --- | --- |
| 型チェック・Lint | 型の契約、静的ルール違反 | ユーザーの操作、実行時のデータ |
| 単体テスト | 関数やコンポーネントの入出力 | 実際のAPIやDBとの接続 |
| 統合テスト | モジュール、API、データ層の接続 | ブラウザーでの実際の移動と画面状態 |
| ブラウザー検証 | クリック、再読み込み、「戻る」などの操作 | 異なる権限、例外条件、本番環境 |
| ビルド | デプロイ用の成果物を生成する工程 | デプロイ後のサービスの挙動 |

<Img src="/261012-070003.webp" width={650} height={433} alt="型チェック、単体テスト、統合テスト、ブラウザー検証で確認できる対象と、別途確認すべき範囲を比較した図"/>

例のリポジトリに `typecheck`、`test`、`build` のスクリプトとPlaywrightが設定されていれば、次のように検査できます。
現在のプロジェクトの `package.json` とテスト設定を調べ、実際のコマンドに置き換えます。

```bash title="변경 범위별 검증 명령"
npm run typecheck
npm run test -- tests/search-state.test.ts
npx playwright test tests/search-history.spec.ts
npm run build
```

文言を変えるだけなら、毎回すべてのコマンドを実行する必要はありません。
依存関係やビルド設定を変えたらビルドを、APIレスポンスを変えたらAPI利用側のテストを追加するなど、影響に合わせて選びます。
権限の変更では、通常のユーザーに加え、アクセスを許可してはいけないユーザーの結果も確認します。

## 失敗の伝え方

AIに「テストが失敗した。直して」とだけ伝えると、同じ仮説に沿った修正が繰り返されることがあります。
ログ全体を貼る前に、失敗したコマンド、テスト名、期待値と実測値、関連ログの場所を整理します。
元のログは、必要なときに読み直せるように保存します。

```text title="검증 실패 전달"
명령: npx playwright test tests/search-history.spec.ts
실패: 뒤로 가기 뒤 검색어가 URL과 함께 복원된다
기대: 입력값 alpha
관찰: URL은 q=alpha, 입력값은 beta
통과: 첫 검색, 두 번째 검색, URL의 뒤로 가기
변경: SearchForm의 초기값 처리
다음 확인: URL 변경을 입력 상태가 다시 읽는지
로그: test-results/search-history/error-context.md
```

失敗の要約では、実際に確認した事実と次に検証する仮説を分けます。
「URLは変わった」は観測結果で、「状態の同期が抜けている」は確認が必要な仮説です。
この区別があれば、AIが推測を確定した原因として扱いにくくなります。

### 中止条件

再試行は新しい根拠が得られたときに意味があります。
続行条件と中止条件は、次のように作業依頼に記載できます。

- 再現テストと関連する回帰テストが通ったら、完了報告に進みます。
- 同じ失敗が繰り返され、新しい観測結果が得られなければ、変更を止めて原因分析に戻ります。
- 実行環境がなく確認できない場合は、未検証の項目と再現方法を残します。
- 要件や権限ポリシーを決める必要があれば、判断すべき事項をユーザーに伝えます。

OpenAIの反復修正の例でも、検証の通過、試行回数の上限、改善の停滞、人の確認が必要な場合を終了条件に挙げています。
[OpenAIの反復修正ループの終了条件](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex)

<Rbox>
テストを通すために、テストを削除したり、期待値を現在の誤った結果に合わせたりしないでください。
要件の変更が確認されていなければ、検証基準を保ち、実装を修正します。
</Rbox>

## 完了を裏付ける記録

「すべて正常です」より、検証した範囲が分かる報告のほうが次の作業に役立ちます。
実行したコマンド、確認した挙動、残る制約を分ければ、人が追加で確認する箇所をすぐに判断できます。

```text title="완료 보고 예시"
변경: URL 변경 시 검색 입력값도 동기화
통과: 타입 검사, 검색 상태 단위 테스트
통과: alpha → beta → 뒤로 가기 → 새로고침 E2E
확인: URL과 입력값이 alpha로 복원
미검증: Safari 실행 환경이 없어 해당 브라우저 미확인
제외: 검색 API와 정렬 규칙은 변경하지 않음
```

上の報告は形式の例で、実際のサービスに対してこの記事で検証を実行した結果ではありません。
実作業では、確認していないコマンドやブラウザーを成功の一覧に入れません。

<Bbox>
検証後にコードを修正したら、その変更の影響を受ける検査を再実行します。
以前のバージョンで通った結果を、最終コードの根拠として流用しません。
</Bbox>

### 作業依頼テンプレート

次の依頼文を作業内容に合わせ、ClaudeやCodexに渡せます。
コマンドと完了条件を具体的に書くと、AIがコード作成と検証を一つの作業として扱えます。

```text title="AI 코드 수정 요청"
목표: 검색 필터의 뒤로 가기 복원 오류 수정
재현: alpha로 검색 → beta로 검색 → 뒤로 가기
기대: URL과 입력값이 모두 alpha, 새로고침 뒤에도 유지
범위: 검색 폼 상태와 관련 테스트
검증: 기존 package.json의 타입 검사와 관련 테스트 실행
회귀: 위 재현을 잡는 테스트를 수정 전후로 확인
재시도: 같은 실패에 새 근거가 없으면 원인과 상태를 보고
완료 보고: 변경 요약, 실행 명령, 결과, 미검증 범위
```

小さな修正では必要な項目だけを使います。
長いテンプレートを毎回使うより、誤りを判断する基準と確認手段を漏れなく伝えます。

## まとめ

AIコードの検証ループでは、期待する挙動を定め、不具合を再現し、小さな修正を実行結果につなげます。
型チェック、テスト、ブラウザー検証は確認する範囲が異なるので、変更の影響に合わせて選びます。

<br/>

**失敗を次の修正の根拠にし、最終コードで確認した結果を残します。**
この流れを依頼に組み込むと、説明の繰り返しや推測に基づく修正を減らし、人がレビューする範囲も明確になります。
