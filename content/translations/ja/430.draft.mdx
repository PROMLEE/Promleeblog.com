## はじめに

「ログインの不具合を直してください」は、人にとっても曖昧ですが、AIコーディングエージェントには特に調査範囲の広い依頼です。
エージェントは、ログイン画面、API、セッション、環境変数、テストをすべて調べ、考えられる原因を推測することになります。
その結果、期待どおりの修正にならないこともあります。

<br/>

**良い作業依頼は、エージェントが実行できる小さな作業契約です。**
この記事では、目標、範囲、制約、完了条件を漏れなく伝える依頼の構成を整理します。

<Bbox>エージェントに任せる作業の大きさは、PR一つ分よりも「検証できる結果一つ分」を目安にするとよいでしょう。小さな契約なら調査範囲が狭まり、失敗したときに原因を調べやすくなります。</Bbox>

## 作業契約

> エージェントが誤ったコードを書く背景には、完了の定義が抜けていることがよくあります。

作業依頼には、次の六つの項目を含めます。
すべてを長く説明する必要はありませんが、エージェントが推測すると危険な点は明記します。

| 項目 | 確認する問い | 例 |
| --- | --- | --- |
| 目標 | 何が変わるべきですか？ | パスワード再設定画面で、リンクの有効期限切れを案内します。 |
| 範囲 | どこを変更できますか？ | `apps/web` と該当するAPIハンドラーだけを修正します。 |
| 制約 | 何を維持しますか？ | 既存の再設定トークンの形式と公開APIを維持します。 |
| 完了条件 | どの状態になれば完了ですか？ | 期限切れのリンクには案内画面が表示され、有効なリンクは従来どおり動きます。 |
| 検証 | どう確認しますか？ | 関連する単体テストと `pnpm lint` を実行します。 |
| 判断の境界 | いつ止めて確認しますか？ | DBスキーマやメールテンプレートの変更が必要なら、先に確認します。 |

OpenAIのCodexガイドでも、`AGENTS.md`、スキル、作業プロンプトなど、エージェントの作業を定める指示を最新に保ち、作業に合う文書を参照させるよう勧めています。
[OpenAI Developersの指示設計の原則](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

## 曖昧な依頼と具体的な依頼

同じ機能でも、依頼の構成によってエージェントが調べる範囲と結果が変わります。

```text title="vague-request.txt"
로그인 오류를 고쳐 주세요.
```

この依頼には、不具合の症状、変更できる範囲、テスト、既存の挙動を維持する条件が書かれていません。
エージェントが広く調査したり、目についたコードを修正した結果、意図と異なる解決策になったりする可能性があります。

```md title="agent-task.md"
## 목표
만료된 비밀번호 재설정 링크를 열면 안내 화면을 표시합니다.

## 범위
- apps/web의 재설정 페이지와 apps/api의 토큰 검증 핸들러만 수정합니다.
- 기존 정상 토큰 흐름은 바꾸지 않습니다.

## 완료 조건
- 만료 토큰은 안내 화면을 표시합니다.
- 유효 토큰은 현재 비밀번호 변경 화면을 표시합니다.
- 관련 테스트와 pnpm lint가 통과합니다.

## 판단 경계
- DB 스키마, 토큰 형식, 메일 문구 변경이 필요하면 구현 전에 질문합니다.
```

二つ目の依頼では実装方法を指定せず、**エージェントがどこまで自分で判断でき、何を維持すべきか**を明確にしています。

<Ybox>実装方法を細かく指定しすぎると、より単純で安全な解決策を選べなくなる場合があります。「Reactの状態を三つ追加する」より、「ユーザーが期限切れだと分かる表示にする」のように、まず結果と範囲を書きます。</Ybox>

## 範囲と判断の境界

作業依頼で特に重要なのは、何を変更してはいけないかを示す一文です。
エージェントは問題を解決しようとして、変更範囲を広げることがあるためです。

### 変更範囲

次の三つを分けて記載すると、不要な範囲拡大を防げます。

- **変更できる範囲**
  変更してよいディレクトリ、ファイル、APIを指定します。
- **維持する契約**
  互換性を保つべき公開API、データ形式、ユーザーの操作手順を書きます。
- **確認が必要な条件**
  スキーマ、決済、権限、デプロイなど、チームの判断が必要な箇所を明記します。

<Rbox>「必要ならリファクタリングしてください」のような広い権限を、既定で与えないようにします。依頼に直接関係しない大規模リファクタリング、依存関係の入れ替え、スキーマの変更は、別の作業に分けます。</Rbox>

作業が大きい場合は、長い依頼一つで進めるより、最初に調査の契約を作ります。
例えば「原因と変更案を整理し、修正前に計画を提案してください」と始め、その後、実装の契約を別に渡します。
こうして分けておくと、大きな変更でも引き返しやすくなります。

## 完了条件

「実装しました」という報告だけでは完了を判断できません。
エージェントとレビュー担当者が同じ結果を確認できるよう、観察可能な条件を書きます。

| 種類 | 曖昧な表現 | 確認可能な表現 |
| --- | --- | --- |
| 画面 | エラーを分かりやすく表示してください | 期限切れのリンクで、見出し、再リクエストボタン、ヘルプへのリンクを表示します。 |
| API | 安全に処理してください | 不正なトークンには400を返し、ユーザー情報を開示しません。 |
| テスト | テストしてください | 期限切れ、有効、欠落したトークンのテストを追加し、実行します。 |
| 性能 | 遅くならないようにしてください | ネットワークリクエストを増やさず、既存のトークン検証を使います。 |

## 依頼テンプレート

次のテンプレートを、Issue、PRの説明、エージェントとの会話の出発点として使ってみてください。

```md title="docs/agent-tasks/password-reset-expiry.md"
 # 목표
<사용자에게 달라져야 하는 결과>

 # 범위
- <수정 가능한 경로>
- <보존해야 하는 기존 흐름>

 # 완료 조건
- <관찰 가능한 결과 1>
- <관찰 가능한 결과 2>
- <실행할 검증 명령>

 # 판단 경계
- <질문이 필요한 변경>
- <명시적으로 제외한 작업>

 # 전달 결과
- 변경한 파일과 이유를 요약합니다.
- 실행한 검증 명령과 결과를 기록합니다.
- 남은 위험 또는 결정이 있으면 적습니다.
```

依頼を書く時間が少し増えても、エージェントの再調査やレビューの往復が減れば、全体の所要時間は短くなります。
特にチームで繰り返す変更では、この形式をIssueテンプレートにすると、品質基準を共有しやすくなります。

## チームのチェックリスト

✓ 目標を、ユーザーやシステムから観察できる変化として書いている。
✓ 変更できるパスと維持する契約を分けている。
✓ 完了条件にテストまたは検証コマンドを含めている。
✓ 追加の判断が必要な箇所を、確認が必要な条件として分けている。
✓ 作業範囲を超えるリファクタリングを、別の契約に分けている。

## まとめ

AIコーディングエージェントへの依頼では、文章の長さより、六つの項目がそろっているかを確認します。
目標、範囲、制約、完了条件、検証、判断の境界を明記した**作業契約**にします。

<br/>

エージェントが推測する箇所を減らし、確認できる基準を増やすと、成果物の品質を高め、チームのレビューを進めやすくできます。
