## はじめに

指示ファイルを短くし、軽量なモデルに替えたら、トークン使用量が減りました。
ところがPRのレビューでは例外処理の抜けが以前より多く見つかり、人が修正する時間が増えました。
トークンのグラフでは改善に見えても、実際の開発は長引くことがあります。

<br/>

シリーズの前半では、コンテキスト、作業依頼、モデル選択、コード検証を扱いました。
最後に必要なのは、**作業方法の変更が完了率、時間、費用にどう影響したかを確認できる記録**です。
この記事では、大がかりなダッシュボードがなくても始められる、作業単位の指標と比較方法を整理します。

## 測定の単位

> 会話やコミットの回数ではなく、完了条件のある作業を一つの単位として記録します。

「検索フィルターの値がブラウザーの『戻る』で復元されない不具合を直す」は一つの作業です。
依頼を3回出し直し、モデルを替えたとしても、同じ作業にまとめます。
呼び出しごとに成功を数えると、何度か失敗して最後に解決した作業の実際の費用が見えにくくなります。

<br/>

まず開始と終了を定義します。
この例では、AIに依頼した時点で開始し、合意した検証とレビューを通過した時点で完了です。
着手しても終えられなかった作業は失敗または中断と記録します。
デプロイまで含めるチームでは、デプロイの確認を終了条件に加え、比較する設定すべてに適用します。

<Bbox>
まず作業番号と完了条件を記録してください。
「検索の改善」より、「ブラウザーの『戻る』でURLと入力値が両方復元される」のように結果を確認できる名前が適しています。
一つの作業が複数のセッションにまたがったら、同じ作業番号で結び付けます。
</Bbox>

## 主要な指標

最初は四つを併せて見れば十分です。
一つを最適化する前に、ほかの指標が悪化していないかを確認します。

| 指標 | 計算・記録の基準 | 注意点 |
| --- | --- | --- |
| 完了率 | 完了した作業数 ÷ 評価を終えた全作業数 | 失敗と中断も分母に含める |
| 手戻り時間 | 人が手作業で直した時間と再依頼の準備時間 | 通常のレビュー時間と区別する |
| 総所要時間 | 最初の依頼から検証とレビューの完了まで | AIの実行時間と待ち時間の原因を分ける |
| 総使用量・費用 | 同じ作業の再試行や上位モデルへの切り替えを含む | API料金と契約の利用上限を区別する |

進行中の作業は最終完了率の分母と分けて集計します。
運用データを評価する締め切りも決めておくと、遅れて完了した作業で先週の数字が何度も変わる事態を減らせます。

<Img src="/261012-080002.webp" width={650} height={433} alt="AIコーディングの完了率、人による手戻り、総所要時間、総使用量を一緒に見る指標の図"/>

OpenAIの公式ドキュメントも、代表的な作業で成否、遅延、トークン使用量、成功1件あたりの費用を併せて比較するよう案内しています。
[OpenAIのデプロイチェックリスト](https://developers.openai.com/api/docs/guides/deployment-checklist)

### 手戻りを分けて記録する

通常のレビューと、AIの成果を修正するための手戻りは区別します。
コードを読んで確認する10分と、抜けた条件を説明して依頼し直す20分は別の費用です。
手作業での修正時間と再依頼の準備時間を記録すると、どの負担が増えたかが分かります。

<br/>

検証中にAIが自ら修正を繰り返した時間は、人による手戻り時間に含めません。
その分は総所要時間と使用量に反映します。
人が修正に介入したかを別途記録すると、最終完了率が高くても、人の助けを多く必要とした作業を見分けられます。

## 作業の記録

最初は、作業ごとのメモやCSVの1行で十分です。
項目は、実際の意思決定に使うものから加えます。
以下はチームで使えるTypeScriptの記録例で、特定のAPIや製品のログ形式ではありません。

```ts title="tools/task-metrics.ts"
type TaskRecord = {
  taskId: string;
  taskType: "small-edit" | "feature" | "debug";
  startCommit: string;
  requestVersion: string;
  modelPath: string[];
  outcome: "accepted" | "failed" | "blocked";
  elapsedSeconds: number;
  humanReviewMinutes: number;
  humanReworkMinutes: number;
  extraRequests: number;
  apiCostUsd: number | null;
};
```

`modelPath` には、実際に使ったモデルと推論設定を実行順に残します。
`extraRequests` は、初回の依頼の後で人が送った追加の修正依頼数とします。
ツール呼び出しとテストの実行はこの数に含めません。
サブスクリプションで `apiCostUsd` が不明なら `null` を使い、確認できない費用を0ドルで埋めないようにします。

<br/>

検証コマンドと失敗の根拠は、第7回の完了報告の形式で別に保存し、作業番号でひも付けます。
集計表には失敗理由を短く残せば十分です。
「エントリーポイントの情報がない」「レスポンスのスキーマを誤解」「テスト環境が未準備」のように具体的に書くと、次の改善を選びやすくなります。

### 使用量の収集

Claude Codeの公式ドキュメントでは、`/usage` のSession欄で、セッションのトークン使用量と推定費用を確認するよう案内しています。
契約ユーザーは同じ画面で利用上限を確認します。API単価で算出したセッションの推定費用は、契約の請求額とは区別します。
実際のAPI請求額を確認するには、Claude Consoleの使用量データを使います。
[Claude Codeの費用管理](https://code.claude.com/docs/en/costs)

一つのセッションで複数の作業を行った場合、セッション全体の使用量を各作業に転記しません。
作業の境界ごとの差分を計算できるか確認し、区別できなければセッション単位でしか集計できないと明記します。
リクエストごとに累積値を加えると同じトークンを何度も数えることになるため、収集する値が累積か個別呼び出しかも確認します。

<Ybox>
入力、出力、キャッシュ、推論のトークンの関係は、提供元が返す使用量データの構造によって異なります。
内訳の値が合計に含まれていれば、重ねて足しません。
トークン総数だけで金額を計算せず、モデル、キャッシュ、処理に適用される料金も確認します。
</Ybox>

## 完了1件あたりの費用

第6回では、一つの作業で上位モデルに切り替えた場合の費用を見ました。
複数の作業を比較する際は、失敗した試行の費用も合計し、完了した作業数で割ります。
完了できなかった作業を除外すると、実際より割安に見えるためです。

```ts title="tools/task-metrics.ts"
function summarize(tasks: TaskRecord[]) {
  const accepted = tasks.filter((task) => task.outcome === "accepted");
  const costsKnown = tasks.every((task) => task.apiCostUsd !== null);
  const totalCost = costsKnown
    ? tasks.reduce((sum, task) => sum + task.apiCostUsd!, 0)
    : null;

  return {
    evaluated: tasks.length,
    accepted: accepted.length,
    completionRate: tasks.length ? accepted.length / tasks.length : null,
    humanReworkMinutes: tasks.reduce(
      (sum, task) => sum + task.humanReworkMinutes, 0,
    ),
    costPerAcceptedTask:
      accepted.length && totalCost !== null
        ? totalCost / accepted.length
        : null,
  };
}
```

この例では、評価を終えた作業だけが入力されると仮定します。
作業ごとの費用には再試行や上位モデルへの切り替えを含み、1件でも費用が不明なら、完了1件あたりの費用も不明とします。
完了した作業が0件の場合も、費用を0とは表示しません。
呼び出しが多い作業を重複集計しないよう、`taskId` ごとに一つのレコードを渡します。

### 比較例

以下は計算用の架空のデータです。実測値やモデルの性能を示すデータではありません。
設定AとBで同じ10件の作業を実行したと仮定します。

| 項目 | 設定A | 設定B |
| --- | --- | --- |
| 完了した作業 | 9件 | 7件 |
| 失敗・中断した作業 | 1件 | 3件 |
| 完了率 | 90% | 70% |
| API費用の総額 | 12ドル | 10ドル |
| 完了1件あたりのAPI費用 | 約1.33ドル | 約1.43ドル |
| 人による手戻り時間 | 45分 | 80分 |

BはAPI費用の総額が低い一方、完了1件あたりの費用と人による手戻り時間が増えています。
人の作業時間とAPI費用を別々に見ると、この違いが分かります。
チームに人件費の基準がなければ、任意の時給で換算し、一つの金額にまとめる必要はありません。

## 比較の条件

異なる作業で得た数値だけを比べると、設定の効果と作業の難しさの違いが混ざります。
同じ初期コード、依頼、検証基準、実行環境を用意し、変数を一つずつ変えます。
前の修正を反映したコードで次の設定を実行すると、最初の設定の結果を引き継いだ比較になります。

<Img src="/261012-080003.webp" width={650} height={433} alt="同じ初期コード・依頼・検証・実行環境を固定し、変数を一つ変えて完了率、手戻り、時間、費用を比較する基準"/>

例えば `AGENTS.md` を短くする効果を見るなら、モデルと推論レベルは固定します。
モデルルーティングを比較する場合は、指示と作業依頼を固定します。
作業依頼、モデル、検証方法を同時に変えると、何が結果に影響したかを判断しづらくなります。

<br/>

OpenAIのSkill評価の記事でも、先に成功基準を定義し、実行結果と検査基準を使って改善と回帰を確認する方法を説明しています。
[OpenAIのSkill評価方法](https://developers.openai.com/blog/eval-skills)

### 作業タイプごとの集計

単純な修正、一般的な機能実装、複雑なデバッグは別々に見ます。
簡単な作業が多かった週と難しい作業が多かった週の全体完了率を比べて、モデルが改善したと結論づけるのは避けます。
作業タイプごとに件数と完了率を併記します。

<br/>

時間は平均に加え、完了した作業の中央値と、時間がかかった事例も確認します。
中央値は値を並べたときの中央の値で、一部の長時間作業の影響を平均より受けにくくなります。
ただし完了した作業だけの時間なので、失敗・中断件数と、そこまでに使った時間は別途記録します。

<Rbox>
完了率を上げるために難しい作業を記録から外したり、検証条件を緩めたりしないでください。
比較の入力と成功基準を変えると、同じ指標名でも過去の結果と直接比較できません。
</Rbox>

## 改善の進め方

指標は、次の行動を選ぶために使います。
数値が悪化した作業の記録と失敗理由を調べ、一つの改善を選びます。

| 観測した変化 | まず確認すること | 改善策 |
| --- | --- | --- |
| 入力使用量の増加 | 繰り返し読む指示、文書、ツール結果 | エントリーポイントを案内し、必要時に参照し、レスポンスの範囲を絞る |
| 完了率の低下 | 失敗の再現と完了条件の抜け | 依頼を具体化し、検証手段を用意する |
| 人による手戻りの増加 | 要件やインターフェースの誤解 | 入出力の例と変更範囲を明記する |
| 待ち時間の増加 | テスト、ツール、環境のボトルネック | 関連する検査を優先し、実行環境を整える |
| 上位モデルへの切り替えと再試行の増加 | 初期のモデル選択と情報不足 | 作業別のモデル選択基準と引き継ぎ要約を調整する |

使用量が増えても、手戻りが減って完了率が上がったなら、受け入れられる変化かもしれません。
一方、費用が減っても検証の抜けが増えたなら、その設定を維持する理由は弱くなります。
数値だけで原因を決めず、個別の作業の根拠を確認します。

<Ads3/>

### 始め方

繰り返し発生する作業タイプを一つ選び、現在の設定で基準値を記録します。
指示の長さ、モデル、推論強度のうち一つだけを変え、同じ事例で比較します。
少数の結果は傾向を見る資料とし、新しい作業でも同じ傾向が続くことを確認してから既定の設定に反映します。

<Bbox>
週に一つ、改善項目を選んでみてください。
「トークンを節約する」のような広い目標より、「同じ検索機能の作業で完了率を維持し、文書の読み直しを減らす」のように観察できる目標を立てます。
</Bbox>

## まとめ

AIコーディングの指標では、コードを生成する速さに加え、検証とレビューを経てどれだけの作業を終えたかを確認します。
作業ごとに完了条件を決め、失敗、中断、再試行まで記録すれば、使用量の減少が実際の効率改善につながったかを判断できます。

<br/>

シリーズで扱ったコンテキスト整理、最小限の指示、リポジトリの案内、作業依頼、SkillとMCPの読み込み、モデルルーティング、コード検証は、一つずつ見直せます。
**基準値を記録する → 変数を一つ変更する → 同じ条件で比較する → 作業ごとに原因を調べる**という順で、チームに合う方法を探してください。
