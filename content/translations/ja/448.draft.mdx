## はじめに

一つのAIに検索画面を、もう一つのAIに検索APIを任せました。
それぞれテストを通過したとのことでしたが、結果を合わせると、画面は `items` を読み、APIは `results` を返します。
同じファイルを編集していないため、Gitの競合は起きません。
それでも機能は動きません。

<br/>

並行作業には、複数のセッションを開く以上の準備が必要です。
**共有する契約と担当範囲を先に決め、変更を分離し、統合した結果を検証します。**
この記事では検索機能を例に、作業を分ける基準、Git worktreeの運用、結果の統合方法を整理します。

## 作業を分ける

> 並行して進められるのは、相手の作業が終わるのを待たずに判断できる作業です。

検索画面とAPIを並行実装するには、入力パラメーターとレスポンスの構造を先に決めておきます。
まだレスポンス形式を選んでいる段階なら、API設計を確定してから分担したほうが進めやすくなります。
合意していない境界を双方が推測すると、実装より調整に時間がかかることがあります。

| 作業の関係 | 進め方 | 理由 |
| --- | --- | --- |
| 契約が確定した画面とAPIの実装 | 並行して進める | 同じ入出力を基準に作業できる |
| レスポンス構造の設計と、それを使う画面 | 設計してから実装する | 先に決めた内容が次の作業の入力になる |
| 異なるモジュールの独立したバグ修正 | 並行作業を検討する | 共有状態とテスト環境の確認が必要 |
| 同じ中核関数に対する別々の修正 | 順番に進めるか、一人の担当者にまとめる | 変更の意図と回帰を確認する条件が重なる |

「フロントエンドとバックエンドを分けて」とだけ依頼するのではなく、契約をコードか文書に記録します。
以下は画面とAPIが共通で使う型の例です。

```ts title="src/contracts/search.ts"
export type SearchItem = {
  id: string;
  title: string;
};

export type SearchResponse = {
  items: SearchItem[];
  nextCursor: string | null;
};

export type SearchError = {
  code: "INVALID_QUERY" | "INTERNAL_ERROR";
  message: string;
};
```

型と併せて、リクエストパラメーター、結果が0件の場合の扱い、HTTPステータスコードも決めます。
型が同じでも、画面が `q` を送り、APIが `query` を受け取るなら、つながりません。
実行時のレスポンスも契約に従っているかを検証します。

<Img src="/261015-110002.webp" width={650} height={433} alt="入出力の契約と基準コミットを定め、画面とAPIを並行実装し、順次統合と回帰検証につなげる作業分担"/>

<Bbox>
共有契約の変更が必要になったら、各担当が独自に変更せず、統合担当者に変更案を伝えるよう決めておきます。
必要な変更を基準コードに反映し、影響を受ける担当者が更新後の契約を確認してから作業を続けます。
</Bbox>

## 担当範囲

各作業には目標と完了条件に加え、変更するファイルの範囲を指定します。
個別の作業で担当しない共通ファイルは、統合担当者が管理します。

| 担当 | 変更範囲の例 | 共有部分との境界 |
| --- | --- | --- |
| 画面 | `src/features/search/`、画面のテスト | API契約に従ってAPIを利用する |
| API | 検索ルートとサービス、APIテスト | 同じ契約に従って応答する |
| 統合 | 共有契約、パッケージ設定、機能全体の接続 | 変更の適用順序と最終検証を決める |

`package.json`、ロックファイル、共通のテスト設定は変更が重なりやすい箇所です。
依存関係の追加が必要なら、要件として記録し、一人の担当者が反映する方法があります。
複数のセッションが同じ設定を同時に編集しないようにするだけでも、調整の範囲を狭められます。

<br/>

参照できる範囲まで一律に制限する必要はありません。
APIの担当者が画面での使い方を読むのは役に立ちます。
**参照できるファイルの範囲と、変更を担当する範囲を分けて**伝えます。

```text title="화면 작업 요청 예시"
목표: 검색어 입력, 빈 결과, 오류 상태 표시
계약: src/contracts/search.ts와 합의된 q 파라미터 사용
수정: src/features/search/와 관련 화면 테스트
공유 파일: 계약·패키지 설정 변경은 제안만 전달
검증: 화면 상태 테스트와 요청 파라미터 확인
완료 보고: 결과 커밋, 변경 파일, 검증 결과, 미검증 범위
```

## worktreeによる分離

同じチェックアウトで複数のセッションが編集すると、ほかのセッションの変更を読み込んだり、上書きしたりすることがあります。
Git worktreeを使うと、一つのリポジトリに複数の作業ディレクトリを関連付け、ブランチごとにファイルとインデックスを分けて使えます。
[Git worktreeのドキュメント](https://git-scm.com/docs/git-worktree)

以下はターミナルで手動管理する例です。
共有契約がすでにコミットされ、使用するブランチ名と作成先のパスはまだ存在しないものとします。
まず、現在のリポジトリの変更状態を確認します。

```bash title="동일 기준에서 작업 공간 생성"
git status --short
task_base=$(git rev-parse HEAD)
git worktree add -b ai/search-ui ../shop-search-ui "$task_base"
git worktree add -b ai/search-api ../shop-search-api "$task_base"
git worktree list
```

`task_base` は二つの作業が出発する共通のコミットです。
現在のディレクトリの未コミット変更はこのコミットに含まれず、新しいworktreeにも自動では引き継がれません。
必要な契約変更がまだコミットされていない場合は、チームの手順に沿って先に基準となる状態を用意します。

<br/>

Codexアプリには、worktreeで作業を分離する機能があります。
アプリが管理するworktreeは、アプリの作成、移動、整理機能で扱います。上の手動コマンドは、CLIで別に管理する場合の例です。
[Codexのworktreeガイド](https://learn.chatgpt.com/docs/environments/git-worktrees)

Claude Codeも、`--worktree` で分離した並行セッションを開始する方法を案内しています。
手動で作ったworktreeを使う場合は、各ディレクトリからセッションを開始できます。
[Claude Codeのworktreeワークフロー](https://code.claude.com/docs/en/common-workflows)

### 共有リソース

ディレクトリを分けても、開発サーバーのポートや外部DBが自動的に分離されるわけではありません。
例えば、二つの作業で同じポートのサーバーを起動すると競合し、同じテストデータを変更すると互いの結果に影響する場合があります。
既存プロジェクトの分離方法に沿って、ポート、テストアカウント、データ領域を分けます。

<Img src="/261015-110003.webp" width={650} height={433} alt="worktreeで分離できるファイルとブランチ、および別途確認が必要なポート・DB・ローカル設定の範囲"/>

Nodeプロジェクトの依存関係や、Gitが追跡していない環境設定ファイルも、個別に用意する必要がある場合があります。
一方のworktreeでサーバーが動いても、もう一方の準備状況は個別に確認します。
例えば画面用サーバーは3101、API確認用のサーバーは3102と決め、内部APIのアドレスとテストのベースURLも合わせます。

<Ybox>
テスト用DBを分けた場合も、マイグレーションの対象と外部APIのアカウントが共通かどうかを確認します。
worktreeが分離するのはファイルへの変更です。外部サービスを実行する権限や、外部のデータは別途分離します。
</Ybox>

## 結果を統合する

並行作業が終わったら、第10回の引き継ぎ記録と同じように、結果のコミット、基準コミット、変更範囲、検証結果を受け取ります。
統合担当者は共有契約が守られているかを確認し、結果を一つずつ反映します。
作業中のファイルをコピーして混ぜると変更単位が見えづらくなるため、変更単位を識別できる方法で取り込みます。

<br/>

以下は、各作業の結果が一つずつのコミットにまとまっている場合の例です。
先に記録した `task_base` と二つの作業ブランチが残っており、各作業は完了して追加修正がないと仮定します。

```bash title="별도 작업 공간에서 순차 통합"
git worktree add -b ai/search-integration ../shop-search-integration "$task_base"
task_ui_commit=$(git rev-parse ai/search-ui)
task_api_commit=$(git rev-parse ai/search-api)
git -C ../shop-search-integration cherry-pick "$task_ui_commit"
git -C ../shop-search-integration cherry-pick "$task_api_commit"
```

`cherry-pick` は、指定したコミットの変更を現在のブランチに適用します。
結果が複数のコミットにまたがる場合、最後のコミットだけでは先行する変更が抜けることがあります。コミット一覧と依存順序を確認するか、チームのマージ手順を使います。
[Git cherry-pickのドキュメント](https://git-scm.com/docs/git-cherry-pick)

<br/>

最初の適用が競合で止まった場合は、次の適用に進みません。
変更の意図と契約を確認して解消し、`git cherry-pick --continue` で続行します。
適用を取り消す必要があるなら、`git cherry-pick --abort` で元に戻る範囲を確認し、進行中の適用を中止します。

### 競合の種類

Gitが競合を表示しなくても、挙動の不整合は起こります。
冒頭のように `items` と `results` が一致しない場合や、画面が空配列を正常とみなすのに、APIがエラーを返す場合です。

| 競合 | 例 | 確認方法 |
| --- | --- | --- |
| ファイルの競合 | 同じ関数の同じ行を変更 | 差分と変更意図を確認 |
| 契約の競合 | レスポンスのフィールドやエラーコードの不一致 | 契約の検査とAPI利用側のテスト |
| 環境の競合 | ポートやテストデータを共有 | 起動アドレスとデータの分離を確認 |
| 検証漏れ | 個別テストだけが通る | 統合後の状態でユーザーの操作を再現 |

<Rbox>
競合を消すために片方の変更を丸ごと採用したり、テストを削除したりしないでください。
双方の完了条件を基準に必要な挙動を残し、統合後の結果を再検証します。
</Rbox>

## 統合後の検証

作業AのテストはAのコード状態、作業BのテストはBのコード状態についての根拠です。
両方を統合した状態には、別途検証が必要です。
統合ブランチで契約と実際の接続を確認します。

- 画面が合意したリクエストパラメーターを送っているか確認します。
- APIの成功、結果0件、エラーのレスポンスを画面で処理できるか確認します。
- 関連する型チェック、単体テスト、統合テストを実行します。
- 検索語の入力から結果表示まで、実際にブラウザーで確認します。
- 統合時にコードを変更したら、影響する検査を再実行します。

モックのレスポンスで画面を先に実装した場合は、最後の接続確認に実際のテスト用APIを使います。
モックと実際のレスポンスが同じ契約に従っているかも確認します。
ここでの例は作業順序のガイドであり、運用中のプロジェクトでコマンドを実行した結果ではありません。

### 作業環境を片付ける条件

成果が保存され、実行中のセッションやサーバーが使わなくなったら、worktreeを片付けます。
手動管理の場合は、`git worktree list` で正確なパスを確認し、変更と必要なローカルファイルを点検したうえで `git worktree remove` を使います。
アプリが管理するworktreeは、そのアプリの整理機能を使います。

<Bbox>
Gitの追跡対象外になっている環境設定ファイルやテストの生成物は、結果のコミットに含まれていない場合があります。
片付ける前に保存すべきファイルがないか確認し、未完了の作業は整理とは別に扱います。
</Bbox>

## 時間と費用

作業AとBが独立していれば、並行実行の区間はおおむね、時間のかかったほうの作業が終わると完了します。
ただし総所要時間には、分担の準備、各作業の調査、結果のレビュー、競合解決、統合検証も含まれます。
小さな修正をいくつかに分けると、こうした付随作業にかえって時間がかかる場合があります。

<br/>

トークンの費用も、すべての作業と統合担当者の使用量を合算します。
並行セッションがそれぞれリポジトリの指示と関連コードを読み込むことがあるため、短縮できた時間と、トークンの増減は分けて確認します。
第8回で紹介した指標と同様に、完了率、人による手戻り、総所要時間、総使用量を比較します。

初めて並行作業を取り入れるなら、契約が安定し、変更範囲が異なる二つの作業から始めてみてください。
統合にどれだけ時間が増えたかを記録すると、チームで並行化する作業の基準を調整できます。

## まとめ

AIによる並行作業では、共有契約を先に定め、担当範囲と作業環境を分け、結果を一つずつ統合します。
worktreeを使っていても、ポートやDBなどの共有リソースと、Gitが表示しない挙動の不整合は個別に確認します。

<br/>

**契約の確定 → 担当範囲の分離 → 作業環境の分離 → 順次統合 → 接続の検証**を基本の流れにしてみてください。
最終回の第12回では、この過程を、依頼の設計、モデル選択、検証、測定とつなぎ、チームの開発ワークフローにまとめます。
