## はじめに

ユーザーは「この文書を要約してください」と一度だけボタンを押しました。
サーバーは文書を検索してモデルを呼び出しましたが、回答に根拠がなかったので、モデルをもう一度呼び出しました。
ユーザーの操作は1回ですが、課金対象のモデル応答は2回です。
**ユーザーのリクエスト1件とモデル呼び出し1回を同じ単位で数えると、原価を過小評価する可能性があります。**
<br/>
例に使うのは、架空の文書要約・質問応答サービスです。
呼び出し回数、トークン数、品質判定は説明用の仮定で、公式単価のみ実際の料金表から引用しています。
料金は2026年10月15日に確認し、為替レートは1ドル＝1,400ウォンと仮定します。

## 費用を数える単位

ユーザーリクエストは利用者が実行しようとした作業で、モデル呼び出しはAPIに送った個々のリクエストです。
成功した処理とは、応答が返るだけでなく、サービスの完了基準を満たした作業を指します。
この例では、質問に答え、回答の主要な主張に文書の根拠をひも付けることが完了基準です。
実際の運用では、完了判定の仕組みにかかる費用や、人によるレビューの費用も別途記録します。

<Img src="/261015-aibiz-02-cost-flow.webp" width={650} height={433} alt="ユーザーのリクエストが検索・モデル呼び出し・品質検査を経て、基準未達なら有料の再試行が加わる費用の流れ"/>

この構成では、モデルAPIに加えて、文書の前処理、埋め込み、検索、保存、サーバーでの処理が必要になる場合があります。
保存は通常、保存量と期間、埋め込みは処理量というように、それぞれ異なる単位で計算します。
月額基本料金に含まれるリソースを処理ごとの費用として再度足すと、二重計上になります。
利用枠を超えて実際に増えた費用や、別途契約した外部サービスの使用料を増分原価として分けます。

## 公式単価を当てはめる

Claude Sonnet 5.5の標準API単価は、通常入力が100万トークンあたり2ドル、出力が10ドルです。
5分間のキャッシュへの書き込みは2.5ドル、キャッシュからの読み取りは0.1ドルです。
以下はグローバル・非バッチでの料金です。ほかの処理オプションの割引や割増は含めていません。[Claude APIの料金表](https://platform.claude.com/docs/en/about-claude/pricing)

| 呼び出し1回あたりの仮定 | トークン数 | 費用（米ドル） |
| --- | --- | --- |
| 通常入力 | 8,000 | $0.016 |
| 出力 | 1,000 | $0.010 |
| 合計 | キャッシュなし | $0.026 |

したがって、想定為替レートでは呼び出し1回あたり36.4ウォンです。
入力には、システム指示、文書、会話、ツール定義など、実際に課金されるコンテキストを含めます。
再試行では前回の回答を一緒に送ることでトークン数が変わる可能性がありますが、今回はすべて同じサイズとして計算します。
*同じ文書でも、モデルが異なるとトークン数が変わる場合があります。*
モデルを替えて比較するときは、そのモデルの使用量フィールドを使って計算し直します。

## 失敗を含めた原価

仮の記録には最初の処理が100件あります。
90件はそのまま品質基準を満たし、10件は応答があったものの根拠が不足していました。
その10件をそれぞれ1回再試行し、すべて基準を満たしたと仮定します。

| 記録項目 | 件数・金額 |
| --- | --- |
| 最初の処理 | 100件 |
| 最初のモデル呼び出し | 100回 |
| 品質基準未達後の再呼び出し | 10回 |
| 課金対象の呼び出し合計 | 110回 |
| 最終的に成功した処理 | 100件 |
| モデルの費用 | 110 × 36.4＝4,004ウォン |
| モデル以外の増分原価の仮定 | 100 × 3.6＝360ウォン |
| 処理費用の総額 | 4,364ウォン |
| 成功1件あたりの費用 | 4,364 ÷ 100＝43.64ウォン |

360ウォンは、外部の前処理や埋め込みなどにかかる追加利用料の予算上の仮定です。特定の提供元の検索単価を示すものではありません。
実際には、月間の追加請求額と該当する処理のまとまりを照合して配賦します。
この43.64ウォンを[第1回の損益計算](/blog/post/450-ai-service-unit-economics)に当てはめると、ユーザー1人あたり200件の処理原価は8,728ウォンになります。
<br/>
ここでいう失敗は、*課金された応答が品質基準を満たさなかったケース*です。HTTPエラーとは区別します。
Claudeは失敗したリクエストには課金しないと案内していますが、成功するはずだったリクエストの途中でクライアントの接続が切れたりタイムアウトしたりした場合は、課金されることがあると説明しています。
エラーを一律に有料と仮定せず、ユーザーに失敗と表示された場合も、請求の有無を確認します。[Claude APIの支払い案内](https://support.claude.com/en/articles/8977456-how-do-i-pay-for-my-claude-api-usage)

<Bbox>
呼び出し記録には、`task_id`、`attempt`、`model`、入力・出力・キャッシュのトークン数、提供元のリクエストID、費用、品質判定を残します。
ユーザーの文書そのものより、費用を追跡するのに必要なメタデータを優先して記録し、提供元の請求明細と照合します。
</Bbox>

## キャッシュと品質による変化

同じ仮の記録でキャッシュが使えたら、費用はどれほど変わるでしょうか。
8,000入力トークンのうち共通の6,000トークンを最初の呼び出しでキャッシュに書き込み、残りの109回が5分以内に同じキャッシュを読み取る理想的なまとまりを仮定します。
各呼び出しの残りの入力2,000トークンと出力1,000トークンはそのまま課金されます。

```text
첫 호출 = 6,000 × $2.5/백만 + 2,000 × $2/백만 + 1,000 × $10/백만
        = $0.029
이후 호출 = 6,000 × $0.1/백만 + 2,000 × $2/백만 + 1,000 × $10/백만
          = $0.0146
전체 비용 = ($0.029 + 109 × $0.0146) × 1,400 + 360
          = 2,628.56원
성공 작업당 비용 = 26.2856원
```

**この条件では、キャッシュへの書き込み費用を含めても、成功1件あたりの原価が下がります。**
実際には、顧客ごとに非公開文書が異なり、一日分のリクエストがすべて5分以内に集中するとも限りません。
この数字は効果を試算するための別シナリオです。第1回の基準原価はそのまま使います。
設定とキャッシュヒットの条件は[プロンプトキャッシュの記事](/blog/post/446-prompt-caching-for-coding-agents)で確認できます。
<br/>
逆に同じ4,364ウォンを使っても、基準を満たしたのが80件なら、成功1件あたりの費用は54.55ウォンです。
成功が0件なら、**成功1件あたりの費用は算出できません**。
総費用と失敗件数はそのまま記録します。
モデルを替える実験でも[検証ループ](/blog/post/433-agent-code-verification-loop)を取り入れ、品質、応答時間、人による修正時間を比較します。

## サブスクリプションとクレジット

サービスのAPI請求額と開発ツールのサブスクリプション料は別々に記録します。
APIキーでCodexを使う開発作業はAPI課金の対象なので、顧客への回答を生成する呼び出しとは、プロジェクト、キー、用途ごとに分けます。[OpenAIの料金案内](https://learn.chatgpt.com/docs/pricing)
<br/>
サブスクリプションにAPIの特典が付く場合もあります。
Claude Max 5xと20xには、それぞれ月100ドルと200ドルのAPIクレジットが案内されています。
利用資格とアカウントの連携が必要です。クレジットはClaude Codeの追加利用には適用されず、未使用分は利用周期の終了時に失効します。[Claude付帯APIクレジットの案内](https://platform.claude.com/docs/en/about-claude/api-credits-for-subscribers)
<br/>
クレジットがあっても、トークン数から計算したリソース原価は記録します。
その下に適用クレジットと追加の現金支出を別々に記載すると、クレジットが失効したり尽きたりした後の収支も比較できます。
この3回の基準は低価格の月額契約一つとAPIクレジット0ドルです。Maxの契約料や特典は含めていません。

## まとめ

原価計算の出発点は、**品質基準を満たす作業を完了するまでにかかった総費用**です。
まずは自分の処理を100件まとめ、最初の呼び出し、再試行、最終的に成功した件数、増分費用を同じ期間で記録してみてください。
次に、トークン数を減らしたときに完了率と人による修正時間が維持されるかを確認します。
次回は、この原価を回収でき、利用者にも分かりやすい[AIサービスの料金プラン](/blog/post/452-ai-service-pricing)を設計します。
