## はじめに

AIと1時間かけてバグを分析し、実装を半分ほど進めました。
翌日、新しいセッションで「昨日の作業を続けて」と頼むと、確認済みのファイルを読み直し、すでに退けた仮説をまた提案します。
一方、前の会話を丸ごと貼り付けると、古いログや失敗した修正まで新しいコンテキストを埋めてしまいます。

<br/>

作業を続けるには、次のセッションが判断できる**現在の状態と確認の根拠**が必要です。
何を目指し、実際のコードがどこまで変わり、何を検証し、次に何をするかを残します。
この記事では、会話の圧縮と作業の引き継ぎを区別し、リポジトリに短い記録を置いて作業を再開する方法を整理します。

## 再開と引き継ぎ

> 会話を復元することと、現在のコードの状態を確認することは別の手順です。

同じツールで以前のセッションを開けるなら、その会話を続けると便利です。
会話が保存されていても、その間に人が編集したファイルや切り替えたブランチまで自動的に一致するわけではありません。
新しいセッションに渡す場合も、既存のセッションを再開する場合も、現在の作業パスと変更状態を確認します。

| 方法 | 引き継がれる情報 | 別途確認すること |
| --- | --- | --- |
| 以前のセッションを再開 | 保存された会話とツールが復元する状態 | 現在の作業パス、ファイル、実行環境 |
| 会話の圧縮 | 次の作業に必要な会話の状態 | 重要な条件や根拠が保たれているか |
| 引き継ぎ記録から開始 | 明示的に残した目標、状態、次の行動 | 記録が現在のコードと一致するか |

OpenAIは長い会話を続けるための圧縮機能を説明し、APIが返す圧縮項目は、人が読める要約文書ではなく内部を直接読み取れない状態であると区別しています。
[OpenAIの会話圧縮ドキュメント](https://developers.openai.com/api/docs/guides/compaction)

したがって、APIの圧縮項目と、人が確認する `handoff.md` では形式も役割も異なります。
引き継ぎ記録は、別のツールや新しいセッションでも作業の根拠を確認できるようにするチームの文書です。

## 記録する状態

会話全体を短く書き直す代わりに、次の判断に必要な四つの項目を残します。
検索フィルターでブラウザーの「戻る」が正しく動かない不具合なら、次のように整理できます。

| 項目 | 残す内容 | 例 |
| --- | --- | --- |
| 目標と範囲 | 完了条件、変更する範囲と対象外 | URLと入力値の復元、APIの変更は対象外 |
| 現在のコード | 作業パス、基準コミット、変更ファイル | 検索フォームを修正中、テストファイルは未追跡 |
| 検証の根拠 | コマンドと結果、実行時のコードの状態 | 型チェックは成功、「戻る」のテストは失敗 |
| 次の行動 | 未完了の作業、残っている判断 | URL変更時にローカル状態を更新する経路を確認 |

### 事実と仮説

「ブラウザーで戻るとURLはalphaに戻るが、入力欄にはbetaが残る」は観察した事実です。
「初期値しか読まず、状態の同期が抜けている」は原因についての仮説です。
両者を記録で分けておくと、次のセッションが推測を確定した事実として扱いにくくなります。

<br/>

見送ったアプローチも、必要な場合に理由とともに残します。
例えば「検索APIのキャッシュが原因という仮説は、入力欄の状態だけがずれる再現結果と合わないため保留」と書きます。
失敗した試行のログやコードをすべて本文に転記する必要はありません。
元のログの場所や関連ファイルを参照できるようにします。

<Bbox>
次のセッションで最初に行うことを一つの手順として書いてみてください。
「検索機能を仕上げる」より、「SearchFormがURLの変更を購読し、ローカルの入力状態を更新する箇所を確認する」と書くほうが着手しやすくなります。
</Bbox>

## 引き継ぎ文書

以下は作業ごとの状態を記録する文書の例です。
ファイル名や配置はチームが決めるもので、ツールによる特別な扱いを前提にしていません。
次のセッションで実際に読んでもらうには、依頼にそのパスを明記します。

```yaml title="docs/tasks/search-history-handoff.yaml"
task: search-history
updated_at: "2026-10-15T15:00:00+09:00"
goal: 뒤로 가기와 새로고침 뒤 URL과 입력값을 함께 복원
scope:
  include: 검색 폼 상태와 관련 테스트
  exclude: 검색 API와 정렬 규칙
workspace:
  path: /Users/dev/work/shop
  head: "git rev-parse HEAD로 확인한 커밋 해시"
  uncommitted: true
  changed_files:
    - src/features/search/SearchForm.tsx
  untracked_files:
    - tests/search-history.spec.ts
observed:
  - alpha → beta → 뒤로 가기에서 URL은 alpha, 입력창은 beta
hypothesis:
  - URL 변경을 로컬 입력 상태가 다시 반영하지 않을 수 있음
checks:
  - command: npm run typecheck
    result: passed
  - command: npx playwright test tests/search-history.spec.ts
    result: failed
    detail: 입력값 alpha를 기대했으나 beta가 남음
  - command: npm run build
    result: not_run
evidence_scope: 위 변경 파일 상태에서 실행한 예시 결과
next_action: URL 변경과 로컬 상태 동기화 경로 확인
```

内容は形式を説明する架空の例で、実際のプロジェクトの実行結果ではありません。
実際の記録には、現在のパス、コミットハッシュ、実行したコマンドとその結果を入れます。
ログを保存した場合はパスを加え、次のセッションから参照できる場所か確認します。

<br/>

特に、**コミットハッシュだけでは未コミットの変更は伝わりません。**
同じチェックアウトで続ける場合は、ファイルが残っているかを確認します。
別の環境へ移す場合は、必要な変更をコミットやパッチなど、チームで選んだ方法で別途渡します。
作業パスだけを記録しても、別の環境にファイルは作られません。

### 更新するタイミング

会話のたびに状態を長く書き直すと、記録に手間がかかります。
次のような作業の節目で更新すると実用的です。

- 原因分析を終えて実装に進むとき
- 検証の失敗を次の修正の基準とすると決めたとき
- 作業を中断するか、新しいセッションや別のツールに渡すとき
- 完了後、残る制約と最終検証を整理するとき

完了した項目を積み上げ続けるより、今の判断に必要な内容に更新します。
詳しい経緯が必要なら、Gitの履歴と元の根拠を参照します。

## コードの状態を照合する

引き継ぎ記録を読んだら、リポジトリの実際の状態と照合します。
macOSのターミナルでは、以下のコマンドで現在のパス、コミット、追跡済みファイルの変更、新しいファイルを確認できます。
GitコマンドはWindowsやLinuxでも共通です。パスの表記は環境に合わせます。

```bash title="재개 전 저장소 확인"
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short
git diff --stat
git diff --cached --stat
git ls-files --others --exclude-standard
```

`git diff` だけを見ると、ステージ済みの変更と未追跡ファイルを見落とす場合があります。
関連ファイルの実際の差分や新しいファイルの内容も、必要な範囲で確認します。
上のコマンドでは、Gitの追跡対象外の環境設定ファイルや外部DBの状態までは分からないため、必要な実行環境は別途確認します。

<Img src="/261015-100003.webp" width={650} height={433} alt="引き継ぎ記録を読み、実際のコードの状態と照合し、検証結果を確認して、次の作業を行う再開手順"/>

<Ybox>
HEADが同じでも未コミットのファイルが変わっていれば、前回のテスト結果が当てはまる範囲も変わります。
コミットが違う場合も、すべての検査を一律にやり直す必要はありません。
変更箇所と既存の根拠の関係を確認し、影響を受ける検査を再実行します。
</Ybox>

## セッションを再開する

Claude Codeでは、`claude --continue` で現在のディレクトリの直近のセッションを続けられます。
過去の会話の一覧から選ぶ場合は `claude --resume` を使います。
[Claude Codeで会話を再開する](https://code.claude.com/docs/en/common-workflows)

```bash title="Claude Code 이전 세션 재개"
claude --continue
```

Codex CLIでは `codex resume` で保存された会話を選んで続けられます。
アプリでは、該当するプロジェクトの既存チャットを開いて作業を続けます。
[Codexのプロジェクトとチャット](https://learn.chatgpt.com/docs/projects)

```bash title="Codex CLI 이전 세션 재개"
codex resume
```

どの方法でも、正しい作業ディレクトリとチャットを選んだかを確認します。
「続けて」とだけ伝える代わりに、現在の記録と実際のコードを照合してから残りの作業を進めるように依頼できます。

### 会話の圧縮

同じ作業を続けていて、会話だけが長くなった場合は圧縮を検討できます。
Claude Codeには自動圧縮と `/compact` があり、保持する内容を指示することもできます。
[Claude Codeのコンテキスト管理](https://code.claude.com/docs/en/best-practices)

```text title="Claude Code 세션의 압축 요청 예시"
/compact 목표와 제외 범위, 변경 파일, 검증 결과, 남은 판단을 보존
```

圧縮は現在の作業を続けるための機能です。引き継ぎ文書は、人が根拠を確認したり、別のセッションへ移したりするための記録です。
ツールごとの圧縮動作が同じとは限らないので、重要な状態は実際のファイルと併せて確認します。
関係のない作業に移るときは、必要な引き継ぎを残して別のセッションを始めると、文脈を管理しやすくなります。

## 新しいセッションへの依頼

会話を丸ごとコピーする代わりに、記録のパスと開始手順を伝えます。
以下の依頼では、引き継ぎファイルのパスと作業名を現在の環境に合わせて変更します。

```text title="작업 재개 요청"
docs/tasks/search-history-handoff.yaml을 읽고 작업을 이어가세요.
먼저 현재 경로, HEAD, 미커밋·미추적 변경을 기록과 대조하세요.
차이가 있으면 관련 파일을 확인해 현재 상태를 갱신하세요.
통과·실패·미실행 검사를 구분하고 결과의 적용 범위를 확인하세요.
다음 행동에 필요한 파일부터 읽고, 기존 목표와 제외 범위를 지키세요.
수정 뒤 관련 검증을 실행하고 인계 기록을 최신 상태로 바꾸세요.
```

新しいセッションが最初に読むファイル数を絞る場合でも、必要な依存関係は後から読めるようにします。
関係のない調査を繰り返す手間を減らし、必要な確認は行います。

<Rbox>
前回の記録にある「完了」や「テスト成功」を、現在のコードの証明として扱わないでください。
記録と実際の状態が食い違う場合は、記録をもとにコードを上書きする前に、何が変わったかを調べます。
</Rbox>

## 記録の有効期間

第2回の `AGENTS.md` と `CLAUDE.md` には、リポジトリで繰り返し適用するルールを置きます。
今回の失敗ログや次の行動まで共通ルールに追加し続けると、どの作業でも同じ古い文脈を読むことになります。
情報がいつまで有効かに応じて、保存場所を分けます。

| 情報 | 適した場所 | 更新の基準 |
| --- | --- | --- |
| 共通ルールと検証コマンド | リポジトリの指示 | ルールや環境の変更時 |
| 今回の作業の現在の状態 | 作業ごとの引き継ぎ文書 | 段階の移行、中断、再開時 |
| 失敗時の詳細な出力 | ログとテストの生成物 | 実行結果ごとに保存 |
| 最終設計と使い方 | 正式な文書やPRの説明 | 実装と合意事項の反映時 |

完了した作業の引き継ぎ文書は、進行中の作業一覧から外すか、完了済みとして整理します。
次の作業で、古い未完了の指示を現在の依頼と取り違えないようにします。
再利用できる結論だけを正式な文書や共通の指示に移します。

<Bbox>
引き継ぎの質は、文書の長さより、次のセッションが何を確認し直したかで判断してみてください。
済んだ調査を繰り返したか、未完了の作業を見落としたか、現在のコードと異なる記録が原因で手戻りが起きたかを確認します。
</Bbox>

## まとめ

AIとの作業を続けるには、短い会話の要約と併せて、コードの状態と確認の根拠を残します。
目標、変更範囲、未コミットのファイル、検証結果、次の行動を記録し、再開時に実際の状態と照合します。

<br/>

**記録を読む → コードの状態を照合する → 根拠を確認する → 次の行動を実行する**という順序を、作業再開の手順にしてみてください。
第11回では、この記録と作業範囲をもとに、複数の作業を並行して進め、結果を統合する方法を扱います。
