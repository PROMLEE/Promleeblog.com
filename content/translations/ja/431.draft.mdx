## はじめに

コーディングエージェントに複数のスキルやMCPサーバーを接続すると、使っていない機能まで毎回コンテキストを占めるように思えます。
実際の費用は、**いつ何が読み込まれるか**によって変わります。
スキルの短い説明、MCPツールの定義、ツールを呼び出した後に受け取る結果は、それぞれ異なる情報です。
これらをまとめて扱うと、削減すべき箇所を見誤ります。

<br/>

この記事では、SkillとMCPの読み込み経路を分け、実際の作業でどの部分を先に確認するかを整理します。

## 読み込みの段階

> コンテキストを節約するには、必要な情報を、必要になる段階で渡します。

Skillは繰り返し作業の**手順**を提供し、MCPは外部データを参照する**実行ツール**を提供します。
OpenAIのドキュメントによると、モデルは最初にSkillの名前と説明を読み、依頼に合う場合に指示の全文を読みます。
MCPサーバーはツールとデータへのアクセスを提供し、Skillはそれらのツールをどの順番と基準で使うかを案内します。
[OpenAI DevelopersのSkillとMCPの役割](https://developers.openai.com/plugins/concepts/skills)

| 段階 | Skill | MCP |
| --- | --- | --- |
| 発見 | 名前と説明で適合性を判断 | サーバーとツールの説明から機能を探す |
| 選択 | `SKILL.md` と必要な参照文書を読み込む | 必要なツール定義を読み込む |
| 実行 | 指示に従って作業を行う | ツールの呼び出し結果をコンテキストに加える |

**ツール定義の読み込みを遅らせることと、呼び出し結果を小さくすることは、別々の最適化です。**
定義を絞っても、一度の検索結果が長すぎれば、コンテキストはまた大きくなります。

## Skillを設計する

Skillの説明は、*どのような依頼でこのスキルを使うか*を伝える短い案内です。
説明が曖昧だと、モデルが不要なスキルを読んだり、必要なスキルを見逃したりします。
OpenAIは、説明を明確かつ短く書き、詳しい手順や例は必要なときに読む参照ファイルに分けるよう勧めています。
[OpenAI Developersのスキルのコンテキスト設計](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

```text title="skills/review-pr/"
review-pr/
├── SKILL.md
├── references/
│   ├── security.md
│   └── performance.md
└── scripts/
    └── summarize-diff.sh
```

例えばPRレビューの依頼では、`SKILL.md` がレビューの順序と出力形式を示します。
セキュリティの変更なら `references/security.md`、パフォーマンスの変更なら `references/performance.md` を読みます。
すべてのレビューで両方を読むよう指示すると、小さな文言変更でも同じ費用がかかります。

```yaml title="skills/review-pr/SKILL.md"
---
name: review-pr
description: PR의 코드 변경을 리뷰하고, 동작 오류와 검증 누락을 찾을 때 사용합니다.
---

변경된 코드와 관련 테스트를 확인합니다.
인증·권한 변경이면 references/security.md를 읽습니다.
성능 경로 변경이면 references/performance.md를 읽습니다.
```

<Ybox>参照ファイルを分けても、SKILL.mdに「作業前にreferencesをすべて読む」と書けば、読み込み量は減りません。読む条件も併せて書きます。</Ybox>

## MCPツール

MCPは、外部システムの機能をツールとして公開します。
ツールが多いと、名前、説明、入力スキーマなどの定義がコンテキストを占める場合があります。
OpenAIのTool Searchドキュメントでは、大きなツール一覧から必要なときに定義を読み込むと、トークン使用量を減らせると説明しています。
ただし検索の段階が増え、使える設定は実行環境によって異なります。
[OpenAI DocsのTool Searchガイド](https://developers.openai.com/api/docs/guides/tools-tool-search)

<br/>

Claude Codeも、MCPツール検索によって定義を遅延読み込みし、ツール名とサーバーの指示を先に確認して、必要なツールを探す方法を文書化しています。
[Claude CodeのMCPツール検索ドキュメント](https://code.claude.com/docs/en/mcp)

<br/>

実務では、次の順番で確認します。

- よく使うツールと、めったに使わないツールを分けます。
- サーバーやツールの名前と説明に、実際の利用条件を記載します。
- 実行環境で利用できるツール検索や、許可するツールの設定を確認します。
- ツールの呼び出し結果から、不要な本文やフィールドを減らします。

例えば「今回のPRで失敗したCIだけを確認する」なら、ビルドログ全体よりも、失敗したジョブ名、エラーメッセージ、関連ログへのリンクが先に必要です。
詳しいログは原因を絞ってから取得すると効率的です。

<Rbox>ツール定義を遅延読み込みしても、外部サーバーのレスポンスは自動で小さくなりません。トークンの削減効果は、ツール一覧と呼び出し結果の両方で確認します。</Rbox>

## 選ぶ基準

SkillとMCPのどちらを追加するか迷ったら、必要な情報の性質で判断します。

| 必要なもの | 適した場所 | 例 |
| --- | --- | --- |
| 繰り返し使える手順 | Skill | PRレビューの手順と出力形式 |
| 作業に応じて選ぶ詳細な指示 | Skillの参照ファイル | セキュリティレビューのチェックリスト |
| 現在の状態の参照・操作 | MCPツール | CI結果の取得、Issue作成 |
| リポジトリ全体の共通ルール | `AGENTS.md` | テストコマンド、変更範囲 |

例えば「CIが失敗した原因を分析する」作業では、スキルとMCPサーバーを一つずつ組み合わせられます。
スキルは分析手順を定め、MCPは現在のCI結果を取得します。
役割を分けると、固定された手順を毎回外部から長い文章として取得したり、リアルタイムのデータをスキルファイルにコピーしたりせずに済みます。

## 確認方法

設定を変更したら、費用と品質が実際に改善したかを確認します。
単純な作業、外部データを必要とする作業、複数の工程がある作業を一つずつ選び、同じ条件で比較します。

- 新しいセッションで、既定で表示されるSkillの説明とMCPツールの定義を確認します。
- 作業中に実際に読み込んだSkillの本文と参照ファイルを記録します。
- 呼び出したツール、レスポンスの大きさ、入力トークン、総所要時間を比較します。
- 正答率が下がったり、検証の漏れが増えたりしていないかも確認します。

**トークンが減っても、必要なツールを見つけられないなら、最適化は失敗です。**
作業完了率と応答時間も併せて見ます。
OpenAIのドキュメントも、ツールの読み込み方式を選ぶ際に、代表的な作業で完了率、入力トークン、遅延を比較するよう勧めています。
[OpenAI Docsのツール読み込み戦略](https://developers.openai.com/api/docs/guides/tools-tool-search)

## まとめ

SkillとMCPのコンテキスト費用は、インストール数だけでは判断できません。
**説明メタデータ → 指示の全文・ツール定義 → 呼び出し結果**の順に、実際に入る情報を確認します。

<br/>

Skillには短い説明と必要時に読む参照文書を置き、MCPには探しやすいツール説明を付け、必要な範囲の結果だけを返すようにしてみてください。
