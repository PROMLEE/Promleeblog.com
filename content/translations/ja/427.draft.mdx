## はじめに

AIコーディングエージェントを使い続けると、*費用*はモデルの選択だけでなく、作業の進め方でも大きく変わることが分かります。
同じ機能でも、必要なファイル（`필요한 파일`）だけを読んで一度でテストを通すこともあれば、リポジトリ全体（`저장소 전체`）を調べ、何度も修正した末にやり直すこともあります。
差が出るのは、入力トークン、ツールの呼び出し回数、待ち時間、開発者が見直す時間です。積み重なるほど、その差を実感します。

<br/>

*コンテキストエンジニアリング*とは、**現在の作業に必要な情報を、適切な順番で提供すること**です。
作業を正確に終えるための情報を選び、次の作業でも再利用できるよう状態を残します。
この原則は、Claude CodeやCodexなど、AIコーディングエージェントに共通して適用できます。

<br/>

この記事では、トークンの使用量と手戻りを減らす実務の流れを扱います。
<Bbox>会社から提供されるエージェントの利用枠に今は余裕があっても、トークンと手戻りを減らす習慣があれば、急な方針変更やモデルの切り替えに対応しやすくなります。</Bbox>

## トークンを節約する原則

> プロンプトが短くても、消費するトークンが少ないとは限りません。

情報が足りないと、エージェントは不要なファイルまで調べたり（`더 많이 탐색`）、誤った仮定に基づいて修正とテストを繰り返したり（`수정과 테스트를 반복`）します。
一方、設計文書やログを一度にすべて渡すと、重要な指示が埋もれ、入力の費用も増えます。

### トークンを余計に使う要因

- **不要なリポジトリ調査**
  作業に関係のないファイルを読むことで、コンテキストが膨らみます。
- **重複したリポジトリの指示**
  AGENTS.md、CLAUDE.md、READMEで同じルールが繰り返され、作業のたびに読み込まれます。
- **大きすぎるツール出力**
  テストログ全体、APIレスポンス全体、ビルド成果物をそのまま渡してしまいます。
- **検証を伴わない修正**
  修正範囲と完了条件が曖昧なため、同じファイルを何度も直します。

トークン使用量は費用の指標で、手戻りの回数は品質の指標でもあります。
*トークンが少なくても、手戻りが多ければ、効率のよい作業とは言えません。*
作業の効率を見るときは、入出力トークンに加え、ツールの呼び出し回数、失敗したテスト数、人が取り消した変更数も記録すると、改善につなげられます。

### 測定する指標

最初から大がかりな計測システムを作る必要はありません。
同じ種類の作業を三つ選び、次の項目を記録するだけでも、改善の効果を確認できます。

| 測定項目 | 問題の兆候 | 改善の目標 |
| --- | --- | --- |
| 読んだファイル数 | 作業範囲より大幅に多い | 変更に必要なファイルに絞る |
| ツールの呼び出し回数 | 同じコマンドを繰り返す | 調査と検証のコマンドをあらかじめ明記する |
| テストの再試行 | 原因が分からないまま繰り返す | 失敗ログの関連部分だけを渡す |
| 修正したファイル数 | 小さな機能で広い範囲が変わる | 変更可能な範囲を依頼に含める |
| 人によるレビュー時間 | 意図を読み解き直す必要がある | 完了条件と検証結果を一緒に残す |

## 作業範囲

機能名だけを伝えると、エージェントは必要なファイルと完了基準を自力で推測します。
<Bbox>プロジェクトフォルダーを渡して「この機能を直して」とだけ頼むと、エージェントは文書全体を調べ、トークンを消費します。</Bbox>
簡単な作業では問題が見えなくても、リポジトリが大きくなるほど調査範囲と仮定が増えます。
**先に作業範囲と完了条件を決めること**が、少ない手間でエージェントの費用を抑える方法です。

### 作業依頼テンプレート

以下のテンプレートは、チャット、Issueの本文、自動化パイプラインの作業指示に使えます。

```text title="agent-task-template.txt"
목표
- 게시글 목록 API에 페이지네이션을 추가합니다.

수정 범위
- src/app/api/posts/route.ts
- src/lib/posts/query.ts
- 관련 테스트 파일

완료 조건
- page와 limit이 없을 때 기존 응답과 호환됩니다.
- 잘못된 쿼리는 400 응답을 반환합니다.
- npm test와 npm run lint가 통과합니다.

금지 사항
- 데이터베이스 스키마와 공개 응답 필드는 변경하지 않습니다.
- 지정한 범위 밖 리팩터링은 하지 않습니다.

작업 방식
- 수정 전에 관련 파일만 읽고 변경 계획을 세웁니다.
- 완료 후 수정 파일과 검증 결과를 짧게 요약합니다.
```

この形式では、*実装の細かな手順を指定しすぎない*ようにします。
問題をどう解くかはエージェントに任せ、読む範囲と成功の判定基準は人が決めます。

### 作業を分ける基準

一つの作業が複数の境界をまたぐなら、分割を検討します。
例えば認証、DBマイグレーション、画面変更を一つの依頼に入れると、どの変更が失敗の原因か切り分けづらくなります。
次の順番で分けると、必要なコンテキストも小さくなります。

- 調査段階（`조사 단계`）では、関連するパスと現在の挙動だけを確認します。
- 実装段階（`구현 단계`）では、確定したファイルとテストだけを扱います。
- レビュー段階（`리뷰 단계`）では、差分と検証結果だけを確認します。

こうして分けると、前の段階の長い調査ログをすべて引き継ぐ必要はありません。

## リポジトリの指示

`AGENTS.md` と `CLAUDE.md` は、チームのルールを伝えるのに役立ちます。
ただし、過去の経緯や例外を一つのファイルに蓄積すると、小さな修正でも無関係な指示を読み込むことになります。
指示ファイルは、作業に合う文書とコマンドに案内する*ルーター*として使います。

### 最小限の指示

ルートの指示には、次のように、ほとんどの作業に共通する内容だけを置きます。

```md title="AGENTS.md"
 # 프로젝트 공통 규칙

- 패키지 설치는 npm을 사용합니다.
- 변경 후 npm run lint와 npm test를 실행합니다.
- API 응답 형식 변경은 요청에 명시된 경우에만 허용합니다.
- 데이터베이스 변경은 prisma/schema.prisma와 migration을 함께 검토합니다.

 # 작업별 안내

- 인증 작업은 docs/auth.md를 읽습니다.
- 배포 작업은 docs/deploy.md를 읽습니다.
- 데이터베이스 마이그레이션은 docs/database-migrations.md를 읽습니다.
```

認証やデプロイなど、一部の作業だけに必要な詳しい手順は、別の文書に置きます。
エージェントは該当する作業のときだけ文書を読み、毎回すべての指示を読み込まずに済みます。

<br/>

OpenAIの公式ドキュメントも、長すぎたり重複したりする `Skill` の説明や、過剰なリポジトリの指示がコンテキストを使い、必要な指示を選びにくくする場合があると説明しています。
[OpenAI Docs — Skillsとプロンプトの再設計](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

### 指示から外せる内容の例

- package.jsonのスクリプトで確認できる長いコマンド一覧。
- Gitの履歴で参照すれば足りる過去の判断記録。
- 特定の機能やフォルダーだけに適用する細かいルール。
- 複数の文書で繰り返されるコードスタイルのルール。

削除する前に、失ってはいけない情報を別の文書へ移します。ルートの指示にはリンクと適用条件を残します。

## 作業の状態

長い作業で会話履歴をすべて維持すると、過去の調査結果と失敗ログがコンテキストを占め続けます。
作業状態を*短いファイル*に残しておくと、新しいセッションで必要な事実だけを読んで再開できます。

### 状態を記録する文書

状態文書は短くて構いません。
以下の情報があれば、新しいエージェントや別のメンバーが引き継げます。

```md title="docs/agent-state/pagination.md"
 # 게시글 페이지네이션 작업 상태

 ## 완료
- 기존 목록 API의 응답 구조를 확인했습니다.
- page와 limit의 기본값을 합의했습니다.

 ## 남은 작업
- query.ts에 범위 검증을 추가합니다.
- route 테스트에 잘못된 limit 사례를 추가합니다.

 ## 검증 명령
- npm test -- posts
- npm run lint

 ## 결정 사항
- 기존 클라이언트 호환성을 위해 total 필드는 추가하지 않습니다.
```

このファイルは、プロジェクトの*判断を記録する文書*です。
作業後は削除するか、重要な判断だけを `ADR` やIssueに移します。

<br/>

Claudeの公式ガイドも、複数のコンテキストウィンドウにまたがる作業では、最初にテストと設定を用意し、後の段階で構造化した状態を活用する方法を推奨しています。
[Anthropic Prompting Best Practices](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/prompt-templates-and-variables)

### 新しいセッションを始める基準

次の場合は、前の会話をそのまま続けるより、新しいセッションを始めたほうが効率的です。

- 調査が終わり、実装範囲が確定した。
- エラーログが長くなり、失敗した試行が積み重なった。
- 担当する機能が変わり、以前のファイル一覧が役に立たなくなった。
- レビューだけが残り、実装中の会話の詳細が不要になった。

新しいセッションの最初の依頼には、作業状態のファイル、変更ファイルの一覧、検証コマンドを渡します。
コンテキストを整理しながら、人が決めたことも引き継げます。

## ツールの出力と検証

エージェントがターミナルやMCPツールを使うときは、コマンド自体よりも結果の出力で多くのトークンを使います。
ビルドログやテーブル一覧をすべて読ませるより、次の判断に必要な結果だけを返すようにします。

### ツールの出力

ファイルを探すときは、全文を表示する前に、パスと検索結果を絞ります。

```bash title="terminal-workflow.sh"
 # 필요한 경로를 먼저 찾습니다.
rg --files src | rg 'posts|pagination'

 # 관련 심볼이 있는 줄만 확인합니다.
rg -n 'getPosts|page|limit' src/app src/lib

 # 확정한 파일만 읽습니다.
sed -n '1,220p' src/lib/posts/query.ts
```

テストに失敗したときも、ログ全体を読む前に、失敗したテスト名、エラーメッセージ、関連するスタックフレームを確認します。
それでも原因が不明な場合に、出力範囲を広げます。

### 検証ループ

トークンを節約するためにテストを省くと、結果的に手戻りが増えます。
作業の完了条件に合う最小限の検証を先に実行し、最後に全体の検証を行います。

```text title="verification-order.txt"
1. 변경한 함수의 단위 테스트를 실행합니다.
2. 변경 경로의 타입 검사와 린트를 실행합니다.
3. 영향 범위가 확인되면 전체 테스트를 실행합니다.
4. 수정 파일과 테스트 결과를 diff와 함께 검토합니다.
```

Codexでは `/status` で、現在のセッションのモデル、コンテキスト使用量、トークン使用量を確認できます。
作業前後の値を記録すると、どの指示と作業手順が実際に役立ったかを判断できます。

## チームのチェックリスト

✓ 作業依頼に、目標、修正範囲、完了条件、禁止事項を書く。
✓ ルートのAGENTS.mdまたはCLAUDE.mdには、共通ルールと文書のパスを残す。
✓ 長いログや大きなレスポンスは検索や要約で絞り、必要な部分を読む。
✓ 調査、実装、レビューなど、必要なコンテキストの異なる段階は別セッションに分ける。
✓ 作業状態と検証コマンドは、リポジトリの短い文書に残す。
✓ 小さなテストから実行し、最後に全体の検証と差分レビューを行う。
✓ 1か月間に三つの作業を選び、読んだファイル数、テストの再試行、レビュー時間を比べる。

## まとめ

ClaudeやCodexのトークンを節約するには、エージェントが適切なファイルを読み、必要なツールだけを呼び出し、一度の修正で検証まで進める作業環境を設計します。

<br/>

作業依頼を契約のように書く、リポジトリの指示を作業別の文書に分ける、状態をファイルに残す。この三つから試してみてください。
