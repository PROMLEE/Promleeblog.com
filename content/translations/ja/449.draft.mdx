## はじめに

メンバーごとにAIの使い方が異なると、PRに残る情報にもばらつきが出ます。
変更理由とテスト結果が明確なPRもあれば、「AIで実装し、動作しています」とだけ書かれたPRもあります。
コードはすぐにできても、レビュー担当者は要件を探し直し、検証コマンドを確認することになります。

<br/>

このシリーズでは、必要な文脈を伝え、モデルを選び、結果を検証する方法を個別に取り上げました。
最終回では、これらの手法を**次の担当者が判断できる根拠が引き継がれる開発フロー**にまとめます。
例にするのは、既存サービスに検索語とステータスのフィルターを追加する作業です。
文書と結果は適用方法を示す例であり、特定のプロジェクトでの実行結果や生産性の測定値ではありません。

## 作業を始める

> 実装を依頼する前に、何をもって完了と判断するかを決めます。

「検索を改善して」ではなく、利用者の操作と期待する結果を書きます。
今回の完了条件は、検索語とステータスフィルターがURLに反映され、再読み込みやブラウザーの「戻る」の後も、画面がその値を復元することです。
結果が0件の場合とエラーの表示も含めます。並べ替えルールとDB構造の変更は対象外です。

<br/>

作業責任者がこの条件と変更範囲を確定します。
AIは既存コードの制約や選択肢を調べて説明できます。製品の挙動が変わる選択を独断で確定しないよう、依頼に判断基準を記載します。
既存の要件で判断できる実装上の選択は、その範囲内で進めます。

```yaml title="docs/tasks/search-filter.yaml"
task_id: search-filter
goal: 검색어와 상태 필터를 URL과 동기화
acceptance:
  - 검색 시 q와 status가 URL에 반영됨
  - 새로고침 뒤 URL과 화면 필터가 일치함
  - 뒤로 가기 뒤 이전 필터가 복원됨
  - 빈 결과와 API 오류를 구분해 표시함
scope:
  include:
    - 검색 폼과 상태 처리
    - 기존 검색 API의 필터 처리
    - 관련 테스트
  exclude:
    - 정렬 규칙 변경
    - DB 구조 변경
contract: docs/contracts/search-filter.md
verification:
  - 저장소에 정의된 타입 검사
  - 필터 파싱과 API 계약 테스트
  - 실제 브라우저의 새로고침과 뒤로 가기
```

このファイルはツールが自動実行する設定ではありません。
依頼文でファイルのパスを伝え、実際のリポジトリのコマンドと文書に合わせて書きます。
小さな修正には必要な項目だけを使います。

<Bbox>
チームで最初に試すなら、繰り返し発生し、結果を確認しやすい作業を選んでください。
まず既存パターンがある機能一つで、依頼、検証、レビューの流れをそろえます。大規模なプロジェクトでは完了基準が曖昧になりがちです。
</Bbox>

## 各段階で残す根拠

作業を依頼、契約、実装、検証、レビューの順につなぎます。
各段階を終えたら、次の段階で使える根拠を残します。
工程全体を測定し、結果を次の作業の改善に使います。

<Img src="/261015-120002.webp" width={650} height={433} alt="依頼・契約・実装・検証・レビューをつなぎ、完了率・手戻り・時間・費用をもとに改善するチームのAI開発サイクル"/>

| 段階 | 判断すること | 次の段階に残すもの |
| --- | --- | --- |
| 依頼 | 目標と完了条件は明確か？ | 作業仕様と対象外の範囲 |
| 契約 | 画面とAPIは同じ挙動を前提としているか？ | パラメーター、レスポンス、エラー処理の基準 |
| 実装 | 必要な情報と変更箇所は何か？ | コード、変更理由、未決の事項 |
| 検証 | 最終コードは完了条件を満たすか？ | 実行コマンド、結果、未検証の範囲 |
| レビュー | 意図と回帰のリスクを確認したか？ | レビュー結果と対応事項 |

Claude Codeの公式ドキュメントも、調査、計画、実装を分け、テストや期待する結果など、確認可能な基準を示すよう推奨しています。
[Claude Codeのベストプラクティス](https://code.claude.com/docs/en/best-practices)

小さな作業なら、短い調査からそのまま実装に進めます。
段階ごとに長い報告書や会議を設けるより、必要な判断と根拠を漏れなく残すために使います。

## 文脈と契約

AIが最初に読む情報を、共通ルール、関係するエントリーポイント、今回の作業仕様に絞ります。
検索画面のエントリーファイル、既存のAPIルート、テストコマンドの記載箇所を伝えると、リポジトリ全体を調べ直す手間が減ります。
追加の依存関係は、実際に必要になった時点で調べるように伝えます。

<br/>

第2回の `AGENTS.md` と `CLAUDE.md` には、リポジトリで繰り返し適用するルールを書きます。
第4回の作業依頼には今回の機能の目標と範囲を、第10回の引き継ぎ文書には作業中の状態を書きます。
有効な期間の異なる情報を、一つのファイルに積み上げ続けないようにします。

### 検索の契約

画面とAPIで共有する基準を先に決めます。
例えば、ステータスフィルターの許可値、空の検索語の扱い、レスポンスのフィールド、エラー時の状態を文書に残します。
フロントエンドが送るパラメーターと、サーバーが読み取るパラメーターを、実際のコードで確認します。

```text title="docs/contracts/search-filter.md"
입력: q는 검색어, status는 all 또는 active 또는 archived
빈 q: 검색어 제한 없이 상태 필터만 적용
status 누락: all로 처리
성공: HTTP 200, items 배열과 nextCursor 반환
잘못된 status: HTTP 400, INVALID_QUERY 오류 반환
빈 결과: HTTP 200, items는 빈 배열
URL 복원: 누락된 status도 화면에서는 all로 표시
```

この契約は説明用に選んだ挙動です。
既存サービスに別の基準があれば、その基準に従うか、変更について合意してから反映します。
型宣言に加え、実際のリクエストとレスポンスが同じ契約を守っているかも確認します。

## モデル選択と実装

既存パターンに沿ったフィルターの実装なら、第6回の基本ルートから始められます。
再現できない状態の不具合や、複数の層にまたがる原因分析が必要になったら、情報不足や環境の問題を先に確認してから、モデルや推論の強度を調整します。
テストの失敗を一律にモデルの性能の問題と見なさないようにします。

<br/>

第5回のSkillは繰り返し使う手順と基準に、MCPは必要な外部の状態を確認するために使います。
第9回のキャッシュは、実際に繰り返し入力がある場合に効果を測って適用します。
費用の最適化を理由に、今回の機能に不要なツールや文書まで加える必要はありません。

### 並列化の判断

検索の契約と担当ファイルが固まっていれば、画面とAPIの実装を並行して進められます。
契約が変わっている途中なら、先に確定してから分担します。
並列化する場合は、第11回のように作業領域と変更の責任を分け、統合後に全体がつながって動くことを確認します。
小さな機能なら、一つのセッションで順番に実装したほうが、引き継ぎや統合の手間を減らせることもあります。

## 検証と手戻り

第7回の検証ループを、今回の完了条件に結び付けます。
フィルターの解析は単体テストで、APIの入出力は契約テストで、戻る操作と再読み込みはブラウザーの挙動で確認します。
大切なのは、どの完了条件を確認できたかです。

| 完了条件 | 確認方法の例 |
| --- | --- |
| q・statusの反映 | リクエストパラメーターとURLを確認 |
| statusがない場合の既定値 | 解析の単体テストとAPIテスト |
| 結果0件とエラーの区別 | 画面の状態をテストし、実際のレスポンスを確認 |
| 戻る操作・再読み込み後の復元 | ブラウザーE2E、または手動再現の記録 |

OpenAIの反復修正の例でも、レビュー、修正、検証をつなぎ、残った失敗を次の修正への入力として渡す流れを説明しています。
[OpenAIの反復修正ループ](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex)

<br/>

失敗した場合は、観測した事実と仮説を分け、次の行動を選びます。
URLは変わるのに入力欄の値が変わらないなら、その再現結果を記録して状態の更新経路を調べます。
テストサーバーが起動しなかったなら、実行環境から確認します。
要件同士が衝突している場合は、作業責任者が決めるべき事項を整理します。

<Rbox>
検証を通すために完了条件を緩めたり、例外の検査を削除したりしないでください。
要件が変わった場合は、変更理由と新しい基準を先に記録し、その基準で再検証します。
</Rbox>

### 中断と引き継ぎ

新しい根拠がないまま同じ失敗への修正を繰り返している場合は、原因分析に戻ります。
現在の作業パスとコミット、未コミットの変更、成功・失敗・未実行の検査、次の行動を記録します。
次のセッションでは、記録と実際のコードを照合してから作業を続けます。
モデルを替えたりセッションを開き直したりしても同じ作業番号を使えば、再試行の費用を一つの作業として集計できます。

## レビューと完了

レビュー担当者は、AIの説明に加え、実際の変更と検証の根拠を確認します。
作業責任者は目標と範囲を確認し、実装担当者は変更内容と実行結果を確認し、レビュー担当者は変更の意図と抜け漏れを判断します。
実装担当者がAIを使う場合も、チームが定めた完了責任を明確にします。

<Img src="/261015-120003.webp" width={650} height={433} alt="作業責任者・実装担当者・レビュー担当者が行う判断と、残すべき根拠を比較した役割表"/>

小さなチームでは、一人が複数の役割を兼ねる場合があります。
その場合も、実装時の説明をそのまま承認するのではなく、完了条件と変更ファイルを基準に見直します。
使ったモデルは運用記録に残し、PRにはレビューに必要な変更理由と根拠を中心に書きます。

```text title="PR 설명 예시"
문제: 검색 필터가 URL에 남지 않아 공유·새로고침 시 조건이 사라짐
변경: q·status 직렬화와 URL 변경에 따른 화면 상태 복원
범위: 검색 폼, API 필터 처리, 관련 테스트
검증: 타입 검사, 파싱·계약 테스트, 브라우저 복원 시나리오
미검증: 실행 환경이 없는 브라우저는 별도로 표시
제외: 정렬 규칙과 DB 구조는 변경하지 않음
작업 기록: docs/tasks/search-filter.yaml
```

上の内容は報告形式の例です。
実際のPRには、実行したコマンド、実行結果、対象のコードの状態を確認できるリンクやログを添えます。
レビューを受けて修正した後は、影響する検査を再実行します。

<br/>

開発完了、マージ、デプロイは、チームの定義に沿って区別します。
この例のように検証とレビューの通過を作業完了とした場合、報告でもその段階を示します。
デプロイまで作業範囲に含まれるなら、既存のデプロイ手順とデプロイ後の確認の根拠を残します。

## 記録と改善

繰り返す作業を改善するには、結果に加え、どこに時間がかかったかを残します。
第8回の完了率、人による手戻り、総所要時間、総使用量を作業番号にひも付けます。
APIを使った場合は実際の料金の基準を、サブスクリプション型のツールを使った場合は確認できる使用量と上限を記録します。

<br/>

OpenAIの定型業務の自動化事例でも、作業の文脈を整理し、実行結果を記録し、前回の実行から学んだことを次に生かす方法を紹介しています。
[OpenAIの定型業務ワークフロー事例](https://developers.openai.com/blog/automating-repetitive-work-at-openai-with-codex)

レビューでAPIのフィールドに関する誤解が繰り返されるなら、契約文書を改善します。
同じ箇所を探す作業が何度も発生するなら、エントリーポイントの案内を補います。
検証の待ち時間が長ければ、実際のボトルネックを調べ、関連する検査を先に実行するようにします。
モデル、指示、検証方法を一度に変えると違いを切り分けにくくなるので、変数を一つ調整し、同じ条件で比較します。

<Ads3/>

<Bbox>
毎週繰り返す問題を一つ選び、共通ルールや作業テンプレートを変えてみてください。
共通ルールには各作業の失敗ログをすべて転記せず、次回も必要な短いルールと、根拠の参照先を残します。
</Bbox>

## シリーズの適用順序

全12回の手法を最初からすべて取り入れる必要はありません。
チームで繰り返し起きる問題に合わせて必要な部分から適用し、測定結果を見ながら広げます。

| チームで繰り返す問題 | 先に取り入れること | 関連回 |
| --- | --- | --- |
| AIが関連ファイルを探すのに時間がかかる | 最小限の指示とリポジトリのエントリーポイント | 第1〜3回 |
| 結果が依頼と異なる | 作業範囲、完了条件、契約 | 第4回 |
| 文書とツールを読み込みすぎる | SkillとMCPを必要なときに読み込む | 第5回 |
| 作業ごとの費用と待ち時間のバランスが悪い | モデルと推論強度の選択 | 第6回 |
| テスト通過後も手戻りが発生する | 再現、検証、完了の根拠 | 第7回 |
| 改善の効果を判断しにくい | 作業単位の指標と比較 | 第8回 |
| 同じ入力を繰り返し処理する | キャッシュの読み書きと総費用の確認 | 第9回 |
| セッションを替えると文脈が途切れる | コードの状態と引き継ぎ記録 | 第10回 |
| 並行作業の結果を統合すると問題が出る | 担当範囲、作業領域の分離、統合後の検証 | 第11回 |

すぐに始めるなら、作業仕様を一つ用意し、リポジトリで実際に使う検証コマンドと完了報告の形式をそろえます。
この三つが運用に乗れば、モデルの振り分けや並列化も、同じ完了条件で比較できます。

## まとめ

チームでのAI開発は、目標と変更範囲を決め、必要な情報を伝え、コードと実行の根拠を確認する流れです。
作業ごとの記録と指標を結び付けると、すぐに生成できたコードが、実際に完了した機能につながったかを確認できます。

<br/>

全12回で共通するのは、**次の判断に必要な情報を残し、実際の結果で確かめること**です。
繰り返し発生する小さな作業からこの流れを使い、完了率と人による手戻りがどう変わるかを見ながら、チームに合わせて調整してみてください。
