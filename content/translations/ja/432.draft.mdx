## はじめに

ボタンの文言を変える作業と、ログインセッションがときどき切れる問題を、同じモデル、同じ推論強度で処理していませんか？
文言の修正は変更箇所が分かれば終わりますが、セッションの問題では、Cookie、サーバーレンダリング、リダイレクトが絡む原因を調べる必要があります。
両方に同じ設定を使うと、小さな修正では待ち時間が延び、複雑な問題では誤った修正を繰り返すことがあります。

<br/>

**モデルルーティングは、作業に合うモデルと推論強度を選び、必要に応じて切り替えるルールです。**
大がかりな自動分類システムから始める必要はありません。
一人で開発するなら、作業開始前にモデルを選ぶ基準と、行き詰まったときに設定を変える基準があれば十分です。
この記事では、Claude CodeとCodexで使える選択基準、設定例、上位モデルへの切り替え、費用比較を整理します。

## 作業の分類

> ファイル数より重要なのは、正しい結果がどれだけ明確か、誤った修正がどこまで影響するかです。

変更先が1ファイルでも、簡単な作業とは限りません。
権限チェックの1行がサービス全体に影響することもあれば、20ファイルのimportパス変更が決まったルールで処理できることもあります。
作業を受けたら、まず三つの問いに答えてみてください。

- **正しい結果は何か？**
修正前後の例と完了条件があれば、判断の負担は小さくなります。
- **どこまで影響するか？**
一つの画面で完結するか、API、DB、認証の境界も変えるかを確認します。
- **どう確認するか？**
型チェックで済むか、複数の状態やユーザー権限を再現する必要があるかを見ます。

この基準で作業を高速ルート、標準ルート、高性能ルートに分けます。
各ルートは特定モデルの固定ランクではなく、チームが検証して割り当てる役割です。

| ルート | 作業の条件 | 開発作業の例 | 開始時の設定 |
| --- | --- | --- | --- |
| 高速ルート | 正しい結果と修正箇所が明確 | ボタン文言の変更、import整理、再現済みの単純な型エラー | 軽量モデル、低い推論強度 |
| 標準ルート | 既存パターンを読み、実装方法を選ぶ | 検索フィルター追加、フォーム検証、APIレスポンス処理 | 主力モデル、標準の推論強度 |
| 高性能ルート | 複数の仮説、設計上の選択、リスクの検討が必要 | セッション消失の分析、並行処理の不具合、データ移行設計 | 判断力の高いモデル、必要に応じた推論強度 |

<Img src="/261003-060002.webp" width={650} height={433} alt="明確な修正は高速ルート、一般的な実装は標準ルート、複雑な判断は高性能ルートに振り分けるモデルルーティング"/>

OpenAIの公式ドキュメントでは、同じ入力でモデルと推論設定を比較し、必要な品質を満たす最も軽量な設定を選ぶよう案内しています。
[OpenAIのモデル選択ガイド](https://developers.openai.com/api/docs/guides/model-selection)

<Bbox>
最初は普段の主力モデルを標準ルートに置き、繰り返す単純な作業から高速ルートに移してみてください。
慣れていないリポジトリの作業まで一度に軽量モデルへ移すと、モデルの性能と作業情報の不足を切り分けにくくなります。
</Bbox>

## モデルと推論強度

モデルを変えることと、推論強度を変えることは別の選択です。
モデルを変えると基本能力と料金体系が変わり、推論強度を変えると、対応モデル内で推論に割く量を調整できます。
軽量モデルの推論強度を上げても、別の高性能モデルと同じ結果になるとは限りません。

<br/>

例えば既存のReactフォームに必須項目の検証を加えるなら、主力モデルの標準強度から始められます。
検証関数とエラーの表示箇所が明確になり、文言を整えるだけなら、低い強度でも処理できます。
一方、検証をどの層で行うか、サーバーとクライアントのエラー処理の契約をどう合わせるかを決めるなら、判断により多くの推論予算を割きます。

<Ybox>
モデルと推論強度を同時に変えると、結果が良くなった理由も悪くなった理由も分かりにくくなります。
同じ作業依頼と検証基準を保ち、一つずつ変えて比較します。
対応する推論レベルはモデルと製品によって異なるので、選択画面や公式設定ドキュメントで確認します。
</Ybox>

## Claude Codeの設定

Claude Codeでは、開始時に `--model` を指定するか、セッション内で `/model` を使ってモデルを選べます。
`sonnet` や `opus` などのエイリアスが指す実際のモデルと利用可否は、実行環境で確認します。
[Claude Codeのモデル設定](https://code.claude.com/docs/en/model-config)

```bash title="터미널에서 Claude Code 시작"
claude --model sonnet
```

作業中に複雑な原因分析が必要になったら、セッション内でモデルを切り替えられます。

```text title="Claude Code 세션"
/model opus
```

### 計画と実装

「構造を決める段階」と「決めた構造に沿って実装する段階」を分けるのも、ルーティングの一つです。
Claude Codeの `opusplan` は、計画モードでOpusを使い、実行モードでSonnetに切り替える方式です。
[Claude Codeのopusplan設定](https://code.claude.com/docs/en/model-config#opusplan-model-setting)

```bash title="계획과 구현 모델 분리"
claude --model opusplan
```

例えば検索機能を追加するなら、計画段階でURLクエリの構造、データの取得箇所、結果が0件の場合の扱いを決めます。
実装段階では、その決定に沿ってコンポーネントとテストを書きます。
計画に「サーバーで処理する」といった短い結論だけを残すと、実装するモデルが同じ問題を解き直すことになります。変更するファイル、入出力、検証条件まで記録します。

<br/>

段階を分けると、引き継ぎにもコストがかかります。
文言一つの修正に設計段階を設けると、節約できる時間より呼び出しと待ち時間が増える場合があります。
設計上の選択が必要な作業に適用します。

## Codexの設定

Codexではモデルと推論強度を個別に設定できます。
CLI設定の `model_reasoning_effort` に指定できる値は、選択したモデルとクライアントがサポートするレベルによって異なります。
[Codexの設定リファレンス](https://learn.chatgpt.com/docs/config-file/config-reference)

以下はCLIでモデルと推論強度を指定する例です。
モデルIDは現在のアカウントで利用できるものを選びます。

```bash title="Codex CLI 기본 작업"
codex --model gpt-6.1-sol --config model_reasoning_effort='medium'
```

```bash title="Codex CLI 복잡한 원인 분석"
codex --model gpt-6.1-sol --config model_reasoning_effort='high'
```

二つ目の例では、同じモデルの推論強度だけを上げています。
どの作業でこの変更が役立つかを先に比較し、それでも不十分なら別のモデルを検討できます。
アプリでは、モデルと推論レベルの選択画面で同じ基準を適用します。
この例は設定の指定方法を示しています。難易度に応じた選択ルールは、ユーザーが運用します。

## 失敗の原因と上位モデルへの切り替え

テストに失敗したからといって、すぐにモデルを変える必要はありません。
依存関係のインストール失敗、空の環境変数、誤った再現手順は、モデルの能力より実行条件の問題である場合があります。
まず失敗を分類し、その後でモデルや推論強度を引き上げる**エスカレーション**を判断します。

| 失敗の兆候 | 先に行うこと | 切り替えの判断 |
| --- | --- | --- |
| ファイルが見つからない | 実際のパスとエントリーポイントを伝える | パスを伝えても依存関係を繰り返し誤解するなら検討 |
| 要件が曖昧 | 期待する挙動と対象外の範囲を確定する | 製品上の判断が必要ならユーザーに確認 |
| テストを実行できない | 環境、コマンド、テストデータを点検する | 実行環境の問題だけでは切り替えない |
| 同じ修正が繰り返し失敗する | 失敗した入力と観測結果を固定する | 仮説を更新できないなら切り替える |
| 認証やデータの境界が見つかる | 影響範囲と検証手順を見直す | 判断に十分な予算を割き、人のレビューを入れる |

再試行の回数にも上限を設けます。
例えば「同じ再現ケースで2回修正しても原因を絞れなければ、状況をまとめて上位モデルに切り替える」というルールから始められます。
2回は製品側の仕様ではなく、チームで調整できる運用基準です。

<Rbox>
権限チェックの削除、テストの削除、例外の無視で失敗を消す修正は、上位モデルに切り替える前に止めます。
高性能モデルを選んだ場合も、認証、決済、データ変更のレビューと完了条件の確認は必要です。
</Rbox>

### 引き継ぎの要約

新しいセッションや別のツールに引き継ぐときは、会話を丸ごとコピーせず、作業の状態と確認の根拠をまとめます。
現在のコードやログを確認できるパスも残します。

```text title="handoff.md"
목표: 새로고침 뒤 검색 필터 유지
완료 조건: q와 status가 URL에서 복원되고 뒤로 가기도 동작
수정 파일: src/features/search/SearchForm.tsx
현재 변경: 초기값을 searchParams에서 읽도록 수정
통과: 타입 검사, 초기 필터 복원 테스트
실패: 뒤로 가기 후 입력값이 이전 상태로 돌아오지 않음
재현: 필터 A → 필터 B → 브라우저 뒤로 가기
관찰: URL은 A지만 입력값은 B로 남음
남은 판단: URL 변경과 로컬 입력 상태의 동기화 방식
제외 범위: API와 검색 결과 정렬은 변경하지 않음
```

上位モデルは、この情報を使ってURLとローカル状態の関係から確認できます。
済んでいるAPIの調査や最初の再現を繰り返す手間が減ります。

## 完了1件あたりの費用

ルーティングの効果は、初回の呼び出し料金より、**検証を通過した作業1件の総費用**で比較します。
軽量モデルで失敗して高性能モデルでやり直すと、最初の試行と引き継ぎの費用が加わります。

以下は試算用の例で、実際の料金やベンチマークではありません。
入力、出力、推論のトークンを金額に換算した呼び出し費用を、同じ単位で示します。

| ルート | 初回の試行 | 再試行・引き継ぎ | 上位モデルの実行 | 完了までの合計 |
| --- | --- | --- | --- | --- |
| 高性能モデルで始める | 10 | 0 | 0 | 10 |
| 軽量モデルで完了 | 2 | 0 | 0 | 2 |
| 軽量モデルの失敗後に切り替え | 2 | 1 | 10 | 13 |

上位モデルへの切り替え率が `p` なら、この例の平均費用は `2 + 11 × p` です。
実際には、上位モデルが先行する変更を利用して早く終える場合もあれば、誤った変更を戻すために時間がかかる場合もあります。
この式から一般的な節約率を求めず、実際の作業記録で計算します。

### 比較の記録

繰り返し発生する代表的な作業で標準ルートの基準値を取り、同じ初期コード、依頼、検証条件で別の設定と比較します。
最初は次の項目を記録すれば十分です。

- 作業の種類、開始時のモデルと推論強度
- 完了条件を満たしたか、切り替えた理由
- 再試行と上位モデルへの切り替えを含む総所要時間
- APIを使った場合の実際の使用量と課金基準に基づく費用
- 人が修正した時間とレビューで見つかった問題

サブスクリプション版のClaudeやCodexの利用上限を、APIのトークン単価でそのまま換算しません。
サブスクリプション環境では完了率、待ち時間、利用枠の消費量を比較し、API環境では実際の使用量と適用料金で費用を計算します。

<Bbox>
誤字修正、一般的な機能の実装、複雑な不具合の分析など、異なる作業タイプは分けて比べてみてください。
全体の平均だけを見ると、簡単な作業での費用削減が、難しい作業での手戻りを覆い隠すことがあります。
</Bbox>

## まとめ

モデルルーティングでは、正しい結果がどれだけ明確か、どの境界に影響するか、どう検証できるかを見て、開始時の設定を決めます。
繰り返す単純な修正から軽量なルートを試し、複雑な設計やリスクのある変更には判断の予算を十分に割きます。

<br/>

行き詰まったら、実行環境と作業情報を先に確認し、モデルの判断力が足りない場合に切り替えます。
**開始時の設定、切り替え基準、引き継ぎの要約、完了1件あたりの費用**を併せて記録すると、作業の完了までにかかる時間と費用をもとにモデルを選べます。
