<br/>
そう思うかもしれません。

このシリーズでは、*React*コンポーネントを堅牢にする方法と、テストコードがもたらす開発の楽しさを一緒に学びます。

## フロントエンドテストの役割

フロントエンドのテストでは、画面が表示されるかに加え、ユーザーがWebサイトで行う*操作*や得られる*体験*を検証します。

- **ユーザーの操作を検証する**
  「ログインボタンを押すと、読み込み画面が出てメインページへ移動するか」といったシナリオを検証します。
- **ビジネスロジックを確認する**
  「カートに入れた商品の合計に10%の割引が適用されるか」といった計算を確認します。
- **回帰テスト（Regression Test）**
  新機能を追加したときに、ユーザー登録など、すでに動いていた機能が壊れていないかを自動で確認します。

## ReactでTDDを使う理由

テストコードを先に書く*TDD（テスト駆動開発）*を、なぜ*React*で使うのでしょうか。

### 1. 自信を持ってリファクタリングできる

フロントエンドのコードはよく変わります。デザインが変わることも、コンポーネントを分割することもあります。
テストコードがなければ、変更するたびに「どこか壊れていないか」と不安になりながらブラウザを再読み込みすることになります。
テストがあれば、構造を大きく変えてもテストが通ることを確認でき、自信を持って変更できます。

### 2. 生きたドキュメントになる

ほかの人が作ったコンポーネントを使うとき、「propsには何を渡せばいいのか」と聞くことが減ります。
テストコードを読めば、どの状況でどう動くかが明確にわかるからです。

```javascript title="src/components/Button.test.js" showLineNumbers
// 이 테스트만 봐도 Button 컴포넌트의 주 사용법을 알 수 있습니다.
test('클릭하면 onClick 함수가 실행된다', () => {
  const handleClick = jest.fn();
  render(<Button onClick={handleClick}>저장</Button>);
  
  fireEvent.click(screen.getByText('저장'));
  
  expect(handleClick).toHaveBeenCalledTimes(1);
});
```

### 3. フィードバックが速い

ブラウザを開き、ログインし、画面を移動してボタンを押すには、思った以上に時間がかかります。
TDDの環境では、コマンド1つで何百もの機能を数秒で確認できます。開発も速く進みます。

## テストの対象範囲

では、何をテストすればよいのでしょうか。すべてをテストすることはできません。
*React*テストの大切な原則は、**ユーザーから見える動作をテストする**ことです。

- **テストすること（○）**
  - ユーザーがボタンを押したときに起こること。
  - フォームに文字を入力したときの値の変化。
  - エラーが起きたとき、画面にメッセージが表示されるか。
- **テストを省くこと（×）**
  - コンポーネント内部のstate名が `isVisible` か `show` か。
  - *React*自体が正しく動くか。useStateの検証は*React*チームが行います。
  - CSSが適用されたかどうかだけの確認。これは視覚的テストツールの対象です。

## これから使うツール

このシリーズでは、広く使われている強力なツールを利用します。

- **Jest**
  テストを実行し、結果を示す*テストランナー*です。バックエンドのJUnitに似ています。
- **React Testing Library（RTL）**
  *React*コンポーネントを仮想環境で描画し、クリックや入力などの操作を再現するツールです。
- **MSW（Mock Service Worker）**
  ネットワークリクエストを捕捉し、モックデータを返すツールです。
