## はじめに

AIエージェントに機能を一つ任せたとき、最初に `docs/` 全体を読むなら、リポジトリの構成を見直す頃です。
*どの作業にどの文書が必要か*が案内されていないと、エージェントは広い範囲を調べます。
小さな修正でも過剰に情報を読むと、費用と待ち時間が増え、古い文書を根拠に誤った判断をする可能性も高まります。
<Bbox>新入社員として、READMEも説明文書もないプロジェクトを引き継いだ場面を想像してみてください。困ることが多いはずです。</Bbox>
この記事では、ルートの指示、作業別の文書、サブディレクトリのルールを結ぶ構成を作ります。

## コンテキストへの案内

> リポジトリの構成は、作業ごとに読む文書の範囲を絞るために整えます。

Codexは、リポジトリのルートから現在の作業パスまでの `AGENTS.md` を順に集め、深い階層の指示を後から適用します。
[OpenAI DocsのAGENTS.mdの読み込み方式](https://developers.openai.com/api/docs/guides/latest-model?gallery=open&galleryItem=trivia-quiz-game&model=gpt-5.3-codex)
そのため、ルートの `AGENTS.md` には、どの作業にも適用する短い取り決めを置くとよいでしょう。
テストコマンド、パッケージマネージャー、変更時に維持する互換性の境界など、*推測に任せると危険な事実*を含めます。

```md title="AGENTS.md"
 # 프로젝트 공통 규칙

- 패키지 명령은 pnpm을 사용합니다.
- 변경 후 관련 테스트와 pnpm lint를 실행합니다.
- 공개 API와 데이터베이스 스키마 변경은 호환성 영향을 설명합니다.

 # 작업별 문서

- 인증 변경은 docs/auth.md를 읽습니다.
- 배포 변경은 docs/deploy.md를 읽습니다.
- 결제 변경은 docs/billing.md와 apps/api/AGENTS.md를 읽습니다.
```

このファイルにアーキテクチャの全体像や過去の障害記録まで入れると、軽微な修正でも無関係な情報の読み込みに費用がかかります。
OpenAIも、すべての作業で文書一式を読み込ませるより、作業の条件に応じて関連文書を案内する方法を勧めています。
[OpenAI Developersのコンテキスト指示設計](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

## 文書を分ける

文書は、**どんな条件で読むか**を基準に分けます。
以下は、Next.jsのサービスとAPIを一緒に運用するチームで使える構成例です。

```text title="repository-layout.txt"
.
├── AGENTS.md                # 모든 작업에 적용되는 최소 규칙
├── README.md                # 사람이 빠르게 이해할 프로젝트 소개
├── docs/
│   ├── architecture.md      # 서비스 경계가 필요한 변경
│   ├── auth.md              # 인증·권한 변경
│   ├── deploy.md            # 배포와 운영 변경
│   └── decisions/           # 중요한 설계 결정 기록
├── apps/
│   ├── web/
│   │   └── AGENTS.md        # 프런트엔드 지역 규칙
│   └── api/
│       └── AGENTS.md        # API와 데이터 접근 지역 규칙
└── packages/
    └── ui/
        └── AGENTS.md        # 디자인 시스템 변경 규칙
```

`README.md` は初めて見る人がプロジェクトを理解するための文書で、`AGENTS.md` はエージェントが安全に作業を始めるための指示です。
一つの文書にまとめると、人に必要な背景説明と、エージェントがすぐに適用するルールが混ざります。

<Ybox>文書を別の場所に置くだけでルートの指示から案内しなければ、エージェントはdocs/auth.mdの存在に気付けません。特定の作業で必要な文書は、ファイル名と参照する条件を併せて記載します。</Ybox>

### サブディレクトリのルール

サブディレクトリの `AGENTS.md` には、ルートの内容を繰り返さず、そのフォルダー固有のコマンド、テスト範囲、禁止する依存関係など、*その場所に固有の違い*を書きます。

```md title="apps/api/AGENTS.md"
 # API 변경 규칙

- API 계약 변경 전 docs/architecture.md를 확인합니다.
- 데이터 모델 변경은 prisma migration을 함께 만듭니다.
- apps/api/의 테스트는 pnpm --filter api test로 실행합니다.
```

ルートの共通原則に従い、APIのディレクトリでだけAPIのルールを加えるので、二つの文書の役割が分かれます。
この構成は、モノレポで特に役立ちます。
フロントエンドの担当者は決済バックエンドの手順を読まずに済み、データモデルの指示はAPIの修正時にだけ追加されるためです。

## 調査にかかる費用

エージェントがリポジトリで文書を探す方法も設計します。
文書の検索は許容したうえで、*既定で読む範囲*と*必要になったら読む範囲*を分けます。

| 情報 | 既定で読み込む | 必要時に読み込む |
| --- | --- | --- |
| 実行・検証コマンド | `AGENTS.md` | — |
| サービスの境界 | 短いリンク | `docs/architecture.md` |
| 認証ポリシー | 短いリンク | `docs/auth.md` |
| 変更履歴 | — | `docs/decisions/` |
| 特定アプリのルール | — | 該当パスの `AGENTS.md` |

作業依頼にもパスを添えると、範囲がさらに明確になります。
例えば、「ログイン画面を修正する」より、「`apps/web` のログイン画面を修正し、`docs/auth.md` のセッションルールを確認してください」と伝えます。

## 確認を繰り返す

構成を変更したら、エージェントが必要なパスだけを読んでいるかを確認します。
以下のような小さな作業で確認すると、文書の漏れや重複を見つけやすくなります。

```text title="repository-context-check.txt"
1. 웹 화면 수정, API 수정, 배포 변경 작업을 각각 하나씩 고릅니다.
2. 각 작업에서 필요한 문서와 AGENTS.md를 목록으로 적습니다.
3. 공통 규칙이 중복되지 않았는지 확인합니다.
4. 작업과 무관한 문서가 기본 지침에 강제되지 않았는지 확인합니다.
5. 문서가 가리키는 테스트 명령을 실제로 실행합니다.
```

`git ls-files '*AGENTS.md' 'docs/*.md'` を使うと、追跡中の指示と主な文書をすぐに一覧できます。
新しいメンバーが文書を変更したときにもこの確認を行うと、時間とともに指示が肥大化するのを防げます。

## チームのチェックリスト

✓ ルートの `AGENTS.md` には共通コマンドと安全上の境界を置きます。
✓ 作業ごとの詳細は `docs/` に分け、参照条件とともにリンクします。
✓ 下位の `AGENTS.md` には、そのパス固有のルールだけを加えます。
✓ `README.md` とエージェント向けの指示では、想定する読者を分けます。
✓ 代表的な作業で、実際に読み込むパスとテストコマンドを確認します。

## まとめ

AIエージェント向けのリポジトリでは、共通ルールを短く保ち、作業条件に応じて詳細な文書を参照できるようにします。
参照先が明確になれば、エージェントは少ない情報で正確に作業しやすくなり、チームも文書の重複とコンテキストの浪費を減らせます。
