## 1. What We Covered

We learned how to use the tools and developed **habits for building better software**.

- **The tools**
  We set up a test environment with *Vitest* as the test runner and *React Testing Library* to render components.
- **The user's perspective**
  We wrote tests around what users see and click, leaving details like state variable names out of the assertions.
- **Safe refactoring**
  With tests as a safety net, we could make larger changes, such as splitting components and extracting hooks.
- **Asynchronous behavior and mocking**
  With *MSW*, we could keep developing the frontend before the backend API was ready.

## 2. How TDD Changed Our Code

What changed after we started using TDD?

### Before TDD: Spaghetti Code
If you don't consider how you'll test the code, UI, business logic, and API calls can get tangled in one component. When the immediate goal is to get something working, it is easy to put everything into `useEffect`.

### After TDD: Separate Responsibilities
Asking yourself how to test the code pushes you to improve its structure.

```typescript title="src/hooks/useUserList.ts" showLineNumbers
// [변화] 로직은 Hook으로 분리되어 독립적으로 테스트 가능해졌습니다.
export function useUserList() {
  const [users, setUsers] = useState([]);
  // ... 데이터 fetching 로직
  return { users };
}
```

- **Custom hook** — Separating business logic makes it easier to reuse and test.
- **Container and presenter** — Separating data handling from rendering simplifies UI tests.

## 3. Frontend Testing Strategy: The Testing Trophy

In Part 13, we learned about the *Testing Trophy*. Choose a type of test that fits the behavior you're verifying.

- **Static analysis**
  Use *TypeScript* and *ESLint* to catch typos and basic errors. These checks give you a lot of coverage for little effort.
- **Unit tests**
  Check utility functions or complex hook logic.
- **Integration tests**
  These are the **most important**. Use *RTL* to verify how users interact with components.
- **End-to-end (E2E) tests**
  Verify critical scenarios such as checkout and sign-in in a real browser.

<Ads3/>

## 4. What to Learn Next

The series is ending, but there are more ways to improve the quality of your frontend.

### E2E Testing with Playwright or Cypress
We tested in jsdom, a simulated browser environment. To check that styles and navigation work in real browsers such as Chrome and Safari, use an *E2E tool*. We'll cover this in an upcoming **bonus installment**.

### Visual Regression Testing with Storybook or Chromatic
What if a feature still works but someone accidentally changes the button color? These tools compare screenshots pixel by pixel to check visual details that are hard to verify in code.

### Contract Testing with the Backend
If the frontend's mock data and the real API specification diverge, the application can fail. Contract testing helps catch that by failing a test when the agreed API specification changes.
