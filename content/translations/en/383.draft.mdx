## What We Covered

Along the way, we learned a *way of thinking that makes software more robust*.

- **The basics (Parts 1–4)**
  We learned the Red–Green–Refactor cycle at the heart of TDD and wrote our first tests with JUnit 5 and AssertJ.
  In particular, we learned the value of writing the *minimum implementation* that gets the test to pass.

<br/>
- **Improving structure and testing each layer (Parts 5–8)**
  We *refactored* messy code to separate the service and repository responsibilities.
  We switched from a fake in-memory store to *JPA* and tested the controller with *MockMvc*.

<br/>
- **Advanced techniques and problem-solving (Parts 9–13)**
  We used *Mockito* to isolate dependencies and verify behavior.
  We validated inputs with `@Valid` and made time-dependent code testable using a *Clock bean*.
  Finally, we learned how to balance *unit tests* and *integration tests*.

## How TDD Helps with Maintenance

Why did we go to all the trouble of writing these tests?
The payoff becomes clear after development is complete.
<br/>

- **Refactoring with confidence**
  Changing code no longer means wondering whether something else will break.
  When the tests give us a *green light*, we can improve the structure with confidence.
- **Living documentation**
  Tests are often more accurate than a complicated wiki.
  If you want to know which inputs make an API return an error, the tests give you an answer you can verify.
- **Faster debugging**
  When a bug occurs, a failing test can show you where to look without searching the entire codebase.
  It's like having security cameras in every corner of the code.

## Your Next Steps

- **Testcontainers**
  We used H2 as an in-memory database, but on a real project you may want to test against the same MySQL or Redis environment you use in production.
  Try learning *Testcontainers*, which uses Docker.
<br/>

- **BDD (Behavior-Driven Development)**
  Tools such as *Cucumber* and *JGiven* let you write tests in language closer to a requirements document, using `Given`, `When`, and `Then` in place of technical assertions such as `assertEquals`.

<br/>

- **Performance testing**
  Once you know the feature behaves correctly, check how fast it runs.
  Try load testing with *JMeter* or *nGrinder*.

<br/>
- **CI/CD pipelines**
  Set up *GitHub Actions* or *Jenkins* to run your tests automatically whenever you push code to GitHub, so they run outside your own computer too.

## Conclusion
