## Before We Begin

When you work with AI coding agents regularly, *cost* depends on model selection and how you organize the work. On the same feature, one agent reads only the `필요한 파일` (necessary files) and passes tests on the first try. Another searches the `저장소 전체` (entire repository), edits several times, then starts over. Input tokens, tool calls, waiting, and developer review time all contribute, and the difference grows with repeated use.

<br/>

*Context engineering* means **providing the information the current task needs in the right order**. It includes leaving a record that the next task can use. The principle applies to Claude Code, Codex, and other AI coding agents.

<br/>

This article covers practical ways to reduce both tokens and rework.

<Bbox>Even if your company provides enough agent usage today, reducing tokens and rework helps you adapt when policies change or you switch models.</Bbox>

## Principles for Saving Tokens

> A shorter prompt can still lead to higher token usage.

Missing information can cause an agent to `더 많이 탐색` (search more widely) or `수정과 테스트를 반복` (repeat edits and tests) based on a bad assumption. Sending every architecture document and log at once can bury important instructions and raise input costs.

### Where Tokens Go to Waste

- **Unnecessary repository exploration.** Reading unrelated files expands the context.
- **Duplicated repository instructions.** The same rules in AGENTS.md, CLAUDE.md, and README are read repeatedly.
- **Oversized tool output.** Full test logs, API responses, and build artifacts are passed through unchanged.
- **Edits without verification.** Vague scope and completion criteria lead to repeated changes to the same files.

Token usage measures cost. Rework also reveals quality problems. *Low usage can still come from an inefficient workflow if rework is high.* Alongside input and output tokens, track tool calls, failed tests, and changes people reverted.

### What to Measure

Start with three tasks of the same kind and record the following.

| Metric | Warning sign | Improvement goal |
| --- | --- | --- |
| Files read | Far more than the scope requires | Read files needed for the affected paths |
| Tool calls | Same command run repeatedly | Specify exploration and verification commands in advance |
| Test retries | Repeated without knowing the cause | Share the relevant part of the failure log |
| Files edited | Wide-ranging edits for a small feature | State the permitted scope in the request |
| Human review time | Reviewer has to reconstruct the intent | Record completion criteria and verification results together |

## Task Scope

A feature name alone forces the agent to infer both the relevant files and what counts as done.

<Bbox>If you hand over a project folder with only “fix this feature,” the agent may spend tokens searching the full set of files and documents.</Bbox>

That may work on simple tasks, but exploration and assumptions multiply as the repository grows. **Define the scope and completion criteria first** to give the agent a cheaper route to the right result.

### Task Request Template

Use the template in a chat, issue, or automated pipeline.

```text title="agent-task-template.txt"
목표
- 게시글 목록 API에 페이지네이션을 추가합니다.

수정 범위
- src/app/api/posts/route.ts
- src/lib/posts/query.ts
- 관련 테스트 파일

완료 조건
- page와 limit이 없을 때 기존 응답과 호환됩니다.
- 잘못된 쿼리는 400 응답을 반환합니다.
- npm test와 npm run lint가 통과합니다.

금지 사항
- 데이터베이스 스키마와 공개 응답 필드는 변경하지 않습니다.
- 지정한 범위 밖 리팩터링은 하지 않습니다.

작업 방식
- 수정 전에 관련 파일만 읽고 변경 계획을 세웁니다.
- 완료 후 수정 파일과 검증 결과를 짧게 요약합니다.
```

The template *leaves implementation decisions open*. The agent chooses how to solve the problem. You specify what it should read and how success will be checked.

### When to Split a Task

Split work that crosses several boundaries. If one request combines authentication, a database migration, and interface changes, their failure causes become harder to separate. The following phases also reduce the context each one needs.

- In the `조사 단계` (investigation phase), identify relevant paths and current behavior.
- In the `구현 단계` (implementation phase), work with the agreed files and tests.
- In the `리뷰 단계` (review phase), examine the diff and verification results.

Each phase can then proceed without carrying the full exploration log from the previous one.

## Repository Instructions

`AGENTS.md` and `CLAUDE.md` communicate team rules. A file containing every historical decision and exception loads irrelevant guidance even for small edits. Treat instruction files as a *router* to the right documents and commands.

### Minimal Instructions

Keep only guidance that applies to most tasks in the root instructions.

```md title="AGENTS.md"
 # 프로젝트 공통 규칙

- 패키지 설치는 npm을 사용합니다.
- 변경 후 npm run lint와 npm test를 실행합니다.
- API 응답 형식 변경은 요청에 명시된 경우에만 허용합니다.
- 데이터베이스 변경은 prisma/schema.prisma와 migration을 함께 검토합니다.

 # 작업별 안내

- 인증 작업은 docs/auth.md를 읽습니다.
- 배포 작업은 docs/deploy.md를 읽습니다.
- 데이터베이스 마이그레이션은 docs/database-migrations.md를 읽습니다.
```

Put detailed procedures for authentication, deployment, and other specific work in separate documents. The agent can read each when it applies.

<br/>

OpenAI's documentation also explains that long or duplicated `Skill` descriptions and excessive repository guidance can take up context and make relevant instructions harder to select. [OpenAI Developers on rethinking skills and prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

### Instructions You Can Move Out of the Root

- Long lists of commands already discoverable in package.json scripts
- Historical decisions that only matter when examining Git history
- Detailed rules for one feature or directory
- Code style rules repeated across several documents

Move anything you need to preserve into a separate document, then leave a link and the condition for reading it in the root instructions.

## Task State

Keeping an entire long conversation carries old exploration and failure logs forward. A *short file* lets a new session resume from the facts it needs.

### The State Document

Keep it brief. The following details are enough for another agent or teammate to pick up the work.

```md title="docs/agent-state/pagination.md"
 # 게시글 페이지네이션 작업 상태

 ## 완료
- 기존 목록 API의 응답 구조를 확인했습니다.
- page와 limit의 기본값을 합의했습니다.

 ## 남은 작업
- query.ts에 범위 검증을 추가합니다.
- route 테스트에 잘못된 limit 사례를 추가합니다.

 ## 검증 명령
- npm test -- posts
- npm run lint

 ## 결정 사항
- 기존 클라이언트 호환성을 위해 total 필드는 추가하지 않습니다.
```

Treat this file as a *record of project decisions*. When the task is done, remove it or move key decisions to an `ADR` or issue.

<br/>

Anthropic's guidance also recommends preparing tests and setup in the first stage of work spanning multiple context windows, then using structured state in later stages. [Anthropic prompting best practices](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/prompt-templates-and-variables)

### When to Start a New Session

A fresh session can be more efficient in these situations.

- Investigation is complete and implementation scope is settled.
- Error logs are long and several failed attempts have accumulated.
- The feature has changed and the earlier file list is irrelevant.
- Only review remains and detailed implementation conversation is no longer needed.

In the first request, include the state file, changed file list, and verification commands. This clears context while preserving decisions.

## Tool Output and Verification

Terminal and MCP calls can consume more tokens through results than through commands. Return what the next decision depends on. Full build logs and complete table lists often add unnecessary context.

### Tool Output

When locating files, narrow the paths and matches before printing file contents.

```bash title="terminal-workflow.sh"
 # 필요한 경로를 먼저 찾습니다.
rg --files src | rg 'posts|pagination'

 # 관련 심볼이 있는 줄만 확인합니다.
rg -n 'getPosts|page|limit' src/app src/lib

 # 확정한 파일만 읽습니다.
sed -n '1,220p' src/lib/posts/query.ts
```

On test failure, start with the test name, error message, and relevant stack frames. Widen the output if the cause is still unclear.

### The Verification Loop

Skipping tests to save tokens can create more rework. Start with the smallest check that verifies the task's completion criteria, then run the full verification at the end.

```text title="verification-order.txt"
1. 변경한 함수의 단위 테스트를 실행합니다.
2. 변경 경로의 타입 검사와 린트를 실행합니다.
3. 영향 범위가 확인되면 전체 테스트를 실행합니다.
4. 수정 파일과 테스트 결과를 diff와 함께 검토합니다.
```

In Codex, `/status` shows the model and the session's context and token usage. Record figures before and after to see which instructions and workflow changes helped.

## Team Checklist

✓ Put the goal, edit scope, completion criteria, and restrictions in the request.
✓ Keep shared rules and document paths in the root AGENTS.md or CLAUDE.md.
✓ Search or summarize long logs and responses before reading the relevant parts.
✓ Separate investigation, implementation, and review into sessions when their context differs.
✓ Keep task state and verification commands in a short repository document.
✓ Run focused tests first, followed by full verification and diff review.
✓ Pick three tasks in a month and compare files read, test retries, and review time.

## Conclusion

Design the work so Claude and Codex can read the right files, call the tools they need, and verify a focused change. That can save both tokens and rework.

<br/>

Start by writing requests as task agreements, keeping detailed repository guidance in task-specific documents, and recording state in a file.
