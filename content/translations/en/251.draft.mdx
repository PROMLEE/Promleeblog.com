## Before We Begin

As an application gains features and more teams contribute to it, a *monolithic* frontend, developed and deployed as a single unit, can become harder to manage.
- A growing codebase can make builds slower.
- Even a small change may require testing and deploying the entire application.
- Teams sharing one codebase face more merge conflicts and have a harder time choosing or upgrading their tools.
- A bug or performance problem in one area can affect the whole application.

*Micro frontends (MFE)* apply the idea of *microservices architecture*, which originated in backend development, to the frontend. We'll look at how micro frontends work, their advantages, how to implement them, and what to consider before adopting them.

## What Are Micro Frontends?

Micro frontend architecture divides a large frontend into *small, independently deployable* applications, sometimes called micro apps. Users still see a single coherent website or app, but it consists of several independent parts working together.

### Main Goals and Characteristics
- **Independent development and deployment**
  Each micro app has its own codebase and can be developed, tested, built, and deployed separately. This can speed up development and releases.
- **Greater team autonomy**
  Each team owns a micro app that corresponds to a business feature or domain. Teams have more freedom to choose their tools and working methods, while still coordinating across the product.
- **Gradual upgrades and technology choices**
  Teams can introduce new technology or upgrade an existing stack in one micro app at a time. In principle, different micro apps can even use different frameworks, such as React, Vue, or Angular.
- **Manageable codebases**
  Splitting a large codebase into smaller ones makes each part easier to manage.

### Comparison with a Monolithic Frontend

| Feature | Monolithic frontend | Micro frontends |
| --- | --- | --- |
| **Codebase** | One large codebase | Several smaller codebases |
| **Development** | All teams work in the same codebase | Each team works in its own codebase |
| **Deployment** | The entire application ships together | Each micro app can ship independently |
| **Technology stack** | One stack that is harder to change | Multiple stacks are possible, and changes can roll out gradually |
| **Team structure** | Teams organized by function, or one large team | Autonomous teams organized by domain or feature |
| **Coupling** | High, so changes can affect many parts | Low, so changes affect a smaller area |
| **Complexity** | Low initially but grows quickly with scale | Higher setup complexity, with simpler individual apps |

## Integration Methods

How do independent micro apps come together into a single experience? This is called *integration*. A common approach is *runtime integration*, where the parts are assembled in the user's browser.

### Runtime Integration Options
- **iframe**
  The oldest and simplest approach loads each micro app in a separate iframe. It is easy to implement, but communication between apps gets complicated, and URL handling and the user experience can feel awkward. These trade-offs make it less popular today.
- **Web Components**
  Use standard Web Components to encapsulate each micro app as a custom HTML element. This works across frameworks, though browser support and ecosystem maturity are considerations.
- **JavaScript integration**
  JavaScript dynamically loads and mounts each micro app in a specific DOM element. Tools such as single-spa and Webpack Module Federation use this approach.

### single-spa: Routing and Lifecycle Management

single-spa is a JavaScript framework that handles *routing* and the *lifecycle* of micro frontends, including loading, mounting, and unmounting.
#### What It Does
- Chooses which micro app to activate based on the URL and handles routing.
- Controls when each app loads, mounts on screen, and unmounts.
- Lets you combine apps built with different frameworks, including React, Angular, and Vue.
#### How It Works
1. **Container app (root app)**
   The main application contains the single-spa configuration.
2. **Application registration**
   Register each micro app with single-spa and specify which URLs activate it and how to load its code.
3. **Routing**
   When the URL changes, single-spa activates the matching micro app and unmounts apps that are no longer needed.

## Webpack Module Federation

Independent micro apps may still need the same libraries, such as React or Lodash, or the same components, such as buttons from a design system. Bundling those resources separately in every app makes the overall application larger. *Module Federation*, introduced in Webpack 5, helps solve this problem.

### Core Concepts
Module Federation lets separately built JavaScript applications share code dynamically at *runtime*.
- **Host**
  An application that imports and uses code from another application, called a remote. The container, or shell, typically acts as the host in a micro frontend.
- **Remote**
  An application that exposes its code to a host. Each micro app can act as a remote.
- **Shared dependencies**
  Libraries that hosts and remotes share. Module Federation considers library versions when managing these dependencies and can avoid duplicate loads. For example, if a host and remote are configured to share React v18, the browser can load that version once.
- **Exposed modules**
  Specific modules, such as components or functions, that a remote makes available to a host.

### Basic Configuration Example

Configure Module Federation in your Webpack configuration.
```javascript title="Remote 앱의 webpack.config.js"
// Remote 앱 (예: 'profileApp')의 webpack.config.js
const { ModuleFederationPlugin } = require('webpack').container;
const deps = require('./package.json').dependencies; // 공유 의존성 버전 관리

module.exports = {
  // ... 기타 설정 ...
  plugins: [
    new ModuleFederationPlugin({
      name: 'profileApp', // Remote 앱의 고유 이름
      filename: 'remoteEntry.js', // Host가 참조할 진입점 파일
      exposes: {
        // 외부에 노출할 모듈 경로 매핑 ('./UserProfile' 키로 접근)
        './UserProfile': './src/UserProfile',
      },
      shared: { // 공유할 의존성 설정
        ...deps, // package.json의 모든 의존성 공유 (간단 예시)
        react: { singleton: true, requiredVersion: deps.react },
        'react-dom': { singleton: true, requiredVersion: deps['react-dom'] },
      },
    }),
  ],
};
```

```javascript title="Host 앱의 webpack.config.js"
// Host 앱 (예: 'containerApp')의 webpack.config.js
const { ModuleFederationPlugin } = require('webpack').container;
const deps = require('./package.json').dependencies;

module.exports = {
  // ... 기타 설정 ...
  plugins: [
    new ModuleFederationPlugin({
      name: 'containerApp',
      remotes: {
        // 사용할 Remote 앱 정보 등록 (profileApp@http://localhost:3001/remoteEntry.js)
        profileApp: 'profileApp@http://localhost:3001/remoteEntry.js',
      },
      shared: { // 공유할 의존성 설정 (Remote와 동일하게)
        ...deps,
        react: { singleton: true, requiredVersion: deps.react },
        'react-dom': { singleton: true, requiredVersion: deps['react-dom'] },
      },
    }),
  ],
};
```
```jsx title="Host 앱에서 Remote 컴포넌트 사용"
// Host 앱의 컴포넌트에서 Remote 컴포넌트 사용
import React, { lazy, Suspense } from 'react';
const RemoteUserProfile = lazy(() => import('profileApp/UserProfile'));

function App() {
  return (
    <div>
      <h1>컨테이너 앱</h1>
      <Suspense fallback="Loading Profile...">
        <RemoteUserProfile />
      </Suspense>
    </div>
  );
}
```
With this setup, `containerApp` imports and uses the `UserProfile` component exposed by `profileApp` as if it were local code. Shared libraries such as React can be loaded once.

> Q: What is Webpack Module Federation, and what problem does it solve in micro frontends?
> A: It lets independently built Webpack applications share code dynamically at runtime. Micro apps can share components and avoid loading common libraries more than once.

## What to Consider Before Adopting Micro Frontends

Micro frontends offer several advantages, but adoption and operation also bring new responsibilities.
- **Initial setup**
  Configuring tools such as Module Federation or single-spa and building the integration takes upfront work.
- **Technology stack management**
  Teams can use different stacks, but too much variety can complicate development, builds, and deployments, and increase bundle size. Agree on a reasonable level of standardization or set guidelines.
- **Shared dependency versions**
  Plan how teams will manage the versions of shared libraries across micro apps. Module Federation helps, but teams still need to coordinate versions.
- **A consistent user experience**
  Teams working independently can easily diverge in design and behavior. Build and use a shared design system, ideally distributed as a library.
- **State and communication between apps**
  If micro apps need to share state or communicate, define clear interfaces and choose how they will communicate. Options include custom events, the window object, router state, or a global state library. This can be one of the hardest parts of MFE.
- **Team boundaries**
  Decide how to divide the apps and teams. Business domains, user journeys, and features are possible boundaries. Aim to keep dependencies between teams low.
- **Independent deployment pipelines**
  Each micro app needs a CI/CD pipeline so it can be built, tested, and deployed independently.
- **Operations and monitoring**
  Managing and monitoring multiple deployment units can make operations more complex.

> Module Federation uses a dependency graph to manage shared modules and versions. single-spa can map URLs to micro apps through routing rules, much like a routing table.

## Conclusion

Micro frontends can help manage the complexity of a large frontend.
- They allow **independent development and deployment**, give teams **more autonomy**, and support **gradual changes**.
- Teams commonly assemble micro apps with **runtime integration**, using iframes, Web Components, or JavaScript.
- **single-spa** handles routing and lifecycles, while **Webpack Module Federation** helps share code and dependencies.
- The approach introduces challenges in **setup**, **user experience consistency**, **communication between apps**, and **operations**.

Whether micro frontends make sense depends on your application's size, team structure, and technical requirements. If you adopt them, plan the integration and roll it out gradually.
