## Before getting started
We have explored several ways of fetching data in Next.js App Router.
This final part summarizes the series and provides a *practical guide* to selecting a strategy for each situation.
## Data-fetching strategy summary
| Strategy: Click for details | Location | When it runs | Advantages | Disadvantages |
|------|------|------------|------|------|
| [Fetch in server components](/blog/post/178-nextjs-fetching-1#fetch-함수-기본) | `app/page.tsx`, `app/layout.tsx`, etc. | Before HTML generation | Fast loading and good SEO | Unsuitable for dynamic interactions |
| [Client component + useEffect](/blog/post/180-nextjs-fetch-3#클라이언트-컴포넌트에서의-데이터-패칭) | A `'use client'` component | After mounting | Can fetch after user interactions | Initial loading may be slower |

## Recommended strategies by situation
### 1. Static content pages, such as blogs and documentation
- Use *server components with default fetch*.
- Configure an update interval with `revalidate` if necessary.
```ts
fetch('https://api.example.com/docs', {
  next: { revalidate: 3600 }, // 1시간마다 갱신
});
```
### 2. Dashboards for authenticated users
- *Read an authentication token with cookies(), then fetch*, or:
- *Use a route-handler API with cache-tag invalidation*.
```ts
const cookieStore = cookies();
const token = cookieStore.get('auth');
await fetch('https://api.example.com/user', {
  headers: { Authorization: `Bearer ${token?.value}` },
});
```
### 3. Data changes after user actions, such as button presses
- *Use SWR* in a client component.
```ts
'use client';
const { data, mutate } = useSWR('/api/posts', fetcher);
// 사용자 액션 후 mutate()
```
### 4. Real-time or frequently changing data
- Use `cache: 'no-store'`.
- Alternatively, fetch periodically on the client with SWR or polling.
```ts
await fetch('https://api.example.com/status', { cache: 'no-store' });
```

## Next.js's direction and philosophy
Next.js follows a *server-first* rendering philosophy.
Together with the *Server Components* concept introduced in React 18, it encourages minimizing client code and fetching on the server wherever possible.
Benefits include:
- Smaller client JavaScript bundles.
- Faster initial page loads.
- SEO optimization.
- Better code separation and security.
However, client-side behavior is sometimes essential, so a *balanced choice* matters.
## Conclusion
Across five parts, this series covered Next.js data fetching from basics to advanced techniques: `fetch`, caching strategies, SWR, route handlers, and cache invalidation.
We covered most of the situations needed in real projects.
Next.js data fetching is closely connected to React, so understanding *React's data flow* is important too.
In the App Router era, that flow is becoming increasingly *server-centered*.
Use this guide when planning your next strategy.
