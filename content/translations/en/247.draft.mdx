## Before We Begin

So far, we have focused on building dynamic user interfaces with React.
React applications often use *Client-Side Rendering (CSR)*, where JavaScript runs in the user's browser to draw the page.
CSR enables rich interactions, but users may see a blank screen during the initial load, and search engine optimization (SEO) can be more difficult.
*Server-Side Rendering (SSR)* and *Static Site Generation (SSG)* were developed to address these shortcomings.
Today, we will look at how these rendering strategies work, what makes them different, and the related concept of *Hydration*.

## CSR: Client-Side Rendering

Let's start with the approach many of us know best: Client-Side Rendering (CSR).

### How It Works

1. When a user visits a website, the browser downloads a minimal HTML file and a JavaScript bundle.
2. The browser runs the downloaded JavaScript.
3. The JavaScript (React code) creates a virtual DOM and updates the real DOM to draw the interface.
4. JavaScript continues to update the UI as the user interacts with the page.

### Advantages

- After the initial load, navigation is fast and smooth, without a full-page refresh.
- The server has less work because it mainly serves as an API.
- CSR works well for implementing rich, dynamic interactions.

### Disadvantages

- The browser must download and run the JavaScript bundle before the user sees the first screen, which can delay the Time to First Meaningful Paint.
- The initial HTML is nearly empty, so search engine crawlers may have trouble collecting the page content, creating an SEO challenge.

## SSR: Server-Side Rendering

Server-Side Rendering (SSR) was introduced to address CSR's initial loading and SEO drawbacks.
As the name suggests, SSR *renders the page on the server in advance* and sends the completed HTML to the client (browser).

### How It Works

1. The browser requests a page from the server when the user visits the website.
2. The server fetches the data required for the page, such as through an API call, and renders the React components into a complete HTML string.
3. The server sends this finished HTML to the browser.
4. The browser displays the HTML immediately, so the user can see the content sooner.
5. Meanwhile, the browser downloads the required JavaScript bundle in the background.
6. Once JavaScript has loaded, React connects event handlers to the server-rendered HTML and makes it interactive. This process is called *Hydration*, which we will discuss shortly.

### How SSR Differs from CSR

- **Initial loading speed (TTFP/FCP)**
  TTFP (Time To First Paint) and FCP (First Contentful Paint) measure how long it takes the user to see the first screen.
  Because SSR sends completed HTML from the server, the First Contentful Paint (FCP) is faster than with CSR, improving perceived initial loading performance.
- **SEO**
  The server provides completed HTML, making it easier for search engine crawlers to collect page content and improving SEO.
- **Server load**
  The server must render the page for each request, so it carries more load than with CSR.
- **Time to First Byte (TTFB)**
  Because the server needs time to generate the HTML, the Time To First Byte (TTFB) may be slower than with CSR.

### Next.js and Streaming SSR

Traditional SSR waits for the entire page's HTML to be generated before sending a response.
If the page is complex or its data takes a long time to load, this can make TTFB slow.
*Streaming SSR* was introduced to improve this behavior.
The Next.js App Router (the app directory approach) supports Streaming SSR by default.
- **Streaming SSR**
  The server sends the basic page shell first, then streams each UI piece (chunk) as it becomes ready.
  The browser progressively renders incoming HTML and loads the required JavaScript to perform Hydration.
- **Advantages**
  Users can see part of the page sooner, and the server does not have to finish rendering everything before responding, which can improve TTFB and the user experience.
  Streaming SSR works closely with React Suspense.

## SSG: Static Site Generation

Static Site Generation (SSG) creates HTML files for all website pages in advance, at *build time*.

### How It Works

1. The developer builds the code.
2. During the build, the framework (such as Next.js or Gatsby) renders each defined route in advance and creates a separate HTML file for it. Required data is fetched at build time as well.
3. The generated HTML, CSS, and JavaScript files are deployed to a static file server or a Content Delivery Network (CDN).
4. When a user requests a page, the server immediately sends the prebuilt HTML file for that route.
5. As with CSR, the browser displays the HTML and then loads JavaScript to make the page interactive through Hydration.

### How SSG Differs from CSR and SSR

- **Performance**
  Because SSG serves prebuilt static files, there is no server-side rendering at request time, so it is very fast.
  A CDN can deliver content quickly from locations around the world.
- **Server dependency and load**
  The server only needs to deliver static files, so its load is minimal; the site can even run without a server (the Jamstack architecture).
- **Security**
  With little server-side logic, the attack surface is smaller, which can improve security.
- **Build time**
  Builds can take longer when the site has many pages or complex data loading.
- **Data freshness**
  When content changes, the site needs to be rebuilt and redeployed for the update to appear.
  Technologies such as Incremental Static Regeneration (ISR) can help address this limitation.

### When Should You Use SSG?

SSG works particularly well when content does not change often and all pages can be generated at build time.
- Blog posts
- Documentation sites, such as API documentation and tutorials
- Marketing and landing pages
- Portfolio sites

> Q: "What is the difference between SSR and SSG, and when should you use each?"
A: "SSR generates HTML on the server for each request, while SSG generates HTML in advance at build time. SSR is suitable for user-specific dynamic content or frequently changing data, while SSG delivers excellent performance for sites with mostly static content."

## Hydration: Making Server-Rendered HTML Interactive

HTML created by SSR or SSG is initially a static document that can only be displayed.
JavaScript (React) is needed for interactions such as clicking a button or entering text.
*Hydration* runs client-side JavaScript (React) on top of the static HTML created by the server, turning it into an interactive application, like watering dry soil until it comes to life.

### Why Is Hydration Needed?

During Hydration, React performs several important tasks.
- **Attach event handlers**
  It connects event handlers defined on components, such as button clicks (`onClick`) and input changes (`onChange`), to the corresponding DOM elements.
- **Initialize state**
  It initializes internal component state managed by tools such as `useState` and `useReducer`, using the initial state passed from the server when needed.
- **Create a virtual DOM tree**
  It creates a virtual DOM tree in memory that matches the server-generated HTML, preparing to handle client-side updates efficiently.

In short, Hydration connects the React "nervous system and muscles" (JavaScript) to the "skeleton" (HTML) created by the server, turning it into a living application.

### Watch Out for Hydration Errors

React expects the HTML rendered on the server to *match exactly* the virtual DOM rendered on the client.
If they differ, React warns that it cannot complete Hydration properly (a Hydration Mismatch Error) and may render the entire page again on the client, which can erase the benefits of SSR or SSG.
Common causes include:
- Differences between the server and client environments, such as accessing the `window` object or using different time zones.
- Invalid HTML nesting, such as placing a `div` inside a `p` tag.
- Logic whose output changes depending on render time, such as `Math.random()` or the current time, because server rendering and client Hydration happen at different times.

To avoid these errors, keep the server and client render output consistent.
When necessary, use `useEffect` to separate logic that should run only in the client.

## Evolving Rendering Patterns

Frontend developers have been exploring new patterns that retain the advantages of SSR and SSG while reducing the cost of loading and running JavaScript.

### Partial Hydration

Instead of Hydrating the entire page at once, Partial Hydration selectively Hydrates *only the components that need interaction*.
Static parts remain as HTML while JavaScript is loaded only for dynamic parts, which can reduce both initial loading time and Time to Interactive (TTI).

### Islands Architecture

Based on Partial Hydration, Islands Architecture structures a page as multiple interactive "islands" floating on a static HTML "sea."
Each island is an independent widget or component that loads its own scripts and performs Hydration.

#### Advantages

Each component (island) loads only the JavaScript it needs, reducing the total JS payload.
JavaScript loading for less important components does not block interactions in more important components.
Progressive Hydration can further improve TTI.

#### Implementation

Modern frameworks such as Astro and Fresh actively use this architecture, and Next.js Server Components pursue similar goals.

## Conclusion

Today we explored several ways to render a React application for users.
- **CSR** handles rendering in the client and supports rich interactions, but may have drawbacks in initial loading and SEO.
- **SSR** renders HTML on the server in advance to improve initial loading and SEO, but can increase server load. *Streaming SSR* is an evolution that can improve TTFB.
- **SSG** creates static HTML at build time to offer excellent performance and reliability, but is limited when handling dynamic data.
- **Hydration** applies JavaScript (React) to static HTML generated by SSR or SSG, making the page interactive.
- **Partial Hydration** and **Islands Architecture** optimize performance by loading and running JavaScript only where needed.

There is no single rendering strategy that is best in every case.
Choose or combine approaches based on the application's characteristics, how dynamic its content is, its performance needs, and the importance of SEO.
Frameworks such as Next.js provide many features that make it easier to use and combine these rendering strategies.
