## Before We Begin

You assign the search interface to one AI agent and the search API to another. Both report passing tests. When you put the changes together, the interface reads `items` and the API returns `results`. Git reports no conflict because the agents edited different files. The feature still fails.

<br/>

Running multiple sessions is only the starting point. **Agree on shared contracts and ownership first, isolate the changes, and verify the integrated result.** This article uses a search feature to show how to divide the work, manage Git worktrees, and integrate the results.

## Dividing the Work

> Tasks can run in parallel when each can make decisions without waiting for the other's unfinished work.

To implement the search interface and API in parallel, agree on the input parameters and response shape first. If the response format is still up for discussion, finalize the API design before splitting the work. When two agents independently guess at an unsettled boundary, coordination can take longer than implementation.

| Relationship between tasks | Suggested workflow | Why |
| --- | --- | --- |
| Interface and API implementation with a settled contract | Work in parallel | Both can rely on the same inputs and outputs |
| Response design and the interface that consumes it | Design first, then implement | The first decision is an input to the second task |
| Independent bug fixes in separate modules | Consider parallel work | Check shared state and the test environment |
| Different edits to the same core function | Work sequentially or have one owner integrate them | The intent of the changes and the conditions for regression overlap |

Put the contract in code or documentation when you assign the frontend and backend work. Here is a type both the interface and API could follow.

```ts title="src/contracts/search.ts"
export type SearchItem = {
  id: string;
  title: string;
};

export type SearchResponse = {
  items: SearchItem[];
  nextCursor: string | null;
};

export type SearchError = {
  code: "INVALID_QUERY" | "INTERNAL_ERROR";
  message: string;
};
```

Along with the type, agree on request parameters, empty results, and HTTP status codes. The interface and API still fail to connect if the interface sends `q` and the API expects `query`. Verify that runtime responses match the contract too.

<Bbox>
If a shared contract needs to change, have the agent propose the change to the integration owner. Apply the required change to the shared baseline and have affected agents confirm the updated contract before continuing.
</Bbox>

## Assigning Ownership

Give each task a goal, completion criteria, and a set of files it may edit. The integration owner manages shared files that no individual task owns.

| Owner | Example edit scope | Shared boundary |
| --- | --- | --- |
| Interface task | `src/features/search/` and interface tests | Consumes the API contract |
| API task | Search routes, service, and API tests | Responds according to the same contract |
| Integration owner | Shared contract, package configuration, and the complete integration | Decides the order of changes and verifies the final result |

`package.json`, lockfiles, and shared test configuration often overlap. If an agent needs a dependency, it can record the requirement for a single owner to apply. Keeping sessions from editing the same configuration at the same time reduces coordination.

<br/>

Agents can still benefit from reading files outside their edit scope. For example, the API agent can inspect how the interface consumes its responses. **State read access and edit ownership separately.**

```text title="화면 작업 요청 예시"
목표: 검색어 입력, 빈 결과, 오류 상태 표시
계약: src/contracts/search.ts와 합의된 q 파라미터 사용
수정: src/features/search/와 관련 화면 테스트
공유 파일: 계약·패키지 설정 변경은 제안만 전달
검증: 화면 상태 테스트와 요청 파라미터 확인
완료 보고: 결과 커밋, 변경 파일, 검증 결과, 미검증 범위
```

## Isolating Changes With Worktrees

When multiple sessions edit the same checkout, one session may read or overwrite another's changes. Git worktree lets you attach multiple working directories to a repository and use separate working files and an index for each branch. [Git worktree documentation](https://git-scm.com/docs/git-worktree)

Here is a terminal example. It assumes that the shared contract is already committed and the branch names and target paths are available. Start by checking the current repository status.

```bash title="동일 기준에서 작업 공간 생성"
git status --short
task_base=$(git rev-parse HEAD)
git worktree add -b ai/search-ui ../shop-search-ui "$task_base"
git worktree add -b ai/search-api ../shop-search-api "$task_base"
git worktree list
```

`task_base` is the commit both tasks start from. Uncommitted changes in the current directory are outside that commit and do not carry over automatically. If a required contract change is still uncommitted, prepare the baseline according to your team's workflow first.

<br/>

The Codex app provides an isolated workflow using worktrees. Use the app's creation, switching, and cleanup controls for worktrees it manages. The manual commands above are a separate CLI workflow. [Codex worktree guide](https://learn.chatgpt.com/docs/environments/git-worktrees)

Claude Code also documents how to start isolated parallel sessions with `--worktree`. If you already created worktrees manually, start each session in its own directory. [Claude Code worktree workflow](https://code.claude.com/docs/en/common-workflows)

### Shared Resources

Separate folders still share access to resources such as development server ports and external databases. For example, two servers will clash if they bind the same port, and two tasks editing the same test data can affect each other's results. Allocate ports, test accounts, and data according to the project's existing isolation practices.

<Img src="/261015-110003.webp" width={650} height={433} alt="Files and branches isolated by worktrees, alongside ports, databases, and local configuration that need separate checks"/>

Node dependencies and environment files that Git does not track may also need separate setup. A working server in one worktree says little about the readiness of another. For example, assign port 3101 to the interface server and 3102 to the server used to verify the API, then configure the internal API address and test base URL accordingly.

<Ybox>
Even if test databases are separate, check whether migrations target the same environment or the sessions use the same external API account. Worktrees isolate file changes. External service permissions and data need their own isolation.
</Ybox>

## Integrating the Results

When the parallel work is done, collect the result commit, base commit, scope of changes, and verification evidence, as in the handoff record from Part 10. The integration owner checks that each change honors the shared contract and applies the results one at a time. Bring them in as identifiable units of change so you can see what each task delivered.

<br/>

The following example assumes each task produced a single commit. The recorded `task_base` and both task branches are still available, and no further edits are being made to either task.

```bash title="별도 작업 공간에서 순차 통합"
git worktree add -b ai/search-integration ../shop-search-integration "$task_base"
task_ui_commit=$(git rev-parse ai/search-ui)
task_api_commit=$(git rev-parse ai/search-api)
git -C ../shop-search-integration cherry-pick "$task_ui_commit"
git -C ../shop-search-integration cherry-pick "$task_api_commit"
```

`cherry-pick` applies the changes from a specified commit to the current branch. If the result spans several commits, picking only the last one may leave out earlier changes. Check the commit list and dependency order or follow your team's merge workflow. [Git cherry-pick documentation](https://git-scm.com/docs/git-cherry-pick)

<br/>

If the first application stops with a conflict, resolve it before proceeding to the next. Check the intended behavior and shared contract, then resume with `git cherry-pick --continue`. If you need to cancel the operation, check what `git cherry-pick --abort` will restore before aborting the current application.

### Types of Conflict

Semantic conflicts can occur even when Git shows no conflict markers. For example, the interface might expect `items` while the API sends `results`, or the interface might treat an empty array as a valid result while the API returns an error.

| Conflict | Example | How to check |
| --- | --- | --- |
| File conflict | Both tasks edit the same line of the same function | Review the diff and the intent of each change |
| Contract conflict | Response fields or error codes differ | Check the contract and run API consumer tests |
| Environment conflict | Sessions share a port or test data | Check server addresses and data isolation |
| Verification gap | Only the separate task tests have passed | Run the user flow on the integrated branch |

<Rbox>
Avoid resolving a conflict by wholesale accepting one side or deleting tests. Use both tasks' completion criteria to preserve the required behavior, then verify the integrated result again.
</Rbox>

## Verifying the Integration

Task A's tests provide evidence about A's code state, and task B's tests provide evidence about B's. The combined state needs its own checks. Verify the contract and the actual connection on the integration branch.

- Check that the interface sends the agreed request parameters.
- Verify that the interface handles the API's successful, empty, and error responses.
- Run the relevant type checks, unit tests, and integration tests.
- Check the browser flow from entering a search to displaying its results.
- Rerun affected checks if you change code during integration.

If you implemented the interface with mock responses first, use the actual test API for the final connection check. Verify that the mock and actual responses follow the same contract. The examples here illustrate the workflow. They do not report commands run against a production project.

### When to Clean Up

Remove a worktree after its results have been saved and no running session or server uses it. For a manual worktree, use `git worktree list` to confirm the exact path, check for changes and local files you need, then use `git worktree remove`. For an app-managed worktree, use the app's cleanup feature.

<Bbox>
Git-ignored environment files and test artifacts may be absent from the result commit. Check whether any of them need to be kept before cleanup, and finish outstanding work before removing its worktree.
</Bbox>

## Time and Cost

If tasks A and B are independent, the parallel execution phase usually ends when the slower task finishes. Total elapsed time also includes preparing the split, exploration by each task, reviewing results, resolving conflicts, and verifying the integration. For one small fix, that overhead can outweigh the time saved.

<br/>

Add up token usage across all tasks and the integration owner. Parallel sessions may each read the repository instructions and relevant code, so a shorter elapsed time does not necessarily mean fewer tokens. Use the measures from Part 8 to compare completion rate, human rework, total time, and total usage together.

When trying parallel work for the first time, start with two tasks that have a stable contract and different edit scopes. Record how much time integration adds so you can refine which tasks your team runs in parallel.

## Conclusion

Agree on the shared contract, separate ownership and working directories, then integrate the results one at a time. Even with worktrees, check shared resources such as ports and databases and look for semantic conflicts Git cannot detect.

<br/>

**Settle the contract → assign ownership → isolate workspaces → integrate sequentially → verify the connection.** The final article, Part 12, connects this process to request design, model selection, verification, and measurement to build a team development workflow.
