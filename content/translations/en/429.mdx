## Before We Begin

If an AI agent's first step on a small feature is to read all of `docs/`, inspect the repository structure. Without a clear path from *each task to the documents it needs*, agents search widely. Excess context makes small edits more expensive and slower, and outdated documentation can lead to poor decisions.

<Bbox>Imagine joining a team and inheriting a project with no README or other documentation. Where would you start?</Bbox>

This article connects root instructions, task-specific documentation, and subdirectory rules.

## Where Agents Find Context

> A repository structure should narrow the documents an agent needs to read for each task.

Codex collects `AGENTS.md` instructions in order from the repository root to the current working directory, applying instructions from deeper directories later. [OpenAI documentation on AGENTS.md loading](https://developers.openai.com/api/docs/guides/latest-model?gallery=open&galleryItem=trivia-quiz-game&model=gpt-5.3-codex)

Keep the root `AGENTS.md` brief and applicable across tasks. Include *facts an agent should not have to guess*, such as the package manager, test commands, and compatibility requirements.

```md title="AGENTS.md"
 # 프로젝트 공통 규칙

- 패키지 명령은 pnpm을 사용합니다.
- 변경 후 관련 테스트와 pnpm lint를 실행합니다.
- 공개 API와 데이터베이스 스키마 변경은 호환성 영향을 설명합니다.

 # 작업별 문서

- 인증 변경은 docs/auth.md를 읽습니다.
- 배포 변경은 docs/deploy.md를 읽습니다.
- 결제 변경은 docs/billing.md와 apps/api/AGENTS.md를 읽습니다.
```

Putting the entire architecture and old incident history in this file consumes context even on minor edits. OpenAI likewise recommends pointing agents to relevant documents based on the task. [OpenAI Developers on designing context instructions](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

## Splitting the Documentation

Organize documents by **when someone needs to read them**. The example below suits a team running a Next.js service and an API.

```text title="repository-layout.txt"
.
├── AGENTS.md                # 모든 작업에 적용되는 최소 규칙
├── README.md                # 사람이 빠르게 이해할 프로젝트 소개
├── docs/
│   ├── architecture.md      # 서비스 경계가 필요한 변경
│   ├── auth.md              # 인증·권한 변경
│   ├── deploy.md            # 배포와 운영 변경
│   └── decisions/           # 중요한 설계 결정 기록
├── apps/
│   ├── web/
│   │   └── AGENTS.md        # 프런트엔드 지역 규칙
│   └── api/
│       └── AGENTS.md        # API와 데이터 접근 지역 규칙
└── packages/
    └── ui/
        └── AGENTS.md        # 디자인 시스템 변경 규칙
```

`README.md` introduces the project to a newcomer. `AGENTS.md` gives agents instructions for starting work safely. Combining them mixes background a newcomer needs with rules an agent needs to act on immediately.

<Ybox>When you move details to a separate file, link it from the root instructions. Give both the path, such as docs/auth.md, and the condition for reading it.</Ybox>

### Subdirectory Rules

Use nested `AGENTS.md` files for *rules specific to that directory*, such as local commands, test scope, and prohibited dependencies. Leave common instructions at the root.

```md title="apps/api/AGENTS.md"
 # API 변경 규칙

- API 계약 변경 전 docs/architecture.md를 확인합니다.
- 데이터 모델 변경은 prisma migration을 함께 만듭니다.
- apps/api/의 테스트는 pnpm --filter api test로 실행합니다.
```

The root provides shared rules. The API directory adds its own rules where they apply. In a monorepo, this keeps billing backend procedures out of frontend work and adds data model guidance when an agent edits the API.

## The Cost of Finding Information

Distinguish what agents should read by default from what they should find when the work calls for it.

| Information | Load by default | Load when needed |
| --- | --- | --- |
| Run and verification commands | `AGENTS.md` | — |
| Service boundaries | Short link | `docs/architecture.md` |
| Authentication policy | Short link | `docs/auth.md` |
| Decision history | — | `docs/decisions/` |
| App-specific rules | — | The directory's `AGENTS.md` |

Paths in the task request also make exploration more predictable. For example, “Update the login screen in `apps/web` and check the session rules in `docs/auth.md`” gives the agent a clearer scope than “fix the login screen.”

## Checking the Structure

After reorganizing the repository, check whether the agent reads the expected paths. A small task like the one below can expose missing and duplicated guidance.

```text title="repository-context-check.txt"
1. 웹 화면 수정, API 수정, 배포 변경 작업을 각각 하나씩 고릅니다.
2. 각 작업에서 필요한 문서와 AGENTS.md를 목록으로 적습니다.
3. 공통 규칙이 중복되지 않았는지 확인합니다.
4. 작업과 무관한 문서가 기본 지침에 강제되지 않았는지 확인합니다.
5. 문서가 가리키는 테스트 명령을 실제로 실행합니다.
```

Use `git ls-files '*AGENTS.md' 'docs/*.md'` to list tracked instruction files and key documents. Repeat the check when teammates revise documentation to catch growth over time.

## Team Checklist

✓ Keep shared commands and safety boundaries in the root `AGENTS.md`.
✓ Move task-specific details to `docs/` and link them with conditions for when to read them.
✓ Keep rules in nested `AGENTS.md` files scoped to the directory.
✓ Write `README.md` and agent instructions for their respective audiences.
✓ Check which paths and test commands agents use on representative tasks.

## Conclusion

Keep shared rules short and give agents clear paths to detailed instructions for each kind of work. Agents can then read fewer files and still make informed changes, while the team reduces duplication and unnecessary context.
