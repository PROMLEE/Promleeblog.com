## Before We Begin

You shorten your instruction files and switch to a lighter model. Token usage drops, but PR reviews uncover more missed edge cases and you spend longer fixing them by hand. The token chart suggests an improvement while the development work may take longer.

<br/>

Earlier installments covered context, task requests, model choice, and code verification. The final step is to **record how changes to the workflow affect completion, time, and cost**. You can start measuring and comparing individual tasks without building a large dashboard.

## What to Measure

> Use a task with clear completion criteria as your unit of measurement. A single conversation or commit may capture only part of it.

“Fix back navigation so it restores the search filter” is one task. If you follow up three times or switch models along the way, keep those attempts under the same task. Counting success by call can hide the actual cost of a task that took several attempts to complete.

<br/>

Define the start and end first. Here, a task starts when you send the request to the AI and ends when it passes the agreed verification and review. Record attempted tasks that did not finish as failed or stopped. If your team includes deployment, add deployment verification to the completion criteria and apply it to every configuration you compare.

<Bbox>
Start by recording a task ID and completion criteria. A name like “Restore both the URL and input value after back navigation” gives you a concrete result to check. Use the same task ID across sessions.
</Bbox>

## Core Metrics

Start with four metrics and check them together. Before optimizing one, see whether another got worse.

| Metric | How to calculate or record it | What to watch for |
| --- | --- | --- |
| Completion rate | Completed tasks divided by all tasks whose evaluation has ended | Include failed and stopped tasks in the denominator |
| Human rework time | Time spent making manual fixes or preparing follow-up requests | Track separately from routine review |
| Total elapsed time | Time from the first request through verification and review | Distinguish agent execution from sources of waiting |
| Total usage and cost | Include retries and model escalation for the same task | Distinguish API charges from subscription limits |

Report in-progress tasks separately from the final completion rate. Define when each reporting period closes to keep late finishes from continually changing last week's numbers.

### Separating Rework From Review

Separate ordinary review from work needed to correct the AI's output. Ten minutes of code review and twenty minutes of explaining a missed condition and preparing a follow-up are different costs. Track manual edits and time preparing follow-ups to see which burden increased.

<br/>

When the AI fixes its own output during verification, count the iterations in elapsed time and usage. Track human intervention separately so you can identify tasks that required substantial help even when the overall completion rate was high.

## Recording Each Task

A short note or one CSV row per task is enough to start. Add fields that inform actual decisions. The following TypeScript example is a team record, independent of any API or product log format.

```ts title="tools/task-metrics.ts"
type TaskRecord = {
  taskId: string;
  taskType: "small-edit" | "feature" | "debug";
  startCommit: string;
  requestVersion: string;
  modelPath: string[];
  outcome: "accepted" | "failed" | "blocked";
  elapsedSeconds: number;
  humanReviewMinutes: number;
  humanReworkMinutes: number;
  extraRequests: number;
  apiCostUsd: number | null;
};
```

In `modelPath`, record the models and reasoning settings used, in execution order. Define `extraRequests` as the number of additional correction requests a person sends after the initial request. Count tool calls and test runs separately. Use `null` for `apiCostUsd` when the API cost is unknown in a subscription environment. Reserve zero for an observed zero cost.

<br/>

Keep verification commands and evidence of failures in the completion report from Part 7 and link them by task ID. A short failure reason is enough in the summary table. Specific entries like “missing entry-point information,” “misread the response schema,” or “test environment unavailable” make it easier to choose the next improvement.

### Collecting Usage

The Claude Code documentation directs users to the Session section of `/usage` for session token usage and estimated costs. Subscribers can see their usage limits on the same screen. The session estimate uses API rates, while the subscription bill is separate. For actual API billing, use the usage data in Claude Console. [Claude Code cost management](https://code.claude.com/docs/en/costs)

When a session covers multiple tasks, avoid copying its entire usage into every task record. Check whether you can calculate the difference at task boundaries. If you cannot separate them, record the limitation that your figures cover the session. Also check whether a figure is cumulative or per call. Adding cumulative values after each request can count the same tokens repeatedly.

<Ybox>
Providers account for input, output, cache, and reasoning tokens differently. If a total already includes a detailed field, count it once. To calculate price, check which model, cache, and processing rates apply as well as the token count.
</Ybox>

## Cost per Completed Task

Part 6 looked at the cost of escalating models within a task. To compare across tasks, include spending on unsuccessful attempts and divide by the number of completed tasks. Otherwise, excluding unfinished work can make a configuration appear cheaper.

```ts title="tools/task-metrics.ts"
function summarize(tasks: TaskRecord[]) {
  const accepted = tasks.filter((task) => task.outcome === "accepted");
  const costsKnown = tasks.every((task) => task.apiCostUsd !== null);
  const totalCost = costsKnown
    ? tasks.reduce((sum, task) => sum + task.apiCostUsd!, 0)
    : null;

  return {
    evaluated: tasks.length,
    accepted: accepted.length,
    completionRate: tasks.length ? accepted.length / tasks.length : null,
    humanReworkMinutes: tasks.reduce(
      (sum, task) => sum + task.humanReworkMinutes, 0,
    ),
    costPerAcceptedTask:
      accepted.length && totalCost !== null
        ? totalCost / accepted.length
        : null,
  };
}
```

This example assumes its input contains only tasks whose evaluation has ended. Each task's cost includes retries and escalation. If any cost is missing, the cost per completed task is unknown. If zero tasks were completed, it is undefined. Pass one record per `taskId` to avoid counting tasks with multiple calls more than once.

### Example Comparison

These are fictional figures for illustrating the calculation. Suppose configurations A and B each run the same ten tasks.

| Item | Configuration A | Configuration B |
| --- | --- | --- |
| Completed tasks | 9 | 7 |
| Failed or stopped tasks | 1 | 3 |
| Completion rate | 90% | 70% |
| Total API cost | USD 12 | USD 10 |
| API cost per completed task | About USD 1.33 | About USD 1.43 |
| Human rework time | 45 minutes | 80 minutes |

B has a lower total API cost, but a higher cost per completed task and more human rework. Track human time and API cost separately to see the difference. If your team has no internal labor rate, you can report the two figures independently.

## Conditions for a Fair Comparison

Numbers from different tasks mix the effect of the configuration with differences in task difficulty. Use the same starting code, request, verification criteria, and execution environment, and change one variable at a time. If you run the second configuration on code modified by the first, it inherits the first configuration's work.

<Img src="/261012-080003.webp" width={650} height={433} alt="Keep the starting code, request, verification, and environment fixed while changing one variable and comparing completion, rework, time, and cost"/>

To measure the effect of shortening `AGENTS.md`, keep the model and reasoning level fixed. To compare model routing, hold instructions and task requests constant. Changing the request, model, and verification together makes it difficult to tell which change affected the result.

### Grouping Tasks

Track simple edits, routine features, and complex debugging separately. A week with more easy tasks can have a higher overall completion rate than a week with harder work even when the model is unchanged. Show the task count and completion rate by category.

<br/>

Alongside average time, check the median and inspect particularly slow completions. The median sits in the middle of the ordered values and is less sensitive than the mean to a few long tasks. It still represents completed tasks only, so record the count of failures and stopped tasks and the time spent on them separately.

<Rbox>
Keep difficult tasks in the record and maintain the verification criteria. If the inputs or success criteria change, the old and new figures cease to be directly comparable even if the metric name stays the same.
</Rbox>

## Choosing What to Improve

Use the metrics to decide what to change next. Inspect the records and failure reasons for tasks whose results deteriorated, then choose one change.

| Observation | What to check first | Improvement to try |
| --- | --- | --- |
| Input usage rises | Repeated reads of instructions, documents, and tool output | Document entry points, reference files when needed, and limit response scope |
| Completion rate falls | How failures reproduce and whether completion criteria are missing | Make requests more specific and provide a way to verify the result |
| Human rework rises | Misunderstood requirements or interfaces | Show input and output examples and specify the change boundary |
| Waiting time rises | Bottlenecks in tests, tools, or the environment | Run relevant checks first and fix the execution environment |
| Escalations and retries rise | Initial model choice and missing information | Adjust model selection by task and improve handoff summaries |

Higher usage may be acceptable if rework falls and completion rises. Lower costs are less persuasive if more verification steps are missed. Inspect individual task evidence before assigning a cause to a change in the numbers.

### Getting Started

Pick a recurring task type and record a baseline for the current configuration. Change only one variable, such as instruction length, model, or reasoning effort, and compare the same cases. Use a small sample as an early signal and check that the trend holds on new tasks before adopting it as a default.

<Bbox>
Choose one improvement per week. Set an observable goal, such as “reduce repeated document reads while maintaining the completion rate on the same search feature tasks.”
</Bbox>

## Conclusion

AI coding metrics should show how much work makes it through verification and review. Define completion for each task and record failures, stops, and retries so you can tell whether lower usage improved the actual workflow.

<br/>

The series covered context organization, minimal instructions, repository guidance, task requests, skill and MCP loading, model routing, and code verification. You can evaluate changes one at a time. **Record a baseline → change one variable → compare under the same conditions → inspect causes at the task level.**
