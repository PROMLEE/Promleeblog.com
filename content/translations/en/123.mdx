## Before getting started
> This post was written for Flutter 3.24.

When developing an app or web frontend, you often need a backend or public API.
Calling it requires HTTP communication, which Flutter can handle with Dio and Retrofit.
The HTTP package is another option, but Dio and Retrofit make requests more convenient.
In particular, Retrofit's type definitions simplify response handling and can improve productivity.
This article explains using both libraries and why type definitions matter.
<Ads1 />
## 1. Installing packages
Retrofit requires four packages, including Dio and Retrofit.
Three packages are used only during development and belong in dev_dependencies.
Install them with the following commands.
```
dart pub add json_annotation dio retrofit
dart pub add --dev build_runner retrofit_generator json_serializable
```
Check pubspec.yaml for the following entries.
Versions shown are those used when this article was written.
```yaml title="pubspec.yaml"
dependencies:
	retrofit: ^4.4.2
	dio: ^5.7.0
	json_annotation: ^4.9.0

dev_dependencies:
	build_runner: ^2.4.13
	retrofit_generator: ^9.1.5
	json_serializable: ^6.9.0
```
The packages serve these roles:
- dio: HTTP communication.
- retrofit: API communication.
- json_annotation: JSON serialization and deserialization.
- build_runner: Code generation.
- retrofit_generator: Generating code for Retrofit.
- json_serializable: Generating JSON serialization and deserialization code for API requests.

### 2.1. Creating model classes
Here is example model code for the API request.
```dart title="lib/model/user_dto.dart"
import 'package:json_annotation/json_annotation.dart';
part 'user_dto.g.dart';

@JsonSerializable()
class UserDto {
	final int id;
	final String name;
	final String username;
	final String email;
	final Address address;
	final String phone;
	final String website;
	final Company company;

	UserDto({
		required this.id,
		required this.name,
		required this.username,
		required this.email,
		required this.address,
		required this.phone,
		required this.website,
		required this.company,
	});

	factory UserDto.fromJson(Map<String, dynamic> json) => _$UserDtoFromJson(json);
	Map<String, dynamic> toJson() => _$UserDtoToJson(this);
} 

@JsonSerializable()
class Address {
	final String street;
	final String suite;
	final String city;
	final String zipcode;
	final Geo geo;

	Address({
		required this.street,
		required this.suite,
		required this.city,
		required this.zipcode,
		required this.geo,
	});

	factory Address.fromJson(Map<String, dynamic> json) => _$AddressFromJson(json);
	Map<String, dynamic> toJson() => _$AddressToJson(this);
}

@JsonSerializable()
class Geo {
	final String lat;
	final String lng;

	Geo({
		required this.lat,
		required this.lng,
	});

	factory Geo.fromJson(Map<String, dynamic> json) => _$GeoFromJson(json);
	Map<String, dynamic> toJson() => _$GeoToJson(this);
}

@JsonSerializable()
class Company {
	final String name;
	final String catchPhrase;
	final String bs;

	Company({
		required this.name,
		required this.catchPhrase,
		required this.bs,
	});

	factory Company.fromJson(Map<String, dynamic> json) => _$CompanyFromJson(json);
	Map<String, dynamic> toJson() => _$CompanyToJson(this);
}
```

### 2.2. Creating the request interface
```dart title="lib/model/user.dart"
import 'package:dio/dio.dart';
import 'package:retrofit/retrofit.dart';
import 'user_dto.dart';

part 'user.g.dart'; // 생성될 파일

@RestApi(baseUrl: "https://jsonplaceholder.typicode.com") // base url
abstract class UserApi {
	factory UserApi(Dio dio, {String baseUrl}) = _UserApi;

	@GET("/users") // 요청할 API
	Future<List<UserDto>> getUsers(); // 요청할 API의 응답을 받을 모델 클래스
}
```
## 3. Generating code
The IDE may show errors or red underlines after you write the code above.
This means code generation is needed.
Run the following command from the project root.
```
dart run build_runner build
```
Check that the following files appear in the relevant directory.
```
lib/model/user_dto.g.dart
lib/model/user.g.dart
```
Once the errors disappear, you are ready to call the API.

## 5. Additional configuration
### 5.1. Passing request parameters
```dart
@GET('/users/{id}')
Future<UserDto> getUserByPathId(@Path() int id); // 파라미터 전달
```
### 5.2. Passing query parameters
```dart
@GET('/users')
Future<List<UserDto>> getUserByQueryId(
	@Query('id') int id,
); // 쿼리 파라미터 전달
```
### 5.3. Passing headers
Use the following form for fixed headers.
```dart
@GET('/users')
@Headers(<String, dynamic>{
	'Content-Type': 'application/json',
	'Authorization': 'Bearer {token}',
})
Future<List<UserDto>> getUsers(); // 헤더 전달
```
Use this form to provide headers dynamically.
```dart
@GET('/users')
Future<List<UserDto>> getUsers(
	@Header('Content-Type') String content_type, 
	@Header('Authorization') String authorization,
); // 헤더 전달
```
### 5.4. Passing a request body
```dart
@POST('/users')
Future<UserDto> createUser(@Body() UserDto user); // 바디 전달
```

## Troubleshooting
### 1. Renaming a class
Renaming a request-interface class may leave errors even after code generation.
Delete the generated d.dart file and generate it again to resolve this.
```
rm lib/model/user/user.g.dart
dart run build_runner build
```

## Conclusion
We have explored API communication in Flutter with Dio and Retrofit and the importance of type definitions.
Types simplify handling API responses and can improve productivity.

### Further ideas
As the response-model field count grows, the code may become long and harder to read.
A tool such as [json_to_dart](https://javiercbk.github.io/json_to_dart/) can generate model classes conveniently.
