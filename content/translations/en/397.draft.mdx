## Before We Begin

Over the last 13 parts, we have learned the technical side of *React* TDD. You now have enough practice to write tests and implement features on your own.
<br/>
The workplace is a little different. You may hear, ‘Who has time to write tests? We're already busy building features!’ Or you may inherit a huge codebase without a single test.
<br/>
Today we will look beyond the technical details and discuss **strategies for making TDD stick on a real project**.

<Ads1/>

## 1. The Costs and Benefits of Writing Tests (J-Curve)

The question I hear most often is, ‘Doesn't TDD make development take twice as long?’
The honest answer is that **it does take longer at first**.

- **Upfront costs**
  Setting up the test environment, creating mock data, and writing tests all take time.
- **Long-term benefits**
  The benefits become apparent as the project grows. You spend far less time tracking down bugs and doing QA, and refactoring becomes much less intimidating.

Think of it as *insurance*. You pay a premium in time each month, but when an accident happens and a bug appears, it can save you a great deal.

## 2. You Do Not Need to Test Everything

A major reason adoption fails in practice is that **people burn out trying to test everything**. Effective TDD requires choosing what to focus on.

- **What to test**
  - Core business logic, such as cart calculations and payment totals
  - Complex shared components, such as dropdowns and modals
  - Areas that change frequently or often have bugs
- **What you can skip**
  - Simple UI rendering, such as checking whether something is red
  - Files containing constants or simple configuration
  - Behavior built into *React* or third-party libraries

## 3. Automate Tests with a CI/CD Pipeline

Even excellent tests are useless if developers forget to run them.
The best approach is to **run tests automatically whenever code is pushed to GitHub**.
This is called *continuous integration* (CI).

### Example GitHub Actions Configuration

Create a `.github/workflows/test.yml` file at the project root, and GitHub will run the tests for you.

```yaml title=".github/workflows/test.yml" showLineNumbersname: Run Tests
name: Run Tests

on:
  push:
#    branches: [ main ] # main 브랜치에 푸시될 때만 동작하도록 변경
    branches: [ "**" ] # 모든 브랜치에 대해 동작하도록 변경
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      # 1. 코드를 내려받습니다.
      - uses: actions/checkout@v4

      # 2. Node.js를 설치합니다.
      - name: Use Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '18'

      # 3. 의존성 패키지를 설치합니다.
      - name: Install dependencies
        run: npm ci

      # 4. 테스트를 실행합니다. (이 단계가 실패하면 Merge가 막힙니다)
      - name: Run tests
        run: npm test
```

With this setup, if someone pushes a change that breaks the tests, GitHub shows a **red X** to flag the failure.
Let the system handle the checks so nobody has to remember to run them.

## 4. Working with Legacy Code (the Boy Scout Rule)

What do you do if you inherit a huge project without a single test?
Trying to write all the tests at once could take more than a year.

### The Boy Scout Rule
> Leave the place cleaner than you found it.

- If the component you need to change today is `Login.tsx`, write tests **just for that file**.
- When a bug occurs, add a test case that reproduces it, then fix it.

As you add tests bit by bit, the important logic gradually comes under test coverage.

<br/>
- **Cost and investment**
  Progress is slower at first, and the investment pays off during maintenance.
- **Automation (CI)**
  Use tools such as GitHub Actions to make tests run automatically and prevent mistakes.
- **Gradual adoption**
  Build coverage for legacy code incrementally, starting with the code you touch.
